# UD-36: capture of the recorded provider response

Registered against: `rt-proposals` (Proposal_Store format, task 7.1) and `rt-xtask export-script` (task 10.6). `rt-proposals` is registered against UD-36 in task 2.1.

## Decision

The user confirmed option 1 with these terms:

1. The Proposal_Store stores accepted structured provider responses and canonical proposals, with hashes and provider and source metadata.
2. Credentials, authorization headers and unnecessary transport data are never stored.
3. "Accepted" means accepted by the protocol, schema and provenance checks. It does not mean approved by a human reviewer.
4. A deterministic demo-script export is supported without another provider request.

## Options (design §8.11.7)

| --- | --- | --- | --- | --- |

## Effect on requirements

- **30.1 holds.** A rejected Provider_Response is never stored. Only a response that passed the protocol, schema and provenance checks is retained, inside its batch file.
- **27.3 holds.** `ruletrace-ai` still writes only the Proposal_Store and the Transmission_Log. The export is run by `rt-xtask`, which is tooling and not a delivered executable.
- **23.25 (RN-27).** The wording is narrowed from "no raw response is kept" to "no raw response is kept except the accepted response payload that the Proposal_Store retains". Credentials and authorization headers are never part of it.
- **Credential echo.** A response payload that contains the credential value is not stored (`RT-AI-0206`, batch rejected).
- **33.8 and 33.10.** The Recorded_Provider_Script is produced by the export, with the hashes of the stored responses. The live step never replaces it automatically.

## Retained content

Per batch file: `request_id`, `response_sha256`, the response `completion` and exact `payload` text, provider kind, model, adapter version, AI identities, caller-supplied `created_at`, and the canonical proposals with their ids. Nothing else of the transport (headers, URL query, credential) is retained.
