# UD-37: Meta Model API as the first real provider over the Responses protocol

Confirmed by the user. All six questions are resolved. Section 1 records the decisions. Section 2 records what was verified from vendor documentation. Section 3 records what was not verified. Section 4 records one open item that this record does not decide.

Requirements: 16.15, 16.17, 23.27 to 23.31, 23.39, 28.2, 28.8, 28.12, 28.17, 29.2, 33.8, 33.10, 35 (new). Design: §3.2, §3.4.5, §3.7.3, §3.7.5, §3.9.2, §8.11.6. Tasks: Phase 10 (10.1 to 10.17).

## 1. Decisions

### D1. Crates

- No `rt-ai-meta` and no `rt-ai-modal` crate.
- The planned crate `rt-ai-openai` is renamed `rt-ai-responses`. It implements the OpenAI Responses protocol, which Meta and OpenAI share, and includes the HTTPS transport planned in task 10.2.
- Meta and OpenAI are Provider_Profiles: constants and data in `rt-ai-tool`, documented with their documentation URLs. A profile holds no network code.
- A generic Chat Completions adapter (`rt-ai-compatible`) may come later, and only for a real use case. It is not part of this version.
- `rt-ai-adapter` stays provider-independent and network-free. Core crates are unchanged.
- `tools/allowed-edges.v1` (the `crate` lines and `forbid-external ... except-under`), `deny.toml` (`wrappers`), the `check-graph` list in `rt-xtask`, and the core-only job of `ci.yml` rename `rt-ai-openai` to `rt-ai-responses`. The specification text is updated now. The files are updated by task 10.2, which owns the dependency bans, and by the task that first links the crate.

### D2. Task 10.4 is un-deferred

- The Proposal_Schema sent to a provider is one provider-neutral flat node table with no recursive `$ref`.
- Limits the generated schema must meet: nesting depth at most 10, at most 5,000 properties. Strict mode needs `additionalProperties: false` and every property in `required`. The Meta Model API rejects recursive schemas, depth above 10 and more than 5,000 properties with HTTP 400.
- An expression of depth 16 must round-trip through the schema to the same Rule IR.
- There is one canonical Proposal schema for all providers. The generator is provider-neutral and does not live in the Responses crate.
- Task 10.4 is no longer optional and runs before the request-body task 10.1.

### D3. Proposal_Store format version 2

- Optional members `protocol`, `reported_model`, `response_id` and `usage` (`input_tokens`, `output_tokens`, `total_tokens`, each optional).
- Version 1 batches are still read. New batches are written as version 2.
- The configured model identity stays separate from provider-reported metadata. Provider-reported identity is never authoritative. No usage or cost is fabricated.

### D4. Configuration version 2

- A `[provider]` table with `id`, `protocol`, `model`, `endpoint`, `credential_env_var` and an optional `reasoning_effort`, a `[limits]` table, and an optional `[capabilities]` table of declarations.
- Version 1 still loads. It is mapped in memory to provider id `openai` and protocol `openai-responses`. The loader never writes or overwrites a user's configuration file.
- Provider id, protocol, model and credential environment variable are configured and validated independently.
- Official endpoint host restriction: for provider ids `meta` and `openai` the endpoint host must equal the documented official host (`meta`: `api.meta.ai`, `openai`: `api.openai.com`). Loopback endpoints are accepted only for tests. The credential is never sent to an arbitrary host. A custom compatible endpoint needs a separate explicit trust decision that is not part of this milestone, and is rejected.

### D5. First real provider

- Meta Model API over the Responses protocol. Base `https://api.meta.ai`. `POST /v1/responses`, `GET /v1/models`, Bearer authentication. The credential environment variable is named in the configuration (the documentation example is `MODEL_API_KEY`).
- Request body: `model`, `input`, `text.format = {"type":"json_schema","name":..,"schema":..,"strict":true}`, `store: false`, no tools, `max_output_tokens` a documented constant sized for reasoning tokens (reasoning tokens count toward it, minimum 16), and an explicit low reasoning effort (`reasoning.effort`) for the initial experiment.
- Accepted reasoning effort values: `none` (refused by the reasoning models), `minimal`, `low`, `medium`, `high`, `xhigh`, `max`.
- First model: `muse-spark-1.3` (Standard). The experiment may compare `muse-ember-1.0` on an identical small benchmark of public clauses.
- Contributor models are never used. A configured model identifier containing `contributor` is refused unless `allow_provider_training = true` is set. The experiment must not set it.
- Public competition documents and synthetic data only.
- The user runs the catalogue query (`ruletrace-ai models`) with their own local credential. The credential is never requested, printed or logged by an agent.
- No silent model change on failure, and no fallback chain.
- Response mapping: `status` completed, reasoning items ignored, exactly one message with exactly one `output_text`, no tool calls. Refusal and incomplete map to `Completion::Refused` and `Completion::Incomplete`.
- Error mapping, by HTTP status and error `type`:

| Shape | Mapping |
| --- | --- |
| 401 `invalid_api_key` | `AuthFailed` |
| 429 with `Retry-After` | `RateLimited` |
| 503 `service_overloaded` or `backend_unavailable`, `Retry-After: 60` | `Unavailable` |
| 504 `gateway_timeout` | `Unavailable` under Req 29.2 as written. See section 4 |
| 400 (schema violation) | `Other` |
| 402 billing | `Other` |

- Usage: `input_tokens`, `output_tokens`, `total_tokens` as reported, otherwise absent.

### D6. Modal

Deferred. No Modal LLM integration. The existing ASR deployment is not touched. No Modal endpoint or secret is needed.

### Capability model and model catalogue (part of D4 and D5)

- `rt-ai-adapter` gains `Capabilities`, `StructuredOutput`, a three-valued `Tri` (unknown, yes, no), a pure `negotiate()`, `Identity { provider, protocol, adapter_version }`, `Usage`, and `ProviderMeta` extended through a constructor with `#[non_exhaustive]`.
- An unknown required capability fails closed.
- New Diagnostics, with the numbers reserved in section 5: capability unsupported, model refused as training mode, endpoint host not permitted for the provider, model discovery failure, model not in the catalogue (only when `verify_model = true`).
- `ruletrace-ai models --config <file>` lists the catalogue. It sends the credential only, no document text, needs no consent, writes a Transmission_Log entry without documents, and never selects a model. `verify_model` is optional.

## 3. Not verified

These facts are not confirmed by any source read for this record. No requirement or task relies on them as established.

- OpenAI current limits (strict-mode properties, depth, `max_output_tokens`). Design §3.7.3 states 5,000 properties and 10 levels from an earlier reading. Task 10.15 re-checks them before the OpenAI profile is relied on.
- Meta Chat Completions usage field names. This version does not use Chat Completions.
- vLLM structured outputs. Not used.
- Prices and billing. No cost is computed or stated anywhere.
- The exact reasoning-token budget. `max_output_tokens` is a documented constant chosen in task 10.1 and measured in the live run. Its value is not decided here. The only fixed facts are the minimum of 16 (user-supplied) and that reasoning tokens count toward it.
- Error `type` and `code` strings (`invalid_api_key`, `service_overloaded`, `backend_unavailable`, `gateway_timeout`), `Retry-After: 60` on 503, HTTP 402 for billing, and the response shape of `GET /v1/models`. These come from the user's record. The stub tests (task 10.15) encode them as a contract, and the first real observation is the live run (10.8).
- That Meta documents `store: false` behaviour. The parameter is sent as required by Req 28.13. Whether the Meta Model API honours it is not verified.
- Data-use terms of the Standard and Contributor modes.

## 4. HTTP 504 `gateway_timeout` and Req 29.2 (OD-37-1, resolved)

Requirement 29.2 retried every HTTP 5xx response as a Transient_Failure. The Meta Model API returns 504 `gateway_timeout`, and the user's record says a 504 must not be retried unchanged. The hazard is that a retry re-sends byte-identical request bytes (Req 29.16) while the provider may still be generating, or may already have billed, the first answer. A reasoning model makes this more likely than a plain completion.

**Decision (user, 2026-11-16, option B, binding):** HTTP 504 is a final failure for the Responses adapters and for any adapter. It is never retried unchanged. Req 29.2 and Req 35.14 are amended. A 504 ends the request after one attempt with `AI_PROVIDER_ERROR` (RT-AI-0105, exit 5), no waiting time and no stored batch. The message names the HTTP status and none of the provider's text. Every other 5xx stays transient, and a `Retry-After` on a 503 is still treated as absent by Req 29.3.

Options that were offered: A, keep Req 29.2 as written with the `max_retries = 0` guidance; B, amend Req 29.2 so that 504 is not retried, for every provider (chosen); C, a profile-declared non-retried status for Meta only.

Implementation record: `ProviderFailure::GatewayTimeout` (non-transient); `ProviderFailure::is_transient` is also false for `Other { http_status: Some(504) }`; the pure `next_step` is unchanged; `rt-ai-responses` maps 504 to `GatewayTimeout`; the mock `failure_from_http` and the script `other` failure with `http_status` 504 give the same value.

## 5. Diagnostic codes reserved by this record

The catalogue entries are not added by this record. Adding a row to `catalogue/diagnostics.v1.json` changes the generated `Code` enum of `rt-foundation`, which is Rust code, so the rows are added by task 10.10 together with the regenerated file. The numbers are the next free numbers of their families and are reserved here.

| Code | Mnemonic | Severity | Exit | Meaning |
| --- | --- | --- | --- | --- |
| RT-AI-0011 | AI_CAPABILITY_UNSUPPORTED | Error | 2 | A capability that the run requires is declared no or is unknown for the provider profile |
| RT-AI-0012 | AI_MODEL_TRAINING_MODE_REFUSED | Error | 2 | The model identifier contains `contributor` and `allow_provider_training` is not true |
| RT-AI-0013 | AI_CONFIG_ENDPOINT_HOST_NOT_PERMITTED | Error | 2 | The endpoint host is not the official host of the provider id |
| RT-AI-0109 | AI_MODEL_DISCOVERY_FAILED | Error | 5 | The `GET /v1/models` request failed, was refused, or its response could not be read |
| RT-AI-0110 | AI_MODEL_NOT_IN_CATALOGUE | Error | 5 | `verify_model` is true and the configured model is not in the provider's catalogue |
