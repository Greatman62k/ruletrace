# UD-27: ledger format and atomic commit

Registered against: `rt-ledger` (parse and print, task 4.7), `rt-review` (task 6.1) and the commit protocol (task 7.3). `rt-ledger` and `rt-review` are registered against UD-27 in task 2.1.

## Decision

The user accepted the recommendation:

1. **Ledger format:** JSON Lines in RT-JSON.
2. **Commit protocol:** a journaled two-file commit (lock, temp files, journal, ordered rename, crash recovery).

## 1. Format comparison (design §3.8.1)

Line 1 of the chosen format is the header `{"format":"ruletrace-ledger","version":1}`. Each further line is one record in canonical compact form. `hash` is the SHA-256 of the record without the `hash` key, so it covers `prev`. A header-only ledger is a valid empty ledger (Req 26.6). `parse_ledger` verifies in this order and stops at the first failing record: syntax and fields (`RT-APR-0101`), sequence with no gap (`0103`), chain (`0102`), reviewer validity (`0105`), contradictions (`0104`).

| Option | Append semantics | Location of a bad record | Fit with atomic commit | Decision |
| --- | --- | --- | --- | --- |
| JSON Lines (header plus one record per line) | Natural, diff-friendly | Line number | Rewrite whole file via temp, same as any option | **Chosen** |
| One JSON document with `records` array | Rewrite of whole document | Line within pretty output | Same | Rejected: records are not independently addressable |
| TOML or binary | | | | Rejected: no canonical form needed beyond RT-JSON; extra parser |

## 2. Commit-protocol comparison (design §3.8.3)

| Option | Two-file atomicity | Reader never sees revision without record | Complexity | Verdict |
| --- | --- | --- | --- | --- |
| Single combined store | Trivial | Yes | Low, but ledger no longer a separate file (violates Req 26.1) | Rejected |
| Two sequential renames, in-process rollback only | Fails on crash | Yes (ledger first) | Low | Insufficient for crash |
| **Lock + temp + journal + ordered rename + recovery** | Atomic on failure; roll-forward after crash | Yes | Medium, about 300 lines, fault-injection tested | **Chosen** |
| Embedded database or write-ahead log library | Yes | Yes | Adds dependency; "no databases" in steering | Rejected |

Protocol outline: lock `<ledger>.lock`; recover from `<ledger>.journal` if present; load and verify; pure `plan_review`; write `.new` files and `.old` backups; write and sync the journal (the decision is durable from here); rename the ledger first, then the Rulebook; remove journal and backups; release the lock. A failure after the journal is written rolls back (exit 70, `RT-APR-0208`). A crash is recovered by the next review command under the lock.

Stated limits: no cross-filesystem or network-filesystem guarantee; no directory fsync on Windows; advisory locks bind only cooperating processes; anyone with write access can bypass everything (R-8, R-14). Fault injection through `FaultFs` at every step is a required test (Req 26.31).

## 3. Phasing

- The JSON Lines format is used from **Phase 2**.
- The one-file append is used from **Phase 4**.
- The journaled two-file commit is used from **Phase 5**.

The user confirmed the recommendation. Status: `Confirmed`.
