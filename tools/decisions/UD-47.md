Confirmed by the user on 2026-11-20 ("proceed with A+"), after review
`docs/reviews/2026-11-20-review-ud46-586aa5e.md` found that option A as applied
by UD-46 weakens T12d: the Launch_Secret authenticates for the whole session,
so a reader of the terminal scrollback during a session can use the
Laboratory, and a hostile local server that shows a Basic prompt can phish a
secret that stays usable.

## 1. Decision

Option A+ keeps HTTP Basic authentication (origin-scoped, which fixes T7) and
adds a binding cookie that the first successful login sets. After that, a
request needs both. The secret then works once, as in the original design:

| Holder | Has | Result |
| --- | --- | --- |
| Server on another local port (T7) | the cookie (cookies are not port-scoped) | refused: no Basic credentials reach it (browser evidence of 2026-11-20) |
| Reader of the scrollback (T12d), after the first login | the secret | refused: no cookie |
| Hostile server with a fake prompt, after the first login | the secret | refused: no cookie |

Remaining residual, the same as in the original cookie-exchange design:
whoever authenticates first, before the user, takes the session; the user sees
the refusal and restarts the Laboratory. Phishing before the user's first login
needs the user to visit the hostile server first; the terminal names the exact
address for the secret. Cross-origin requests still carry the cookie (other
ports are the same site) and the Basic credentials of the Laboratory's own
origin, so the Origin and CSRF checks stay load-bearing.

## 2. Behaviour (for the prototype now and `ruletrace-lab` later)

1. Checks, in order: Host (37.3); Origin (37.4); Basic credentials; binding
   cookie; CSRF token for state-changing requests (37.9).
2. Valid credentials, no Laboratory_Session yet, and no binding cookie: the
   request starts the Laboratory_Session and the response sets
   `rt_lab_session=<at least 128 bits>` with HttpOnly, SameSite=Strict, Path=/,
   no Domain, no Secure, no Expires or Max-Age.
3. While a Laboratory_Session exists: valid credentials and exactly one
   `rt_lab_session` cookie equal to the session's value: served. Valid
   credentials and a missing, repeated or different cookie: 403, with a body
   that says the session is bound to another browser and the Laboratory must be
   restarted, and no `WWW-Authenticate` challenge (a challenge would make the
   browser prompt again). Missing or invalid credentials, with or without a
   cookie: 401 with the Basic challenge. More than one Authorization header:
   401.
4. Session end (user end, or 30 minutes without an authenticated request; a
   refused request does not reset the limit): the secret and the cookie value
   are invalidated; every later request gets 401 until restart (LT-5).
5. Logs and the session directory hold no credential, Launch_Secret, session
   identifier, Authorization value, or CSRF token.

## 3. Draft amendment (awaiting approval of wording; not applied)

To be applied over UD-46 with Old/New records:

- **Laboratory_Session (draft).** The period from the first request that
  presents the valid Launch_Secret as HTTP Basic credentials while no
  Laboratory_Session exists, whose response sets the binding cookie, until the
  session is invalidated under Requirement 37 criterion 8 or 17, with its own
  temporary directory and its own CSRF token.
- **Launch_Secret (draft).** A random value of at least 128 bits that
  ruletrace-lab generates at each start and gives to the user only through the
  terminal, and that the browser presents as the password of HTTP Basic
  authentication for one Laboratory_Session, which is bound to the browser that
  presented it first by the binding cookie (Requirement 37 criteria 5 to 8).
- **37.6 (draft).** WHEN a request presents valid credentials and no
  Laboratory_Session exists, THE ruletrace-lab executable SHALL start the
  Laboratory_Session and SHALL set in the response one binding cookie whose
  value is a session identifier of at least 128 bits from the operating-system
  source of cryptographic randomness, with the attributes HttpOnly,
  SameSite=Strict, and Path=/, and with no Domain, Secure, Expires, or Max-Age
  attribute. THE ruletrace-lab executable SHALL hold at most one
  Laboratory_Session at a time; browser tabs that present the same credentials
  and the binding cookie belong to that Laboratory_Session.
- **37.7 (draft).** IF a request that passes the Host check of criterion 3 and
  the Origin check of criterion 4 carries no valid HTTP Basic credentials for the
  current Launch_Secret, or carries more than one Authorization header, THEN THE
  ruletrace-lab executable SHALL refuse it with HTTP status 401 and a
  `WWW-Authenticate: Basic` challenge. IF it carries valid credentials while a
  Laboratory_Session exists but not exactly one binding cookie equal to that
  session's identifier, THEN THE ruletrace-lab executable SHALL refuse it with
  HTTP status 403 and no `WWW-Authenticate` header, with a message that the
  session is bound to another browser and that the Laboratory must be
  restarted. In both cases it SHALL start no subprocess, SHALL read no workspace
  file, and SHALL write no file. The checks are made in this order: Host
  (criterion 3), Origin (criterion 4), credentials, binding cookie, CSRF token
  (criterion 9).
- **37.8 (draft).** As amended by UD-46, with "invalidate the Launch_Secret"
  replaced by "invalidate the Launch_Secret and the session identifier", and
  "authenticated request" meaning a request with valid credentials and the
  binding cookie.
- **37.18 and 37.22 (draft).** "session identifier" is listed again among the
  values that the session directory and the logs never hold.
- **37.24 (draft).** THE ruletrace-lab executable SHALL accept the binding
  cookie only together with valid HTTP Basic credentials; a request that carries
  the cookie but no valid credentials is refused under criterion 7.
- **37.25 (draft, the test).** "requests that present the valid credentials
  from a second browser tab, and requests that present credentials of an earlier
  Launch_Secret" becomes "a second browser tab, which shares the session; a
  second browser that presents the valid credentials without the binding cookie,
  which is refused with 403; and credentials of an earlier Launch_Secret, which
  are refused with 401".

Criteria 5 and 9 stay as amended by UD-46. Places to update when applied:
design §11.2 diagram, §11.5 notes, §11.18.5; threat model T7, T12d, R-L2, R-L7,
LT-6, and a new prompt-phishing row.

recorded, and an independent reviewer accepts the mitigation. The conditions
