# UD-48: LT-6 option A++

Confirmed by the user on 2026-11-20 ("start A++"). It supersedes the A+ draft
of UD-47, whose review `docs/reviews/2026-11-20-review-ud47-2bf4e89.md`
(NEEDS_CHANGES) showed that a binding cookie with `Path=/` also reaches a
hostile server on another port, so A+ does not stop phishing after login (B1).
This record folds in B1 to B3 and N1 to N6 of that review.

## 1. Idea

A++ keeps HTTP Basic authentication, which the browser sends only to the
Laboratory's own origin (scheme, host and port; browser evidence
`docs/security/2026-11-20-lt6-browser-evidence.md`). After the first login the
Laboratory moves the session to an unguessable Session_Path `/s/<token>/` and
sets a binding cookie scoped to that path. Cookies are not port-scoped, but a
browser sends a cookie only to request paths that match its `Path`. A server on
another port receives the cookie only if the browser requests that server at
`/s/<token>/`, which needs the token. The token is never sent to any other server; it is
held only by the user's browser (address bar, history, possibly browser sync)
and is visible on the user's screen. Every application request then needs three things: valid
Basic credentials, the Session_Path, and the binding cookie.

## 2. Who can do what

| Holder | Has | Result |
| --- | --- | --- |
| Server on another local port (T7) | neither credentials (never sent to it) nor the cookie (sent only to `/s/<token>/`, and it does not know the token) | nothing to replay |
| Reader of the terminal scrollback (T12d), after the first login | the secret | 403: no cookie, and the 403 never reveals the Session_Path |
| Hostile server that shows a Basic prompt (phishing), after the first login | the secret, if the user types it there | 403, as above |
| Page on another port that navigates the browser to the Laboratory | the browser's own credentials and, at `/s/<token>/` only, the cookie | without the token it cannot address the Session_Path, so it gets 403; in browsers that send `Sec-Fetch-Site` it is also refused as `same-site` or `cross-site` (criterion 4 as drafted); in a browser that does not send that header the unguessable path is the only control |

Residuals, stated and not mitigated further:

1. First-login race (as in the original cookie-exchange design): whoever
   presents the secret first starts the session. The user then gets the 403 of
   section 3 and restarts the Laboratory.
2. Phishing or scrollback before the user's first login: an attacker who
   obtains the secret before the user logs in can send `GET /` itself, receive
   the 303 and the cookie, and own the session, including approvals. The user
   then gets the 403 of section 3, whose text says to restart the Laboratory at
   once if the user did not start the session. The terminal names the exact
   address `http://127.0.0.1:<port>/` for the secret.
3. Three-part attack: the token (from the user's screen, history or sync),
   the cookie, and the secret. The cookie needs no user decision once the token
   is known: any page the user loads from a hostile server on another local port
   can request `/s/<token>/x` on that server, and the browser sends the cookie
   with it (cookies are not port-scoped and `SameSite=Strict` does not separate
   ports of one host). The secret comes from scrollback or phishing. All three
   are needed; the token is the part that is hardest to obtain.
4. Denial of service by any local server, for example oversized cookies set on
   `127.0.0.1` (cookie bombing) that push the request over the header limit.
   Unmatched cookie values are ignored, so cookie tossing alone does not deny
   access (N2).
5. Same-user processes (X5) can read browser history, which holds the token;
   outside the threat model, as before.
6. Usability: a browser restart drops the cookie and needs a Laboratory
   restart (LT-5); a new tab must use the session address, because `/` does not
   reveal it (N5); a link to the Laboratory from a page on another local port
   is refused as `same-site`; if the 303 of the start is lost, or the browser
   rejects the cookie, the session cannot be used and the Laboratory must be
   restarted. The run instructions (Requirement 36 criterion 23) state
   these.

## 3. Behaviour (prototype now, `ruletrace-lab` later)

1. Check order: Host (criterion 3); Origin and `Sec-Fetch-Site` (criterion 4,
   with the addition that any request whose `Sec-Fetch-Site` is `same-site` or
   `cross-site` is refused with 403; an absent `Sec-Fetch-Site`, or a value other
   than those two, is not refused on that ground, C1); Basic credentials; Session_Path and
   binding cookie; CSRF token for state-changing requests (criterion 9).
2. Missing or invalid credentials, or more than one Authorization header:
   401 with `WWW-Authenticate: Basic`. A cookie never replaces credentials.
3. Session start (B2, N1): only a `GET` whose request target is exactly `/`,
   with valid credentials, without a `Sec-Purpose` or `Purpose` header
   (prefetch, prerender; C3), while no Laboratory_Session exists, starts the
   session, in one atomic step (a single
   compare-and-set; exactly one request wins), whatever cookies it carries. The
   response is 303 with `Location: /s/<token>/` and `Set-Cookie:
   rt_lab_<port>=<identifier>; HttpOnly; SameSite=Strict; Path=/s/<token>/`, with
   no Domain, Secure, Expires or Max-Age. The token and the identifier are
   distinct values of at least 128 bits each from the operating-system source
   of cryptographic randomness. The request that starts the session is an
   authenticated request (B3) and starts the 30-minute clock. Any other
   request with valid credentials while no session exists gets 403 with a fixed
   body that says to open `/` (C2).
4. With a Laboratory_Session: a request with valid credentials, a path under
   the Session_Path, and at least one `rt_lab_<port>` cookie value equal to the
   identifier (values that do not match, from any number of Cookie lines, are
   ignored, N2, N4) is an authenticated request and is served. The path test is a
   byte-prefix match of the raw request target, before any decoding, against
   `/s/<token>/`; the token is 32 lowercase hexadecimal characters; a target
   that contains a dot-segment, a backslash, or a percent-encoded `.`, `/` or
   `\` is refused with 400 (C5). The token comparison and every cookie-value
   comparison run in constant time, and all cookie values are compared without
   an early exit (C6). Any other request with valid credentials, including `GET /`, a
   request losing the start race, a second browser and a request outside the
   Session_Path, gets 403 without `WWW-Authenticate`, with a fixed body saying
   that the session runs in the tab where it was started, that a new tab must use
   that tab's address, that another browser needs a restart of the Laboratory,
   and that the Laboratory must be restarted at once if the user did not start the
   session. No 403, 401 or 400 response contains the token or the identifier.
5. Pages and forms use relative URLs, so the token appears only in the
   `Location` header of the start response and in the browser's address bar,
   never in a response body. `Referrer-Policy: no-referrer` and
   `X-Frame-Options: DENY` (criterion 10) keep it out of Referer headers and
   frames. All application content, assets included, is under the
   Session_Path.
6. Session end (user end, or 30 minutes without an authenticated request; a
   refused request does not reset the limit): the secret, the token and the
   identifier are invalidated; every later request gets 401 until restart.
7. Logs record the path with the token replaced by `<session>`; logs, error
   bodies, terminal output and the session directory never hold the secret, the
   token, the identifier, an Authorization value or the CSRF token, and never
   echo a raw request target (C7).

## 4. Evidence required before LT-6 can close

1. Prototype server tests on three platforms for every rule of section 3
   (including C1 to C7), with mutants that remove each check (Host, Origin,
   `Sec-Fetch-Site`, credentials, Session_Path, cookie, CSRF, the start
   restriction to exactly `GET /`, the prefetch exclusion) and that reveal the
   token in a refusal.
2. Browser protocol on Firefox and Google Chrome: after login, the recorder on
   another port receives neither an Authorization header nor the cookie at `/`
   and `/other`; control: a request to the recorder at `/s/<token>/`, which the
   recorder's own page can trigger once it is given the token, does carry the
   cookie (this shows that the token's secrecy is load-bearing); the cross-origin POST is refused; the secret alone (a second
   browser profile) gets 403 without the token in the response.
3. The user's approval of the wording of section 5, and its application.
4. An independent reviewer's acceptance of the mitigation in the threat model,
   with the residuals of section 2.

## 5. Draft amendment of Requirement 37 over UD-46 (awaiting approval of wording; not applied)

- **Laboratory_Session (draft).** The period from the request that starts it
  under criterion 6 until it is invalidated under criterion 8 or 17, with its own
  Session_Path, Session_Identifier, temporary directory and CSRF token.
- **Session_Path (new, draft).** The path `/s/<token>/` of one
  Laboratory_Session, where the token is a random value of at least 128 bits;
  every application resource of the session is under it.
- **Session_Identifier (new, draft).** A random value of at least 128 bits,
  distinct from the token, carried in the binding cookie `rt_lab_<port>` of one
  Laboratory_Session.
- **Launch_Secret (draft).** As amended by UD-46, with "for one
  Laboratory_Session" kept and "(Requirement 37 criteria 5 to 8)" kept.
- **Authenticated request (new, draft).** A request with valid HTTP Basic
  credentials for the current Launch_Secret whose path is under the
  Session_Path and that carries at least one binding-cookie value equal to the
  Session_Identifier, and the request that starts the Laboratory_Session.
- **37.4 (draft, added sentence).** IF any request carries a Sec-Fetch-Site
  header with the value `same-site` or `cross-site`, THEN THE ruletrace-lab
  executable SHALL refuse it with HTTP status 403, SHALL start no subprocess,
  and SHALL write no file.
- **37.5 (draft).** As amended by UD-46, with "together with the fixed user
  name `lab`" extended to "together with the fixed user name `lab` and the
  address `http://127.0.0.1:<port>/` (or the `[::1]` form) to open".
- **37.6 (draft).** WHEN a GET request for `/` presents valid credentials and no
  Laboratory_Session exists, THE ruletrace-lab executable SHALL start the
  Laboratory_Session in one atomic step, whatever cookies the request carries,
  and SHALL answer with HTTP status 303 to the Session_Path and with one
  Set-Cookie header for `rt_lab_<port>` whose value is the Session_Identifier,
  with the attributes HttpOnly, SameSite=Strict, and `Path=` the Session_Path,
  and with no Domain, Secure, Expires, or Max-Age attribute. THE ruletrace-lab
  executable SHALL hold at most one Laboratory_Session at a time; of concurrent
  requests that could start it, exactly one SHALL start it. A request that
  carries a Sec-Purpose or Purpose header SHALL NOT start it. Browser tabs that
  use the Session_Path with the binding cookie belong to that
  Laboratory_Session. The Launch_Secret is valid for that Laboratory_Session
  only.
- **37.7 (draft).** IF a request that passes criteria 3 and 4 carries no valid
  HTTP Basic credentials for the current Launch_Secret, or more than one
  Authorization header, THEN THE ruletrace-lab executable SHALL refuse it with
  HTTP status 401 and a `WWW-Authenticate: Basic` challenge. IF it carries valid
  credentials and is neither an authenticated request nor a request that starts
  the Laboratory_Session under criterion 6, THEN THE ruletrace-lab executable
  SHALL refuse it with HTTP status 403 and no `WWW-Authenticate` header, with a
  fixed message that the session runs in the tab where it was started, that a
  new tab must use that tab's address, and that another browser needs a restart.
  No 401 or 403 response SHALL contain the Session_Path token or the
  Session_Identifier. In each case it SHALL start no subprocess, SHALL read no
  workspace file, and SHALL write no file. The checks are made in this order:
  Host (criterion 3), Origin and Sec-Fetch-Site (criterion 4), credentials,
  Session_Path and binding cookie, CSRF token (criterion 9).
- **37.8 (draft).** As amended by UD-46, with "invalidate the Launch_Secret"
  replaced by "invalidate the Launch_Secret, the Session_Path and the
  Session_Identifier", and "no authenticated request" meaning no authenticated
  request in the sense of the definition above.
- **37.9 (draft, issuance sentence).** "first with the page that answers the
  request that starts the session" becomes "first with the page at the
  Session_Path that the browser requests after the redirect of criterion 6".
- **37.18 (draft).** The list of values that the session directory never holds
  becomes "credential, Launch_Secret, Session_Path token, Session_Identifier, or
  CSRF token".
- **37.19 (draft, first condition).** "lacks valid HTTP Basic credentials for
  the current Launch_Secret" becomes "is not an authenticated request", and the
  test that omits each element in turn omits the credentials, the Session_Path
  and the binding cookie separately.
- **37.22 (draft).** The path is logged with the Session_Path token replaced by
  `<session>`; the list of values never logged becomes "document text, Proposal
  text, credential, Launch_Secret, Authorization header value, Session_Path
  token, Session_Identifier, or CSRF token".
- **37.23 (draft, list of mutants).** Adds criteria 6 and 22 and a separate
  mutant for each of the credential check, the Session_Path check and the
  binding-cookie check of criterion 7.
- **37.24 (draft).** THE ruletrace-lab executable SHALL accept a binding cookie
  only in an authenticated request and SHALL ignore every cookie value that does
  not equal the Session_Identifier, compared in constant time, from any number of
  Cookie header lines.
- **37.25 (draft, the test).** The test list becomes: a second tab that uses the
  session address, which shares the session; a tab opened at `/` after the start,
  which gets 403 without the token; a second browser with valid credentials,
  which gets 403; concurrent first requests, of which exactly one starts the
  session; credentials of an earlier Launch_Secret, which get 401; and a cookie
  of the same name set with `Path=/`, which does not deny access.

Places to update when applied: Requirement 36 criterion 23 (run
instructions: user name `lab`, the address, the browser prompt, and the
