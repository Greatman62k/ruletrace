Status: **Pending** (awaiting the user's answers in "Questions for the user"). Nothing here is Confirmed. The `check-decisions` vocabulary is `Confirmed` or `Pending` only.

## What this record does not assert

No claim is made here about whether the Kiroween 2026 rules page or the ICC Men's T20 World Cup 2026 pages publish usable scores, group results or net run rate (NRR) values, or under what licence. Nothing has been fetched. Each such fact is listed below as "to verify", with who verifies it.

## Constraints already fixed

- UD-34 (Confirmed): Prize Check uses the Kiroween 2026 Official Rules. Its iterative tie-break is reported as needing human adjudication or Unsupported, and prize allocation is out of scope. Bracket Check uses the ICC Men's T20 World Cup 2026 Playing Conditions, clauses 16.10.1 to 16.10.7, with supplied and verified NRR values and no bracket generation or seeding.
- UD-32 (Confirmed): Rank_Reference, kept separate from External_Ranking_Value.
- Req 33.13: data must include an eligible participant, an ineligible participant, a participant with a Missing_Value giving an Indeterminate Outcome, a Tie_Group, one Published_Result equal to the computed result, and one with a deliberately seeded difference labelled as seeded in the manifest.
- Design §8.11.10: the Missing_Value belongs to an eligibility input only. `standings-missing.csv` is a separate small file with a missing ranking key (Req 32.7).
- Req 34.6 and ST-SYNTHETIC (§8.12): synthetic data is labelled synthetic in the manifest, the runbook and the Proof_Report header, and is never presented as real results.
- NRR values are labelled as supplied (UD-34), whichever option is chosen.

## The `nature` manifest field (design §8.11.3)

Each `data[]` entry has `path`, `sha256`, `nature`, `note`, `seeded_difference`.

| Field | Values | Meaning |
| --- | --- | --- |
| `nature` | `real` | Values copied from a published source that is named in `note` (address, edition, retrieval text) and licensed for the committed use |
| `nature` | `synthetic` | Values written for the demonstration, with no claim that they are real results |
| `seeded_difference` | `true` only for the file holding the deliberately different Published_Result | Labels the seeded difference. `false` for every other file |

Proposed handling of a file that mixes real and synthetic values: not allowed. Split the file so each file has one `nature`. The user may instead ask for a third value `mixed`; that would change the design §8.11.3 enumeration and is not recommended.

A file whose values are real but whose licence is not recorded cannot be `real`. The manifest test already fails when a licence is absent for a document. For data files the equivalent check (licence reference in `note` for each `real` file) is a proposed addition to task 11.2, to be confirmed with this decision.

## Alternatives

### (a) Real where licensed, otherwise synthetic and labelled (recommended)

Use real published values for any file where the source is public, the values fit the Rulebook, and the licence permits committing them. Everything else is synthetic and labelled. Expected shape, to be confirmed by the verification below: Prize Check data is synthetic (the Kiroween rules page is a rules document, and whether it publishes any scores is unverified). Bracket Check group results and NRR are real only if a licensed public source is verified. The Published_Results follow the nature of the data they compare against.

Consequences:

- Honest-claims (11.9): ST-SYNTHETIC lists exactly the synthetic files per demonstration. Real files need a source and edition statement. Both Proof_Report headers differ per demonstration.
- Claims lists (11.8): `required-statements.v1.json` keeps ST-SYNTHETIC as conditional (present when any file is synthetic). The prohibited-phrase list must reject wording that presents synthetic data as actual results, and wording like "official results" for any synthetic file.
- Goldens (11.5): unchanged in shape. Real values are copied byte-exact from the source, so they must be re-blessed if the source edition changes.
- Demo acceptance (11.6): asserts Req 33.13 composition from the golden results, plus a check that every file's `nature` matches the runbook and header statements.
- Reproducibility (Property 48): holds, because files are committed and the offline flow reads no network. Real data adds no run-time dependency.
- Risk: a real file may not contain an eligible, ineligible, Missing_Value or Tie_Group case. The composition must then come from a synthetic companion file, and the labels must keep the two apart.

### (b) All synthetic and labelled

Every data file and Published_Result is written for the demonstration.

Consequences:

- Honest-claims (11.9): ST-SYNTHETIC applies to every file. The README (11.10) says no real competition results are used.
- Claims lists (11.8): same lists as (a), with the synthetic statement always required.
- Goldens (11.5): fully under our control, no source edition to track.
- Demo acceptance (11.6): the composition of Req 33.13 can be guaranteed by construction. The `real` value of `nature` is never exercised in the demonstration, so the manifest test needs its own fixture for it (task 11.2 or 6.x manifest tests).
- Reproducibility (Property 48): holds.
- Cost: weaker demonstration of fit to real documents. No licensing work.

### (c) All real

Every file and Published_Result is a real published value.

Consequences:

- Likely infeasible. Req 33.13 needs an Indeterminate participant, a Missing_Value on an eligibility input, and a seeded Published_Result. A seeded difference is by definition not a real published value, so (c) cannot satisfy Req 33.13 as written. A real Published_Result with an altered value would be a modified real record and would need its own label.
- Honest-claims (11.9): ST-SYNTHETIC would be inapplicable, but the seeded file still needs labelling as seeded.
- Claims lists (11.8), goldens (11.5), acceptance (11.6): depend on licensing and fit that are unverified.
- Reproducibility (Property 48): holds if committed, but a licence that forbids committing breaks it.
- Not recommended. Choosing it would need a Req 33.13 change, which is the user's decision.

## One equal and one seeded-difference Published_Result

In every option:

- `published.csv`: a Published_Result equal to the computed result. `seeded_difference: false`. Its `nature` follows the data it was derived from. If the computed result is produced by RuleTrace, an "equal" Published_Result written by the author is synthetic by definition (it copies our computed output). Only a result published by an outside authority can be `real`.
- `published-seeded.csv`: the same shape with one deliberate difference. Always `seeded_difference: true`. Always labelled seeded in the manifest, runbook and Proof_Report header. The seeded file is never `real`.

Question for the user: which demonstration carries the equal and the seeded Published_Result. Proposed default: both demonstrations carry both, since the Req 33.15 acceptance test asserts them for the demonstration data as a whole. This is the minimum that needs confirming.

## Labelling requirements (all options)

- Manifest: `nature` on every data file, `seeded_difference` on every data file, `note` naming the source for `real` files and the reason for `synthetic` files.
- Demo_Runbook: states which inputs are real, synthetic or scripted (Req 33.12), and that the seeded Published_Result is seeded.
- Proof_Report header and application report headers: ST-SYNTHETIC and the list of synthetic files, when any exist.
- `demo/README.md` (11.10): what is real, what is synthetic or stand-in.
- Supplied NRR values: labelled as supplied wherever they appear, whichever `nature` they have.

## Licensing and attribution questions (to answer, not assumed)

2. What attribution text does the source require, and where does it go (manifest `note`, README, report header)?

## Interaction with RN-30

RN-30 (open): how Competition_Data carries External_Ranking_Value metadata (authority, edition or effective date, provenance). It needs its own user decision and changes the Competition_Data format.

Does UD-35 depend on RN-30? **Not for confirmation, and not for the minimum demonstration.** The Req 33.13 composition needs no External_Ranking_Value. Under Req 14.25, any Rule that needs one is Unsupported until RN-30 is decided, and UD-34's scope (group points, ranking, ordered criteria, top-two qualification through Rank_Reference) does not require one.

It becomes a dependency only if the user wants a real or synthetic external ranking (for example a pre-event seeding list) as a tie-breaker in the demonstration data. In that case:

- RN-30 must be decided first, because the data file layout would depend on the carrying form.
- That ranking must be supplied in Competition_Data with authority, edition and provenance, never fetched or invented (Req 14.20).
- A synthetic external ranking must be labelled synthetic like any other data. Presenting it with a real authority name would be a false claim.

Question 5 below asks whether the demonstration uses one. Proposed default: no, so UD-35 is independent of RN-30.
