# UD-38: RuleTrace Laboratory, category Frankenstein, three runtime executables

Confirmed by the user on 2026-11-18. This record states the decision, what it supersedes and keeps, the consequences for requirements and tasks, and the open items that the Laboratory threat model (task L1) must resolve. It changes documentation only. No code, test, golden file, `tasks.md` or `design.md` text is changed by the phase that records it.

Requirements: 7.23, 15 (unchanged, checked), 24.12 and 24.13, 27 (user story, 27.1, 27.15), 31.3, 31.10 to 31.12, 32.1, 33.7, 34.1, 36 (new), 37 (new). Steering: `product-principles.md`, `technical-architecture.md`.

## 1. Decision

### Category and product

The submission category changes from Kiroween "Skeleton Crew" to "Frankenstein".

The product is **RuleTrace Laboratory**: one integrated application combining AI-assisted rule interpretation, human approval, deterministic Rust execution and auditable proof.

Tagline: "A language model guesses. A rulebook must be exact. We stitched them together without trusting the guess."

It is one integrated local application with selectable Prize and Tournament (standings) demonstration workflows. It is not two standalone products. The existing engine, data, explain, AI and provider crates, ledger, CSV mapping, report models, tests, fixtures and goldens are kept. The workspace is not restructured. There are no top-level `prize-check/` or `bracket-check/` folders.

### The user's decisions, quoted

D1, scope and steering (approved, narrow):

> Allow exactly one local RuleTrace Laboratory front end: one integrated local application; a local browser interface served by a new executable `ruletrace-lab`; a front end to the existing compiler, approval and execution machinery that may orchestrate existing processes but never replaces their authoritative responsibilities. Still out of scope: hosted application services, cloud dashboards, user accounts and remote authentication services, hosted databases, a general-purpose workflow SaaS, and replacing the compiler or engine with UI-side logic. The Laboratory is a functional interface to RuleTrace, not a substitute for it.

D2, process separation (non-negotiable):

> `ruletrace-ai` = provider integrations and AI credentials, natural-language interpretation, untrusted structured proposals, provider/model/usage metadata, no access to approval or execution authority. `ruletrace` = review and approval, append-only ledger, validation, compilation, deterministic evaluation, provenance and proof verification; no AI credentials and no network. `ruletrace-lab` = local web interface, workflow orchestration, display of proposals, findings, approval history and decisions, controlled invocation of the existing CLI processes; no direct ledger writes; no independent approval or decision-making authority; no AI provider credentials. The Laboratory never approves automatically; an approval requires an explicit human action, a reviewer identity, and confirmation of the exact rule revision and content hash. Credential isolation: the Laboratory must not inherit, read, expose, persist or log the AI provider credential; process separation alone does not prove credential separation; the threat model (task L1) must resolve the subprocess/credential mechanism, and if the chosen mechanism makes the credential reachable by the Lab a safer mechanism must be chosen before implementation. Process hand-offs use hash-bound, validated file artifacts; AI output stays untrusted even with a valid hash. Existing CLI trust boundaries stay intact.

D3, user interface form:

> Local web Laboratory served by `ruletrace-lab`, loopback-only binding, never remotely accessible or hosted. The threat model must address: loopback-only binding; Host and Origin validation; CSRF protection and session authorization; no CORS; no remote scripts, fonts, images or other external UI dependencies; restricted filesystem access; safe subprocess invocation without shell-string construction; input validation and output escaping; session shutdown and temporary-file handling; protection against unauthorized approval requests. No long-lived access token in the URL (browser history/referrer leakage); design a safer per-session authorization mechanism. A real usable workflow, not a static mockup. The submission must provide a reproducible build or installation/run instructions (a localhost URL alone is not accessible to judges).

D4, executable set:

> The product runtime executable set becomes exactly `ruletrace`, `ruletrace-ai`, `ruletrace-lab`. prize-check and bracket-check become library workflow modules under crates/ (input mapping, workflow question construction, application-specific report presentation; no duplicated business logic). Distinguish development/test utilities (e.g. rt-xtask) from the product runtime executable set.

D5, metaphors must represent actual behaviour:

> Brain = untrusted AI proposals and validation findings; Spine = human approval and the hash-chained ledger; Heart = compilation and the exact-arithmetic deterministic engine; Lightning = execution of the approved compiled rulebook (the creature comes alive at deterministic execution, never when the AI responds); Ghost = missing data and Indeterminate outcomes; Autopsy = proof reports, calculation traces and source provenance. No decorative elements that do not improve comprehension.

The existing deferrals (9.3 `rank_reference` and the others recorded in `tasks.md` under "Approved deferrals") remain in force.

## 6. Open items for the L1 threat model

The requirements state what must hold. The threat model and design decide how.

1. Credential mechanism. How `ruletrace-ai` obtains its credential when the Laboratory starts it, without the credential being in the Laboratory process environment, files, logs or responses. Candidates: the user starts `ruletrace-ai` through a separate terminal step; a launcher that is not the Laboratory; a pre-existing credential file or OS credential store read only by `ruletrace-ai` (this changes Req 28 and needs a user decision); or the Laboratory spawns `ruletrace-ai` with an environment that excludes the variable while the variable is supplied another way. A mechanism that makes the credential reachable by the Laboratory is rejected before implementation. Process separation alone is not accepted as proof. A canary test must verify the result.
2. Per-session authorization without a long-lived URL token: a one-time launch secret exchanged for an HttpOnly, SameSite=Strict, Path-scoped cookie, or an equivalent. Lifetime, rotation and single-use behaviour.
3. HTTP server implementation: dependency choice, written justification, loopback-only listener, request size limits, no CORS, Content-Security-Policy, no external assets.
4. Filesystem roots: which directories the Laboratory may read and write (workspace directory, a per-session temporary directory), path canonicalisation, symlink handling.
5. Subprocess invocation: argument vectors only, fixed executable resolution (no PATH search from user input), environment allow-list, output size limits, timeouts, cancellation.
6. Hash-bound hand-offs: which artifact is hashed, who verifies it, how a changed file between display and approval is detected (the approval confirmation names revision number and Rule_Content_Hash and `ruletrace review` verifies them).
7. Whether the Laboratory may link the Workflow_Module libraries (which depend on the Rules_Engine) for mapping, Question construction and presentation while obtaining every Outcome from a `ruletrace evaluate` subprocess. Requirement 36 criterion 10 and Requirement 24 criterion 13 require that the Laboratory calls no engine evaluation function. A source scan or an edge rule must enforce this. The design confirms or chooses another split.
8. Reviewer identity entry: a free-text string (Req 26, R-8 deferral of authentication) and how the Laboratory prevents an AI identity from being entered (UD-23 string comparison).
9. Demo mode: how `mock-replay` is selected without a credential, and how the Laboratory labels the recorded run as a replay of recorded Reviewer decisions.
10. Distribution: build and run instructions for judges (source build with the pinned toolchain; optionally a prebuilt release artifact). A localhost URL alone is not a deliverable.
11. Single-user concurrency: two browser tabs, repeated approval requests, and the existing review lock.
12. Session shutdown: idle timeout, explicit stop, temporary-file cleanup, behaviour on a crashed Laboratory.
