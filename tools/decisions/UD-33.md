# UD-33: packaging of the Application_Layers

Awaiting the user's decision. This record is `Pending`. `rt-xtask check-decisions` accepts only `Confirmed` or `Pending`, so `Pending` is the "awaiting user decision" value. Nothing here is a confirmation. The orchestrator sets `Confirmed` only after the user answers.

Registered against: `prize-check` and `bracket-check` in `tools/decision-gates.v1` (task 2.1). Requirements 27.1, 27.15, 31.3. Design §8.2, §9.2.

## Question

How are the two Application_Layers (Prize_Check and Bracket_Check) delivered, and what is the set of executables the workspace builds?

- A. A third RuleTrace executable with `prize-check` and `bracket-check` subcommands.
- B. Two small Demonstration_Executables, `prize-check` and `bracket-check`, one Cargo package each (library target plus binary target of the same name). Recommended.
- C. Library-only packages. Cargo `examples/` targets and tests are the only entry points.

## Current state of the spec (applied before confirmation)

Requirements and design already apply B as "Recommended-pending". Req 27.1 says exactly two RuleTrace executables plus exactly two Demonstration_Executables. Req 27.15 tests that the built executable set equals `ruletrace`, `ruletrace-ai`, `prize-check`, `bracket-check`. Req 31.3 names a Demonstration_Executable of the same name as its crate. `tools/allowed-edges.v1` already lists both packages as `class app`. The packages do not exist yet (tasks 9.5 and 9.6). Until this record is `Confirmed`, neither may be added to the workspace, because `check-decisions` fails for a gated workspace member.

## Options

### Option A: third RuleTrace executable with subcommands

- Description: one new executable (for example `rt-apps`) with `prize-check` and `bracket-check` subcommands over both Application_Layer libraries.
- Packages: both Application_Layer crates (Req 31.1 requires separate crates) plus one new binary package that depends on both.
- Executables: 3 (`ruletrace`, `ruletrace-ai`, the new one).
- Req 27.15 test: set of three names. Req 27.1 needs a different amendment (three RuleTrace executables, `ruletrace` and `ruletrace-ai` unchanged).
- Req 31.3: not satisfied as written. No executable has the name of its crate. Needs a rewording.
- Dependency graph and allowed edges: the new binary depends on both applications. The edges `forbid-name prize-check -> bracket-check` and the reverse stay valid for the libraries, but the new package needs its own class and edge entry, and `tools/decision-gates.v1` needs a gate line for it.
- CI jobs: the gate set gains one executable. `check-executables` expects three names.
- Demo runbook: s08 calls one binary with two subcommands.
- Claims the demo can make: both applications run, but from one binary and one dependency tree. This weakens the claim "two applications, one engine".
- Risks: couples both applications; adds a third entry point to the RuleTrace executables; re-opens Req 27.1, 31.1 and 31.3.
- Status in the design: rejected.

### Option B: two Demonstration_Executables, one package each (recommended)

- Description: each application is one Cargo package whose name equals its executable name. The library target (`lib.rs`, `mapping.rs`, `questions.rs`, `report.rs`) has no I/O. The binary target (`main.rs`, `io.rs`) reads the named files and writes the named report files by temp file and rename. Only `io.rs` and `main.rs` may do I/O.
- Packages: `prize-check`, `bracket-check` (two). No `rt-*` package added.
- Executables: 4 (`ruletrace`, `ruletrace-ai`, `prize-check`, `bracket-check`).
- Req 27.15 test: the built executable set equals exactly those four names. The criteria 5 to 7 and 9 to 13 of Req 27 apply to `ruletrace` and `ruletrace-ai` unchanged. Neither Demonstration_Executable is a command of, started by, or in the dependency tree of those two.
- Req 27.1: one amendment (already made). Req 31.3 holds literally.
- Dependency graph and allowed edges: as already in `tools/allowed-edges.v1` (lines 25 to 26, 43 to 45): `rt-foundation rt-numeric rt-data rt-compiled rt-engine rt-explain rt-srcmodel`, with transitive bans and no edge between the two applications. No change.
- CI jobs: `check-executables` and `check-app-layers` (task 9.8) cover four names. `demo-offline` runs s08 by invoking the two binaries. `cargo build --workspace --bins` builds them.
- Demo runbook: s08 runs `prize-check` and `bracket-check` as ordinary commands with `--emit-*` and `--report-*` options. Byte identity with `ruletrace evaluate` is checked on the emitted files and the exit code.
- Claims the demo can make: two independent applications, each with its own binary and tree, over one engine, with an ordinary command line for a reviewer. Allowed claims stay inside the First_Version_Support_Boundary (Req 34).
- Risks: two executables beyond the two RuleTrace executables; I/O code in two `io.rs` files (about 60 lines each) that the file allowlist and process tests must cover; Req 27.1 wording differs from the original steering text, so steering files need the update of task 9.19.

### Option C: library-only packages with `examples/` targets

- Description: `prize-check` and `bracket-check` become library-only packages. Entry points are Cargo `examples/` targets and tests.
- Packages: `prize-check`, `bracket-check` (two, library only).
- Executables: 2 built by `cargo build --bins` (`ruletrace`, `ruletrace-ai`). Examples are built by `cargo build --examples` and by `cargo test`.
- Req 27.15 test: reverts to two names, `ruletrace` and `ruletrace-ai`. Req 27.1 reverts to its earlier wording. Req 31.3 and the Demonstration_Executable glossary term change to examples.
- Dependency graph and allowed edges: no change to the package edges. The example targets need an I/O allowlist entry in `tools/scan-allow.v1` and in `check-app-layers`.
- CI jobs: `check-executables` expects two names and must ignore examples explicitly. `demo-offline` s08 runs `cargo run --example` or a test harness. Needs a toolchain and a build in the demo job.
- Demo runbook: s08 is no longer an ordinary command. A reviewer needs the Cargo workspace and a build step.
- Claims the demo can make: the applications are thin libraries over the engine. The claim "a reviewer can run Prize_Check and Bracket_Check as commands" cannot be made.
- Risks: poor reviewer entry point; examples are built by `cargo test` and are easy to miss; Req 31.11 and 31.12 (exit codes, no env, no network) must be restated for examples; process tests in 9.17 launch examples through Cargo, which adds environment dependence that the tests must exclude.

## Comparison

| Aspect | A | B (recommended) | C |
| --- | --- | --- | --- |
| Executables the workspace builds | 3 | 4 | 2 |
| Packages added | 2 libraries plus 1 binary | 2 | 2 |
| Independence of the two applications | One binary and one tree couple them | Separate binary and tree each | Separate libraries |
| `ruletrace` and `ruletrace-ai` trees | Unchanged | Unchanged | Unchanged |
| Req 27.15 executable-set test | Three names | Four names | Two names |
| Req 31.3 (same name as crate) | Not met | Met | Not met |
| Reviewer entry point | Good | Good | Poor |
| Spec edits needed | 27.1, 27.15, 31.1, 31.3 | None beyond those already applied | 27.1 (revert), 27.15, 31.3, 31.11, 31.12 |

## Recommendation: B

1. It keeps the two applications independent and keeps one engine visibly behind both.
2. It leaves the dependency trees and the Req 27 criteria 5 to 7 and 9 to 13 of `ruletrace` and `ruletrace-ai` unchanged.
3. One package per application satisfies Req 15.8 (exactly two Application_Layer crates) and Req 31.3 literally.
4. It gives a reviewer ordinary commands for the demonstration.
5. The spec, `tools/allowed-edges.v1` and `tools/decision-gates.v1` already assume it. Choosing B changes nothing.
6. The cost is one amendment of Req 27.1 and a small `io.rs` per application, both bounded and testable.

## Consequences of confirming B

- Tasks 9.5 to 9.8 proceed as written. The gate on `prize-check` and `bracket-check` clears.
- `check-executables` expects exactly four names.
- Steering updates 6 to 8 of design §9.3 (task 9.19) describe two demonstration executables.

## What changes if the user chooses differently

Choosing C:

- `prize-check` and `bracket-check` become library-only packages with `examples/` targets. The `main.rs` and `io.rs` binary files become example files. The executable-set test of Req 27.15 reverts to two names (`ruletrace`, `ruletrace-ai`).
- Req 27.1 and the Requirement 27 user story return to "exactly two executables". Req 31.3, 31.11, 31.12, the Demonstration_Executable glossary term, UD-22 and the traceability and consistency notes change accordingly.
- Tasks 9.7, 9.8, 9.17, 9.18, 9.20, 11.11, 11.13 and 11.14 are reworded: the executables become examples, `check-executables` checks two names and ignores examples by rule, and s08 runs examples.
- `scan-allow.v1` needs an entry for the example files. `allowed-edges.v1` and `decision-gates.v1` need no change.
- Claims: the demonstration cannot state that Prize_Check and Bracket_Check run as ordinary commands.

Choosing A:

- A new binary package is added with its own `allowed-edges.v1` entry and gate line. Req 27.1, 27.15, 31.1 and 31.3 are reworded. Tasks 9.5 to 9.8 change, and task 9.7 builds the third binary. The design rejects this option, so it needs a design change as well.

An answer that is none of A, B or C, for example separate library and binary packages (four packages), conflicts with Req 15.8 and 31.3 as written (design §8.2 considered and rejected it). It needs a requirements change first.
