# UD-45: remaining LT-6 and LT-7 decisions

Confirmed by the user on 2026-11-20 ("your recommendations are ok apply them"),
on the four recommendations given after the LT-7 real-executable evidence
(`docs/security/2026-11-20-lt7-lifeline-real-executables.md`).

## 1. LT-6: check order (decided)

For option A of design §11.18.5 (HTTP Basic authentication, no session
cookie), each request is checked in this order: Host; then, for a
state-changing request, Origin; then the Basic credentials; then, for a
state-changing request, the CSRF token. A cross-origin POST is therefore always
refused with 403 and never causes a credential prompt. This is the order of
the prototype `spikes/lt6-basic-auth`, which the review
`docs/reviews/2026-11-20-review-spk-19290e1.md` accepted.

## 2. LT-7 V-2: signal handling (decided, option a)

Design §11.11 states that `std` has no portable signal API and offers a small
dependency or treating Ctrl+C as an abrupt exit. The user chose the dependency,
which keeps Req 37.17 as written (orderly shutdown on SIGINT, SIGTERM and
Ctrl+C). Candidate: the `ctrlc` crate (docs.rs lists 3.5.3 on 2026-11-20;
licence MIT or Apache-2.0; the `termination` feature adds SIGTERM and SIGHUP;
alternative `signal-hook`). The workspace crates keep
`#![forbid(unsafe_code)]`. Whether the crate itself uses `unsafe`, its
transitive dependencies and its maintenance status are checked when it is
added. It is added only with `ruletrace-lab` (13.4), through the dependency
procedure (justification in `tools/dependencies.v1`, `check-justification`,
`cargo deny`). The `termination` feature also handles SIGHUP, which Req 37.17
does not name; 13.4 decides whether SIGHUP is handled the same way, and if so
tests it. V-2 is verified by three-platform tests in 13.4/13.6. Nothing is added
now.

## 3. LT-7 V-1 and V-4: kill harness (approved, test only)

The user approves a test-only harness that kills the real `ruletrace-ai
propose` and `ruletrace review approve` at many points across their write
phase on Linux, macOS and Windows, and then checks that the next run accepts or
recovers the state (V-1: "Kill during a store write leaves no file that a later
run rejects (§11.6)"; V-4: "Kill of a real `ruletrace review approve` and
`ruletrace-ai propose` during the write leaves a recoverable state"). It
extends the scoped exception of UD-44: test code only, no production change,
no test hook in production code. Method: for each executable and platform,
at least 100 trials, each killing the process after a delay drawn
deterministically (fixed seed, recorded) across the measured duration of its
write phase; after each kill the state on disk is classified as "before the
write", "during the write" (temporary or journal file present) or "after the
write", and the next run (or the recovery of the next review command) must
accept it. Trials that never land "during the write" do not count as evidence
for that window; if no trial lands there on a platform, V-1 or V-4 is reported
as inconclusive on that platform. Its evidence is statistical ("no rejected or
unrecoverable state in N kills, of which M during the write"), not a proof for
every instant; the deterministic in-process fault-injection tests
(`crates/rt-cli/src/tests_commit_faults.rs`, `tests_commit_recovery.rs`) remain
the per-step evidence.

## 4. LT-6: draft amendment for option A (awaiting approval of wording)

Not applied. The current text stays in force until the user approves this
wording; then it is applied with Old/New records in `traceability.md`, and the
design and threat-model places listed at the end are updated with it. Option A
replaces the session cookie by HTTP Basic credentials, so every criterion that
names the cookie, the session identifier or the exchange is affected.

- **Laboratory_Session (draft).** The period from the first request that
  presents the valid Launch_Secret as HTTP Basic credentials until the session
  is invalidated under Requirement 37 criterion 8 or 17, with its own temporary
  directory and its own CSRF token.
- **Launch_Secret (draft).** A random value of at least 128 bits that
  ruletrace-lab generates at each start and gives to the user only through the
  terminal, and that the browser presents as the password of HTTP Basic
  authentication for one Laboratory_Session (Requirement 37 criteria 5 to 8).
- **37.5 (draft).** THE ruletrace-lab executable SHALL generate a
  Launch_Secret of at least 128 bits from the operating-system source of
  cryptographic randomness at each start, SHALL print it once, together with the
  fixed user name `lab`, to the terminal (standard error or standard output) of
  the process that started ruletrace-lab, and SHALL place it in no URL, query
  string, fragment, command-line argument, referrer, response body, file, or
  log. THE ruletrace-lab executable SHALL accept the Launch_Secret only as the
  password of HTTP Basic authentication (RFC 7617) with the user name `lab`,
  compared in constant time. The user SHALL enter it in the browser's own
  credential prompt by copying it from that terminal.
- **37.6 (draft).** THE ruletrace-lab executable SHALL set no cookie. The
  first request that presents valid credentials starts the Laboratory_Session.
  THE ruletrace-lab executable SHALL hold at most one Laboratory_Session at a
  time; browser tabs that present the same valid credentials belong to that
  Laboratory_Session. The Launch_Secret is valid for that Laboratory_Session
  only.
- **37.7 (draft).** IF a request that passes the Host check of criterion 3 and
  the Origin check of criterion 4 carries no valid HTTP Basic credentials for the
  current Launch_Secret, or carries more than one Authorization header, THEN THE
  ruletrace-lab executable SHALL refuse it with HTTP status 401 and a
  `WWW-Authenticate: Basic` challenge, SHALL start no subprocess, SHALL read no
  workspace file, and SHALL write no file. The checks are made in this order:
  Host, Origin, credentials, CSRF token.
- **37.8 (draft).** WHEN a Laboratory_Session has had no request for 30 minutes
  or the session is ended by the user, THE ruletrace-lab executable SHALL
  invalidate the Launch_Secret, so that every later request that presents it
  receives HTTP status 401, and SHALL accept no credentials until it is
  restarted; a restart generates a new Launch_Secret under criterion 5, and no
  Launch_Secret is used for more than one Laboratory_Session. A test with a
  simulated timer SHALL verify the 30-minute boundary (a request at 29 minutes
  59 seconds succeeds, a request at 30 minutes 0 seconds receives 401).
- **37.9 (draft, last sentence only).** The sentence exempting the Launch_Secret
  exchange from the CSRF token is removed, because there is no exchange; the
  CSRF token is served in pages that are themselves served only to
  authenticated requests.
- **37.19 (draft, first condition only).** "lacks a valid session cookie" becomes
  "lacks valid HTTP Basic credentials for the current Launch_Secret".
- **37.22 (draft, list only).** "session identifier" becomes "Authorization
  header value".
- **37.24 (draft).** THE ruletrace-lab executable SHALL ignore every Cookie
  header for authentication, so that a request that carries a cookie but no
  valid HTTP Basic credentials is refused under criterion 7.

Unchanged but to re-check when applied: 37.23 (the run instructions name how
the user obtains the Launch_Secret; they must name the user name `lab` and the
browser prompt). Places to update with the wording: requirements.md
definitions and criteria above; design.md §11.4 (start page and exchange), §11.5
(session), the §11 overview diagram, the RN rows that mention the cookie, and
§11.18.5; threat model T7, T12d (the secret is used for the whole session
instead of being consumed once) and R-L7 (unconsumed secret without expiry).
