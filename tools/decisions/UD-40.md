# UD-40: decisions on RN-51, RN-52, RN-38 and M3 task closure

Confirmed by the user on 2026-11-18. The user's instructions are summarised faithfully.

## 1. RN-51 accepted, with invariants

- **Proposal import.** The Laboratory discovers and reads batches that `ruletrace-ai` wrote in `<workspace>/proposals`. It does not upload, copy, move or write batches into the Proposal_Store; `ruletrace-ai` stays its writer. Artifact structure, schema, content hash and source metadata are validated before an imported batch is presented. Unsafe paths, path traversal and symlinks are rejected. Imported AI content stays untrusted; a valid hash is neither human approval nor evidence that the interpretation is correct.
- **Evaluate exit 2 with a complete, structurally valid results file** is an executed evaluation. Execution status and provenance status are kept separate. The interface communicates: evaluation executed; results available and validated; provenance not verified. An unverified result or proof is never labelled verified. Diagnostics and errors are preserved. Execution success does not imply that every decision is trustworthy or decided.
- **Requirements 34.9 and 34.10**: the corrected wording is approved. Every displayed proposal or revision identifies its origin (AI-generated; manually authored; authored offline demonstration entry). AI-generated proposals are explicitly untrusted and non-authoritative until human approval. Offline demonstration mode replays hand-authored scripted responses, not recorded provider outputs; the final requirement wording and demo text must not imply otherwise.
- **Workspace layout** approved. `<workspace>/proposals` is written by `ruletrace-ai` and read by the Laboratory. The authoritative ledger and approved Rulebook revisions stay in the durable workspace. Approval mutations happen only through `ruletrace`. Session cleanup never deletes or invalidates authoritative approvals. Temporary imports and derived interface artifacts may be cleaned up.

## 2. RN-52: one implementation, existing owners

The objective is to eliminate duplicated implementation, not only to detect divergence. No generic common crate. Owners: `rt-data` for shared preparation, parsing and data mapping; `rt-explain` for shared result interpretation, explanation and reports. Before task 9.21 moves code: list every duplicated function with its location, inputs, outputs and responsibility; recommend the owner; explain any dependency-edge or Req 24.12 amendment; confirm no cycle and no evaluation-authority bypass. Move only after this check. Keep the drift test until the shared implementation and focused regression tests exist, then replace it by tests of the shared implementation and its consumers. A function that fits neither crate is presented with alternatives; no crate is created by assumption.

The ownership check is `docs/rn-52-ownership-audit.md`.

## 3. RN-38 accepted as a current-language invariant

Under the current rule language an engine Error always co-occurs with an Indeterminate Outcome. This is a tested invariant of Rule_IR version 1, not a guarantee for future language extensions. Error Diagnostics and Indeterminate Outcomes stay separately represented in evaluation and reporting; an Indeterminate Outcome must not conceal an Error Diagnostic. Regression coverage of the current behaviour is added or retained.

Not early because the library exists; not held open for unrelated future tasks. Task 9.6 stays partial and open until its deferred qualification requirements are satisfied.
