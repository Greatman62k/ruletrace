## 3. Blocking findings

**B1. Windows clippy step fails; Windows tests would never run.**
`spikes/lt7-lifeline/tests/crash.rs:32` declares `State::Zombie`, which only the
`#[cfg(unix)]` `state()` (line 41 onwards) constructs. On Windows the variant is
dead code, and `.github/workflows/spike-lt7.yml` runs `cargo clippy ... -- -D warnings`.

    cargo clippy --offline --locked --all-targets --target x86_64-pc-windows-gnu -- -D warnings
    error: variant `Zombie` is never constructed  --> tests/crash.rs:32:5
    exit 101

The same code passes `cargo check` for that target with one warning (exit 0). In
the workflow the failed clippy step skips the later test steps in the windows-2022
job, so the "Windows crash test, two steps back to back" evidence of §11.18.6
would not exist. Fix (not applied; reviewer does not edit): silence the warning
for Windows only (for example `#[cfg_attr(windows, allow(dead_code))]` on the enum)
and re-check with the command above. lt6 is clean for the same target (exit 0).

## 4. Non-blocking findings

- N1. `tests/crash.rs` has no `#![forbid(unsafe_code)]` (the binary has it,
  `src/main.rs`). `grep -rn unsafe spikes --include='*.rs'` finds only a comment. Cosmetic.
- N2. Origin is checked before authentication (`lab.rs` handle, check order Host,
  Origin, Authorization, CSRF). I accept the deviation: a cross-origin POST is a
  403 whether or not credentials are attached, and it never draws a 401 challenge,
  so no second credential prompt. Consequence: an unauthenticated POST without the
  right Origin gets 403, not 401. Item 1 of §11.18.5 lists only credential cases
  without a POST, and those tests pass. §11.18.5 should state the order.
- N3. Item 2 of §11.18.5 says the cross-origin post is refused "by the Origin and
  CSRF checks". Because Origin is checked first, a browser run reaches only the
  Origin refusal. The CSRF refusal is shown only by the server tests
  (`post_with_wrong_or_missing_csrf_is_403`). The design also says the record is
  committed under `docs/security/`; the protocol keeps its table in `spikes/`.
- N4. BROWSER-PROTOCOL.md (assessment below) is good. Remaining ways to a false
  "no Authorization header": (a) credentials not cached in the session. Step 6
  catches this, but it runs after step 4, and any browser restart or profile
  clear between steps 2 and 4 is not caught, since step 6 only proves the cache
  at that later time. (b) `grep -i authorization` returns no output also when the
  log file is empty or the wrong file; the protocol asks for the verbatim log block,
  which covers this, but the pass criterion should say "log contains the GET / block".
  (c) A browser proxy that does not bypass 127.0.0.1 is not mentioned.
  (d) The recorder never sends a 401 challenge, so the protocol tests preemptive
  sending only; that is the right question and the file says so in its last section.
  The recorder is on `127.0.0.1` as the Laboratory is, so the host name matches
  (the host-name pitfall does not apply if the steps are followed).
- N5. Browser protocol and secret generator are Unix only (`util::random_hex`,
  `/dev/urandom`). Windows browsers are not covered; the protocol says so.
  The Laboratory targets Windows too, so LT-6 stays unproven there.
- N6. README says the compare is "in constant time". `ct_eq` has no early exit, but
  nothing measures it and the optimiser is not constrained. Wording only; length is
  documented as not secret.
- N7. Measured Linux times are 1 to 4 ms (kill to absent). The 5 s bound has a
  1000-fold margin; §11.18.6 wants the bound set from measurement per platform.
  Only Linux is measured so far.
- N8. Workflow: `actions/checkout@v5` and `upload-artifact@v6` are tag-pinned as in
  `ci.yml`, not SHA-pinned. Consistent, noted only.

## 5. What held up

- **Boundaries.** Each `Cargo.toml` has an empty `[workspace]` and an empty
  `[dependencies]`; each `Cargo.lock` lists only its own package (read).
  `cargo metadata --offline --no-deps --format-version 1` in the scratch copy that
  includes `spikes/`: 28 workspace members. Main worktree `git diff --stat` empty,
  `git status` shows only the 19 untracked paths. `spikes/*/.gitignore` is `target/`;
  with a created `target/x`, `git status --ignored` shows `!! spikes/lt6-basic-auth/target/`.
  The root `.gitignore` is `/target` only. Repo scanners in `rt-xtask` read
  `crates/<name>` only (scan.rs:358, app_layers.rs:886); a full `rt-xtask` run was not made.
- **LT-6 option A, code.** `lab.rs` checks Host (exactly one header, exact
  `127.0.0.1:port`), Origin for POST, Basic credentials (user and password both
  compared with `ct_eq`, non-short-circuit `&`), CSRF for POST. No cookie is set
  and `Cookie` is ignored. Expected statuses and base64 literals in
  `tests/server.rs` are written from the design, not computed by the server.
- **LT-6 tests.** `cargo test --offline --locked` lt6: 8 unit + 15 integration,
  all pass, exit 0. They assert exact statuses: no Authorization 401 with a
  `Basic realm="` challenge; former cookie only 401 and no Set-Cookie; cookie with
  wrong credentials 401; wrong user, wrong password, one char short, one char long,
  malformed headers all 401; wrong or repeated Host 403; POST with other port,
  other host, `null` and missing Origin 403; five wrong or missing CSRF forms 403;
  all correct 200 `accepted`; POST without credentials but right Origin and CSRF
  401; recorder logs the Authorization line verbatim and logs none when none sent.
- **LT-7 option L, code.** `watch_lifeline` exits 70 on EOF or read error and
  ignores data; the parent keeps `ChildStdin` in `held` until exit; the control
  (`--no-lifeline`) has no watcher. The harness kills with `Child::kill`, waits,
  and polls PIDs to absence with a 5 s limit. The probe uses `kill -0`, then
  `ps -o stat=,args=`; zombie, wrong tag and vanished PID are separate states
  (test `e_`). Linux crash tests: 8 pass, exit 0 (times above).
- **Windows compile.** `cargo check --offline --locked --all-targets --target
  x86_64-pc-windows-gnu`: lt7 exit 0 (one dead-code warning, see B1); lt6 exit 0.
  `tasklist /FO CSV /NH` parsing read: fields split on `","`, PID and image name
  compared, "INFO:" lines ignored since they do not start with `"`.
  `taskkill /PID /F` is only cleanup. `kill -0` through `sh` and BSD-style
  `ps -o stat=,args= -p` read as valid on macOS. None of this was executed.
- **Format and lint on Linux.** `cargo fmt --check` exit 0 and `cargo clippy
  --all-targets -- -D warnings` exit 0 for both spikes.
- **Workflow.** Triggers are `workflow_dispatch` and `pull_request` with paths
  `spikes/**` and its own file. `permissions: contents: read`, no `secrets`, runner
  labels `ubuntu-24.04`, `macos-15`, `windows-2022`. `ci-gate` in `ci.yml` has
  `needs` of its own jobs and counts matrices only inside `ci.yml`, so this workflow
  cannot change it. `defaults.run.shell: bash` makes GitHub run `bash -eo pipefail`,
  and each step also sets `set -o pipefail`, so a failing cargo command in a `| tee`
  pipeline fails the step. `fail-fast: false`. The `ci` workflow also triggers on
  every pull request (no paths in `ci.yml`), so a PR for these spikes runs both.
  Not run: any CI dispatch.
- **READMEs.** LT-7 README lists what is not shown (real children, journaled writes,
  read errors, handle leaks, reaper-less containers, tree kill). I found no overclaim.

### BROWSER-PROTOCOL.md judgment

It would show item 2 of §11.18.5: step 4 has the recorder on another port of the
same host name receive the browser's own requests and logs headers verbatim; step 5
makes the browser post cross-origin and Terminal A logs whether `Authorization` and
which `Origin` arrived; step 6 is a positive control. Steps are numbered, give
commands, expected outputs and where to look, and are readable by a non-expert,
with the gaps in N3 and N4. It records browser name, exact version, OS and version,
date and ports, and the results table and paste area are blank. It tells the
tester not to fill in browsers not run.
