## 4. Non-blocking findings

**F1 (Medium): the second tie-breaker is redundant in this data model.**

- Mutant: `crates/rt-engine/src/rank.rs:428`,
  `tie_breakers.iter()` becomes `tie_breakers.iter().take(1)`. This keeps the
  first tie-breaker and drops the second. All 4 tests passed, so it survived.
- Cause: the score is `wj*judges + wt*technical`, with both weights nonzero in
  every variant. Participants tied on score and on one of `judges` or
  `technical` are therefore also tied on the other. The model's
  `(score, tb1, tb2)` key never has a tie that only `tb2` separates. The same
  holds for the pinned rows and for the property generator.
- Effect: the property detects a wrong tie-breaker order (the reverse-order
  mutant in the status note is killed through `tb1`). It cannot detect an
  engine that ignores a tie-breaker after the first.
- Classification: a genuine coverage gap, not an equivalent mutant of the
  engine. Closing it needs a rule with tie-breaker criteria that are not a
  function of score and tb1, for example `age` as a second tie-breaker. That
  needs a new fixture revision and is a design decision. I changed nothing.

**F2 (Low): the 256-case floor is not enforced.**
`const CASES: u32 = 256` feeds `ProptestConfig::with_cases`. I found no
`check-*` scan or assertion that fails if the constant is lowered. Policy §7
says the floor must not be reduced. Review would catch a reduction, and the
build would not.

**F3 (Low): only one weight varies.**
The variant is `judges` 0.6 to 0.7 and `technical` stays 0.4. A mutant that
hard-codes only the `technical` weight (0.4) would pass. The task asks for
exactly one weight change per variant, so this is within the task. Also, the
weights sum to 1.1 in the weight variant. That is harmless for the test and is
a documented effect of changing one weight only.

**F4 (Low): the ledger appends are not asserted.**
`build_compiled` asserts exit code 0 for each `review approve`, then for
`validate` and `compile`. It does not read back the ledger to check the record
count or that the reviewer is `Test Reviewer`. A wrong or missing record would
instead surface as a `validate` or `compile` failure. Because compile requires
approval, the gap is small.

**F5 (Info): the status note is incomplete about mutants.**
It lists three mutants, all of which I reproduce as killed. It does not mention
the surviving mutants of F1 and of the Target-kind mapping (see section 7).
The note correctly says that bracket qualification, published files and the
Laboratory path are not covered.

## 5. What held up

1. **Approval path (check 1).** `build_compiled` calls only `rt_cli::run`
   through `Session`, for `review approve`, `validate` and `compile`. The ledger
   starts as a copy of the committed `slice-basic` ledger. No ledger record is
   written by hand. Each variant adds exactly one revision to the shared base:
   `rank.standing` r2 (two tie-breakers), then `score.weighted` r2 (weight),
   `elig.basic` r2 (threshold) or `rank.standing` r3 (order).
   `rule_content_hash` only supplies the `--content-hash` confirmation. The
   CLI checks it itself, so a wrong hash would be refused (Req 33.11).
2. **Hand table (check 2).** I recomputed it from the rulebook weights, the
   `>= 16` and `>= 18` thresholds and the pinned rows. It matches the test
   comments and expected values.
   - Base: scores a 7.6, b 7.6, c 7.6, d 7.4, e 5. Eligibility a, b, c, d true
     and e false (no licence). Standings a, b, c (judges 8, 7, 6), d, e.
   - Weight 0.7: a 8.4, b 8.3, c 8.2, d 8.3, e 5.5. b and d tie, and judges
     (d 9, b 7) give a, d, b, c, e.
   - Threshold 18: only d flips to false. c at age 18 stays true. Scores and
     standings are unchanged.
   - Order swapped: technical (c 10, b 8.5, a 7) gives c, b, a, d, e.
3. **Outcomes (check 3).** `outcomes_checked` calls `identical(...)`, which
   compares the application's results bytes and exit code with
   `ruletrace evaluate`, for every variant, both applications and every
   property case. The pinned test asserts `assert_ne` for the changed groups
   and `assert_eq` against the base for unrelated groups, as listed below.
   - Weight: eligibility equal, scores and standings differ.
   - Threshold: eligibility differs, scores and standings equal.
   - Order: eligibility and scores equal, standings differ.
   - Bracket: standings differ for weight and order, equal for threshold.
4. **Reference model (check 4).** It is independent. It uses integer tenths and
   a plain sort by `(score, tb1, tb2)` descending with the participant name as
   the order within a tie group. Position is `1 + participants ahead`. It
   imports no production code. Its arithmetic matches the rulebook: weights
   0.6/0.4 (7/0.4 in the weight variant) and `age >= threshold && licence`.
   `tenths_text` prints the canonical number form (`5`, `7.6`), as the pinned
   tests require. The hand check `the_reference_model_matches_a_hand_derived_tie`
   covers both orders. The model is not an independent calculation of the
   second tie-breaker, as F1 shows.
5. **Property (check 4).** Rows have 1 to 8 participants in shuffled file
   order. Ages come from 14..=22 plus 16, 17 and 18. Judges and technical come
   from 0..=4, so ties are common. Each case runs four Compiled_Rulebooks and
   both applications. The compiled bytes are cached once per process, which is
   fine because they are inputs, not results. The run took 25 s for
   256 cases.
6. **Limitations (check 6).** The note states that bracket qualification
   (no committed qualification rule), published files and the Laboratory path
   are not covered. That is accurate. An application that hard-codes a value
   equal to one variant's value is still caught, because the four variants
   differ pairwise on the observable Outcomes.
