# AI-independence matrix and origin-independence test (task 8.18)

Range f4e0250..9724798 (three local commits). Adds `crates/rt-demo/tests/ai_independence.rs` (Property 41 as an 8-cell matrix), `origin_independence.rs` and block 5e2 of `acceptance.rs` (Req 16.18 against a hand-authored Rulebook over the `ai` document), `demo/stand-in-ai/rulebook/hand-authored.json`, a `core-only` CI loop change, and spec notes. The matrix runs the nine `hand` runbook steps plus four failing commands in every cell and compares each with committed goldens and each cell with the first. The origin test compiles and evaluates the hand-authored Rulebook and compares `compiled.json` and `results.json` with the `ai` goldens. Both halves are real evidence, and the two deviations from the task text are disclosed. The weaknesses are a few coverage and CI-assertion gaps, none of which makes a claimed guarantee false.

Watch for: the 256-case minimum is replaced by an exhaustive matrix without a recorded user decision (confirmed, needs sign-off, not a defect); the `core-only` job never asserts that `ruletrace-ai` is absent from its target directory (confirmed, hardening); the matrix plants configuration only at paths nothing reads, so it cannot catch a realistic default-location lookup (confirmed by mutant).

**Verdict**: APPROVED

## High-level view

The matrix varies three things `ruletrace` could in principle notice: a `ruletrace-ai` file beside it, on `PATH` and in the working directory; an `ai.toml` in the working and home directories plus a `RULETRACE_AI_CONFIG` variable; and a canary in three credential variables. `ruletrace` reads only its arguments (`rt-cli/src/main.rs` has no `env` access), so the cells exercise a black-box guard, and the guard works: a mutant that reacts to a sibling `ruletrace-ai` fails the matrix at the first step of the affected cell. Because the domain is these three booleans, an exhaustive run is a stronger statement than 256 random draws, but it is a change to a stated minimum, so it needs explicit sign-off.

The origin comparison is independent in the way that counts. The expected bytes are the committed `ai` goldens, the three content hashes passed to `review approve` are pinned from the golden ledger and re-verified by `approve` against the file's own computed hash, and a changed threshold is refused with `RT-APR-0203`. The Rule_Content of the hand file must equal the AI output for any comparison to be possible, so the file is a transcription, not an independent derivation. Its independence comes from the pinned hashes and goldens, not from the author.

The CI change adds both test files to the existing core-only/full loop. Equal goldens in a build without AI crates and a build with them prove byte equality, and the `--skip ai_profile_` filter is safe in this workspace. Nothing in CI asserts that the core-only directory lacks a real `ruletrace-ai`, so that half rests on `check-tree` and the exclude list.

### Does the 2x2x2 matrix test what Property 41 states

The design text of Property 41 quantifies over "any combination of presence of `ruletrace-ai`, an AI_Configuration file and the credential variable". That is three booleans, and all eight combinations run, each with nine runbook steps and four failing commands (exit 2 and 3 paths, diagnostics checked by code). Outputs, written file sets and file bytes are compared across cells, and every step is compared with goldens that predate the test. I ran `ai_independence` and `origin_independence` (4 tests, pass), the full `acceptance` test (7 pass), and a core-only simulation with only `ruletrace` in `RT_BIN_DIR` (8 cells equal, inert stand-in used). `cargo fmt --check` and `cargo clippy -D warnings` on `rt-demo` are clean.

The cells really differ. `the_cells_differ_in_what_is_visible_to_ruletrace` asserts per cell that a `ruletrace-ai` file exists beside the binary and is found by walking `PATH`, and that the config file is present or absent. It does not assert the credential variables, which are set unconditionally in `run_command` from the cell flag, so that dimension is trusted by construction. The tool cell places the file beside the binary, on `PATH` (same directory) and in the cwd together, so "beside" and "on PATH" are not separated. Given that `ruletrace` reads neither, this loses nothing today, but a future launcher keyed on one location only would still be caught because all three are present together.

Mutants run against `rt-cli/src/main.rs` (reverted, tree clean):

- Writing `ai` to stdout when `ruletrace-ai` exists beside `current_exe`: killed. Failure: `tool=1 config=0 credential=0 step s01 stdout differs from its golden file`.
- Writing `ai` to stdout when `$HOME/.config/ruletrace/ai.toml` exists: survived. The matrix never plants that path. The mutant reads a location the spec does not define, so this is a coverage statement, not a violated requirement.

The test's "256 cases" deviation: the testing policy forbids reducing the generated case count without a specification decision. Here no generator exists, and the exhaustive run covers every input of the stated domain. The domain in the design text does not include varied command inputs (the inputs are one fixed runbook), so the property is "for the same inputs", as written. I judge the deviation acceptable on the merits and it is disclosed, but it still needs an explicit user decision. The design's Property 41 also covers `prize-check` and `bracket-check`; those applications are not part of this task and no claim is made about them.

The canary check (`leaked`) runs over the reference cell only, which is the cell without credentials. The equality assertions make this transitively sound, but the assertion as written proves nothing by itself.

### Hand-authored comparison

`hand-authored.json` is a Rulebook with origin `manual`, a different name, and the three rules of the `ai` flow. The test pins the three content hashes taken from the `ai` golden ledger and passes them to `review approve`, which recomputes the hash and refuses a mismatch. Then `validate`, `compile` and `evaluate` run and the artifacts are compared with the `ai` goldens (committed before this task), and the first four ledger lines (header and three records) equal the golden's. A mutant that hashes `manual` origin differently was reported as killed (first difference at byte 92); I did not re-run it. Equality is not trivial: compiled bytes embed the document and content hashes, and the rulebook name differs yet the bytes match, so name and origin are excluded from the compiled form as the design intends. `a_changed_rule_is_refused_with_the_original_content_hash` shows the binding is real: threshold 17 with the original hash gives exit 3 and `RT-APR-0203`.

### CI core-only changes

The loop runs the four test targets for the core-only target directory and then the full one, with `RT_BIN_DIR` pointing at each. In the core-only run the `ruletrace-ai` binary does not exist (`rt-ai-tool` is excluded), so the "present" cells use the inert file. The full run uses the real tool. Both compare to the same goldens, so equal pass results mean equal bytes. No AI crate is built for the core-only loop: `rt-demo` has no AI dependency (dev-dependency is `rt-xtask` and `proptest`). The `bin_dir` fallback runs `cargo build -p rt-cli` without `--target-dir`, which writes to `./target` and not `target/core-only`, but `RT_BIN_DIR` is set in the loop and the earlier step built the binaries, so this is the same behavior as the existing hand tests.

The absence of a real `ruletrace-ai` in `target/core-only/debug` is an assumption of the job, not an assertion. If a dev-dependency edge later pulled `rt-ai-tool` into the core-only build, the matrix would silently use the real tool and `check-tree` would be the only guard. A one-line `test ! -e` check would close this.

`--skip ai_profile_` is a substring filter. A workspace-wide grep finds exactly seven functions containing that string, all in `rt-demo/tests/acceptance.rs`, and all intentionally AI-profile tests. The filter would also silently skip any future test whose name merely contains `ai_profile_`. `ai_profile_windows_goldens_differ...` is skipped though it needs no tool, which loses a little core-only coverage and is not a defect.

### Windows and macOS

`binary_path` appends `EXE_SUFFIX`, so the inert file is `ruletrace-ai.exe` on Windows and the snapshot exclusion uses the same name. Snapshot keys are normalised to `/`, and argv uses forward slashes, which Windows accepts. `.gitattributes` has `* -text`, so goldens have no line-ending conversion. `env_clear` followed by `PATH`, `HOME` and `USERPROFILE` leaves `SystemRoot` and `TEMP` unset on Windows; the existing demo harness clears everything including `PATH`, and a plain Rust binary using only file I/O does not need them, so the risk is the same as the hand tests that already run on the three platforms. It remains unverified until the `demo-offline` run. On macOS the temp directory is under a symlinked `/var`, which only matters for paths printed in stderr; the goldens contain none in these steps. On Unix, `fs::write` for the inert file gives mode 0644 (see issue 6). Real `ruletrace-ai` copies keep the executable bit through `fs::copy`.
