# Review of UD-47 (LT-6 option A+), uncommitted, HEAD 2bf4e89

## 1. Verdict

NEEDS_CHANGES. The idea (Basic credentials plus a binding cookie) removes
the T12d scrollback-reader case and keeps the T7 cross-port case out. But
the decision text makes one false security claim (finding B1), section 2
has a gap that a normal restart triggers (B2), and the draft amendment
omits criteria that must change (B3). The behaviour of section 2 is **not
sound to implement as written**. It is sound after B1 to B3 and the
conditions N1 to N3 are applied (see section 4 and the closing statement).

## 3. Blocking findings

**B1. Section 1 table, row 3 (UD-47.md:30) is false for the realistic
case.** A hostile local server on another port that shows a fake Basic
prompt is only phished if the user's browser visits it. That visit sends the
binding cookie to it, because cookies are not scoped by port and
SameSite=Strict does not apply between ports of the same host (same site).
HttpOnly stops page script from reading the cookie. It does not stop the
server from reading the `Cookie` request header. The attacker then holds
the secret (typed by the user) and the cookie, and it can call the
Laboratory itself with both. This is the same cross-port cookie exposure as
T7 (row 1 of the table concedes the server holds the cookie). So post-login
phishing is not mitigated by A+. The cookie only helps when the phished
secret reaches an attacker who has no cookie (a different browser, or
scrollback reading). The text at UD-47.md:32-38 and the planned threat-model
"prompt-phishing row" must state this as a residual that depends on the
user not re-entering the secret after first login. Fix the table row and
the claim in the front matter title/Section 1 ("The secret then works once",
line 24, is also inexact: the secret works on every request, together with
the cookie).

**B2. Section 2 item 2 (UD-47.md:44-47) leaves "valid credentials, no
session, a stale or foreign `rt_lab_session` cookie" undefined.** Item 2
requires "no binding cookie" to start a session. Item 3 applies only while a
session exists. A browser keeps a session cookie across a Laboratory restart
on the same host (and cookies are shared by every port of 127.0.0.1), so the
first login after a restart will usually carry the old cookie. As written
that case is neither started nor refused. The draft 37.6 (line 76-84)
is correct (no cookie condition) and disagrees with section 2. The rule
should be: valid credentials and no session start the session whatever
cookie arrives, and the response overwrites it. Add a test (two successive
Laboratory runs, second login carrying the first run's cookie).

**B3. The draft amendment (UD-47.md:62-112) misses criteria that must
change.**
- 37.19 (requirements.md:1327) says "lacks valid HTTP Basic credentials".
  After A+ an approval request with credentials and no or wrong cookie is
  refused by 37.7, but 37.19 has an explicit test that "omits each of these
  elements in turn". It should list the binding cookie, and the test must
  omit it (expect 403, ledger byte-identical). Answer to the question asked:
  yes, 37.19 should also require the binding cookie.
- 37.23 (requirements.md:1331) lists criterion 7 for a check-removal mutant.
  Name a mutant that removes the cookie check separately, because criterion 7
  now has two independent checks and one mutant would not show both.
- 37.9 issuance sentence (requirements.md:1317): "only in pages served to
  authenticated requests, first with the page that answers the request that
  starts the session". With the draft 37.8 definition ("authenticated" means
  credentials and cookie), the request that starts the session has no cookie
  yet, so the sentence contradicts itself. Define "authenticated request"
  to include the session-starting request, in 37.8 and 37.9. The same
  definition decides whether the starting request sets the 30-minute clock.
- Add glossary entries for the binding cookie and the session identifier;
  they appear in 37.6, 37.7, 37.8, 37.18, 37.22, 37.24 but have no
  definition. The `grep -n "cookie"` of requirements.md finds only 37.6
  (line 1314) and 37.24 (line 1332); both are covered by the draft.

## 4. Non-blocking findings (conditions for implementing)

**N1. Session-start race is not specified.** Two tabs, or the page plus a
parallel request such as `/favicon.ico`, can send valid credentials before
the first response's `Set-Cookie` is stored. Whichever the server serialises
first starts the session. The other gets 403 "bound to another browser",
which is wrong for a legitimate second tab and tells the user to restart,
although the session is intact (a refusal does not end it). Specify that the
start is one atomic compare-and-set under a lock, that the loser gets 403
without effect on the session, and that the message does not claim another
browser. Test it with a deterministic two-thread barrier. An attacker racing
the user needs the secret, so this is a usability and determinism issue, not
an additional exposure.

**N2. Cookie tossing and name collision.** Any server on any port of
127.0.0.1 can set `rt_lab_session` (Path=/ or another path). With the rule
"exactly one equal cookie" (UD-47.md:49) it can force 403 for the user
(denial of service only; no access). Two Laboratories on different ports
overwrite each other's cookie for the same reason. Use a per-port cookie name
(for example `rt_lab_session_<port>`) and state the tossing DoS in the
threat model. Add that the refusal text is not the only diagnostic.

**N3. Cross-origin GET still carries both credentials and cookie.** Basic
credentials and the Strict cookie are attached to requests from a page on
another port (same site). Origin is absent on no-CORS GETs and 37.4
explicitly allows GET without Origin (requirements.md:1312). Today this is
harmless: GET starts no subprocess and writes no file (37.9), and the
response cannot be read (CORP same-origin, no CORS, 37.10). SameSite=Strict
adds nothing across ports and must not be cited as a cross-port control; the
Origin and CSRF checks carry it, as UD-47.md:36-38 says. For defence in
depth, refuse requests whose `Sec-Fetch-Site` is `same-site` or
`cross-site` (allow `same-origin` and `none`) before authentication, with a
mutant test. Any future state-changing or data-returning GET would make this
blocking.

**N4. Cookie comparison.** State that the session identifier is compared in
constant time and that more than one `Cookie` header line is "repeated" too.

**N5. Closed-browser lockout.** After a browser restart the cookie is gone
but the credentials prompt reappears; the user gets 403 and must restart the
Laboratory. This is the intended "works once" behaviour; say so in the run
instructions (37.23 / Requirement 13.7).

**N6. UD-47.md:24 and 28 wording.** Row 1 ("refused: no Basic credentials
reach it") rests on the browser evidence file; cite its path as UD-46 does.

## 5. What held up

- **T7:** a server on another port receives the cookie, never the
  credentials (origin-scoped Basic, per the browser evidence cited). A cookie
  alone is refused because the credential check precedes the cookie check
  (section 2 item 1 and 3), so there is no oracle for cookie validity (a
  cookie-only request always gets 401, never 403).
- **T12d, scrollback reader after first login:** secret without cookie gets
  403 (section 2 item 3, draft 37.7), no side effects.
- **403 without challenge:** RFC 9110 section 15.5.2 requires
  `WWW-Authenticate` only on 401; section 15.5.4 allows 403 without it. The
  split is consistent with HTTP. It also matches 37.7 as amended by UD-46:
  UD-46 covers "no valid credentials or two Authorization headers" with 401,
  and the draft keeps that and adds a distinct state. Omitting the challenge
  is right: a challenge would re-prompt and could invite phishing. The 403
  reveals session existence and binding only to a holder of the valid secret.
- **Session end:** section 2 item 4 matches 37.8 ("no credentials until
  restart"; refused requests do not reset the limit) and 37.17.
- **Preemptive Basic to a subpath:** no extra exposure. The credentials go to
  the same origin only, and every path passes the same ordered checks.
- **Restart cookie reuse:** a new identifier is drawn per session (>= 128
  bits) and the old one is invalidated at session end, so a stale cookie
  never authenticates; the gap is only B2.
- **Front matter** keys and order match UD-46. `amends: none yet (...)` is
  honest: nothing is amended until section 3 is applied. `status: Confirmed`
  applies to the user's choice of A+, not to the wording, and the text says so
  (lines 8, 62-64). LT-6 stays OPEN (lines 120-123). No requirement file or
  other tracked file is modified.

## 9. Closing statement on section 2

Not sound to implement as written. Implement it after: B2 (start on valid
credentials regardless of cookie); N1 (atomic start, defined loser
behaviour); N2 (per-port cookie name, duplicates refused); N4. Record B1 as
a residual: A+ defends T7 and T12d, and does not defend against a hostile
local server that the user's browser visits and that obtains the secret from
the user, because that server also receives the cookie.
