# Provider profiles, configuration v2 and host restriction (UD-37 wave 2)

Commits 1787c2b (profiles), c61a1c8 (configuration v2, host restriction, model guard, capability declarations), 394eb8a (stored-batch depth cap), 0b44965 (index == node count test), c62c7af (Cf filtering) and 37fc9f0 (exact official origin), reviewed at 37fc9f0 in a separate worktree. The credential cannot be routed to a host other than the official one or a loopback address by any endpoint form I tried (about 65, table in the details). Capability declarations can only restate or lower, a v1 file is mapped in memory and nothing is written on load, and the depth cap is exact at 61 containers. The profile facts match the Meta and OpenAI pages I fetched, with one per-model caveat missing.

Watch for: a Cf mutant survives (U+FEFF is untested, *confirmed*), the `max` effort is accepted for every Meta model although the reasoning page lists it for three models only (*possible*), and the endpoint is stored as written, so the future transport must normalize a trailing `/` and an upper-case scheme (*possible*).

**Verdict**: APPROVED

## High-level view

The host restriction is sound. The parser refuses backslashes, whitespace and control characters outright, takes the authority up to the first `/`, `?` or `#`, and compares the lower-cased host for equality with the official host as a bare origin. Userinfo and queries are stopped one stage earlier by the inline-secret check. Loopback is matched by parsed address or the literal `localhost`, so suffix tricks fail.

The model guard is a case-insensitive substring test and the allow flag defaults to false. Capability declarations are checked against the profile with a single rule, and the effective value feeds negotiation. Version 1 files are read as text and mapped in memory, and a real-disk snapshot test covers it.

The depth-cap fix is correct and exactly at the boundary. The Cf table is identical to Unicode 16.0 Cf. The edits to existing tests are forced by the host restriction or by the new schema version and weaken no assertion.

## Endpoint and host restriction

I tried about 65 endpoint forms against a v2 `meta` configuration through `load_config`. Every form that carries userinfo (`https://api.meta.ai@evil.example`, `https://evil.example@api.meta.ai`, `https://api.meta.ai:x@evil.example`, `;@`, a backslash before `@`) gives RT-AI-0003. A query gives RT-AI-0003. Malformed URLs (`https:/\api.meta.ai`, `https:/api.meta.ai`, `https:api.meta.ai`, an empty port, any space, tab or NBSP) give RT-AI-0002. All of these exit before any host decision. The lookalikes that reach the host check all give RT-AI-0013: trailing dot, `api.meta.ai.evil.example`, `evil.example/api.meta.ai`, `%2e`, `%2f` and `%40` forms, full-width and ideographic dots, Kelvin sign, a zero-width space at the end or inside, `xn--api.meta.ai`, port 443 and 8443, a fragment, `//`, `/v1`, an IPv4 literal and a global IPv6 literal. The accepted forms are `https://api.meta.ai`, with a single `/`, and any ASCII case, as the spec requires. `http://api.meta.ai` and `ftp` give RT-AI-0004.

Loopback: `localhost`, `LocalHost`, `127.0.0.1`, `127.9.9.9` and `[::1]:99` are accepted, with a port and a path as Req 35.6 allows. Rejected with RT-AI-0004 or RT-AI-0003: `localhost.evil.example`, `127.0.0.1.evil.example`, `localhost.`, `localhost@evil.example`, `127.0.0.1:80@evil.example`, `[::ffff:127.0.0.1]`, `0.0.0.0`, `127.1`, `0x7f.0.0.1`, `2130706433`, `127.00.0.1`, a zone id and `[::1]evil`. `http://127.0.0.1/..%2f@evil.example:80` is accepted, and it is a loopback host with a path, which is the stub-server case. `http://localhost` relies on the resolver mapping the name to loopback. That is the spec's choice (Req 28.6).

Provider `mock-replay` has no official host and forbids an endpoint at the field stage. An unknown provider id never reaches an `Authorized` value, because the pair check returns RT-AI-0006 before authorization. A v1 kind that is not built in is marked `unmapped_kind`, so v1 cannot name `meta`.

Mutants killed: bare-origin check removed (M2), `localhost` as a prefix (M3), plain http for any host (M8).

## Model guard and capability declarations

`contributor`, `CONTRIBUTOR`, `contrib\u{75}tor` (the same string), and `contributor ` with a trailing space give RT-AI-0012. `allow_provider_training = true` lifts it, and `false`, the string `"true"` and `1` do not (RT-AI-0012 or RT-AI-0002). It is read with `is_some_and`, so absence means false. A model name with a zero-width space inside (`contrib\u{200b}utor`), a Turkish dotted capital I, a Cyrillic `о` or full-width letters is not refused. Those are different identifiers at the provider, which compares exactly, so I do not count them as a bypass. A control character gives RT-AI-0002.

`check_declarations` accepts a value equal to the profile value or yes lowered to no, and refuses everything else, including unknown to no and yes to unknown, as Req 35.4 says. Mutants killed: declarations check disabled (M1), declaration forced to yes (M13), allow flag defaulting to true (M12), `none` accepted as an effort (M5).

## Version 1 mapping and the no-write rule

The loader receives text only. `tests_config_v2_disk` snapshots every file with bytes and mtime before and after two runs of six cases (v1 and v2, mock and hosted, refused and dry run) on a real directory and asserts equality, repeatable output and exact codes. A v2 mock run equals the v1 run byte for byte for the store batch and the log. Mutant M11 (v1 mapped to `meta`) is killed. The v1 behaviour changes are all required by the spec: the openai host is now restricted (35.6), the model is limited to 200 characters with no control character (35.10), and a `contributor` model is refused with no way to allow it in v1, since the v1 field list has no allow flag (35.8, test name "and to version 1").

## Edited existing tests

Every edit falls into one of three groups and I found no weakened assertion. The placeholder host `api.example.org` became `api.openai.com` in about a dozen tests and fixtures because a v1 hosted configuration now maps to `openai`. `schema_version = 2` as the invalid value became 3 because 2 is now valid. The accepted-endpoint list lost `https://api.example.org:8443/v1`, `https://0.0.0.0` and `https://[::]:443/`, which are now refused by design. They were replaced with the official origin and loopback forms, and the refusals are asserted in the new `tests_config_endpoint` and `tests_config_v2`. The hostile 20,000-node chain now expects RT-LIM-0003 with the 61 message instead of RT-AI-0202, which the spec amendment requires and the commit discloses. The `/a@b` case now asserts the new RT-AI-0013 at line 5, column 1 for the official host with a path. The order property test (512 cases, 12 stages) matches the Req 28.17 list: syntax, secret, fields, limits, scheme, host, disabled, pair, guard, capability, consent, credential, and asserts that the environment is read only at the last stage.

## Stored-batch depth cap

The cap is `MAX_CONTAINER_DEPTH - 3 = 61` containers for the lowered rule, counted by an iterative scan that handles strings and escapes, before the recursive decoder runs. My probe built rules from a `not` prefix and an `and` chain and stored them through `store_batch` and `parse_batch` and `check_store`. A rule of 61 containers (3 nots over 28 and-levels) was accepted, stored and re-read. A rule of 60 (the 29-level and-chain, 59 nots) too. A rule of 62 (30 levels), 61 nots and the mixed 30/15 and 31/15 forms were refused with RT-LIM-0003 and nothing was stored, because only an `AcceptedBatch` can be stored. The suite covers depth 500 and 100,000 nodes on a 1 MiB thread stack. Mutant M6 (cap 62) is killed. The probe source was not committed and was deleted with the worktree.

## Cf filtering
