### Q2. LT-6 and LT-7 and their candidate mitigations

**Status.** Both are still clearly OPEN. Evidence: `design.md:3517-3518`, `:3583`, `:3590` ("no Laboratory code starts"), threat model status line and rows T7/T17/R-L2/R-L3/LT-6/LT-7, `tasks.md:1570` and task 13.9, `traceability.md` register entry, UD-39 §B. No text claims either is solved. The cookie wording is honest: it states cookies are not port-isolated and that SameSite and Host checks do not fix it (`design.md:3571`).

**LT-6, HTTP Basic with the RFC 9110 protection space (§11.18.5, option A).**
- Port scoping: sound by specification. RFC 9110 defines the protection space by the canonical root URI (scheme and authority, so including the port) plus the realm ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html); the same wording is quoted in [this Stack Overflow answer](https://stackoverflow.com/questions/71998981/does-http-protocol-facilitate-for-specification-of-uris-associated-with-an-aut)). RFC 6265 §8.5 says the opposite for cookies: they are not isolated by port ([CERT VU#804060 quoting RFC 6265 §8.5](https://kb.cert.org/vuls/id/804060/)). I found no browser-side source that confirms port-keyed caching in Firefox, Chromium and Safari. That is exactly what task 13.9 plans to record, and it must stay a manual finding, not an assumption.
- Cross-origin attachment: the design's statement is right. Browsers attach cached HTTP-auth credentials to requests from other origins to the Lab's origin. A Chromium issue records that credentials are sent preemptively in credentialed third-party contexts ([Chromium 41475900](https://issues.chromium.org/issues/41475900)). SameSite does not apply to Authorization. So Origin, Host and CSRF checks must stay, as the design says.
- **F6 (medium).** The design lists the change to 37.5/37.6 but misses a weakening. Under Basic the Launch_Secret is presented on every request and cannot be "consumed on first use". Threat-model row T12d relies on that consumption (scrollback leakage). Under option A a leaked scrollback line stays valid for the whole session. T12d, R-L7 and 37.5 need an explicit amendment, and the 30-minute idle expiry (37.8) must make the server reject the secret, because the browser keeps sending it (this is the LT-5 "no reuse" rule).
- **F7 (low).** Option B's description ("Web Storage is per origin") is correct, but the fallback is a larger surface (D-17 reversed). Option "A then B" is reasonable, but the decision rule if browsers disagree (for example one browser keys the credential cache by host only) is not stated. Say so in 13.9's observable.

**LT-7, lifeline pipe on standard input (§11.18.6, mechanism L).**
- The mechanism is sound in principle. The OS closes the parent's write end when the process dies, so the child reads EOF. It needs no `unsafe`.
- It depends on cooperation of the children's own code. A child that is hung before the watcher thread starts, or any future non-RuleTrace child, is not covered. A stopped (SIGSTOP) or hung Laboratory is not a crash and orphans nothing by this mechanism. Neither is mentioned.
- Windows handle inheritance: the design's risk is real but imprecisely described. Rust's std wraps spawn in a lock to limit inheritance races ([rust-lang/rust#38227](https://github.com/rust-lang/rust/issues/38227)). The documented leak is a child inheriting the parent's own standard handles ([#54760](https://github.com/rust-lang/rust/issues/54760)). The parent's end of a `Stdio::piped()` stdin pipe is created non-inheritable, so another child should not hold the write end. I did not run this. The design's "start at most one child at a time" is a conservative guard, not a proof. The Windows crash test (13.9) is the evidence. Until it passes, no claim.
- `std::process::exit` from a watcher thread: memory-safe, and the Rust docs say no destructors run on any thread. So any `Drop`-based cleanup (lock files, temp files) does not run. That is equivalent to SIGKILL, which the design says the commit protocol already survives. The evidence is only simulated: `crates/rt-cli/src/tests_commit_faults.rs` drives the real `run` over a `FaultFs`, and there is no test that kills a real process. V-1 is correctly listed as unverified (`design.md:3524`). **F8 (medium):** the sentence "crash safety of an abrupt exit, which the journaled review commit … already require[s]" (§11.18.6 table) states as fact something that is verified only in simulation. Reword, and make a real-process kill test of `ruletrace review approve` mid-commit part of 13.9 or 13.3.
- 5 s bound: not justified in the text. It is a test parameter chosen without a measurement. Kernel pipe closure and `exit` are immediate, so 5 s is generous on Linux. On macOS and Windows CI the polling and PID-reuse behaviour is the real risk. **F9 (low):** state it as a harness timeout, record the measured times in 13.9, and have the harness check process identity (start time) as well as PID.
- **F10 (low).** `--lifeline-stdin` on `ruletrace` and `ruletrace-ai` is a CLI change. Req 17 (the grammar that 37.14 now cites), the exit-70 meaning and the "no existing output changes" rule need a matching requirement note. Today the amendment lives only in task 13.3. The design also rejects Job Objects as needing `unsafe`, without weighing a reviewed dependency (permitted by "documented exception"). Not blocking.
