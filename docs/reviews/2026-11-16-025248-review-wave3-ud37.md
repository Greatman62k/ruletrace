# rt-ai-responses: Responses request, envelope mapping and HTTPS transport (commits ab62eae, 5bd264f, 5c7f555)

The three commits add the `rt-ai-responses` crate (request body builder, envelope mapper, status mapper, `ureq` + `rustls` transport with the embedded `webpki-roots` store, a loopback stub suite), rename the planned `rt-ai-openai` edges in `allowed-edges.v1`, `deny.toml`, the `check-graph` list and the core-only job, and add the dependency closure to `tools/dependencies.v1`. The crate is not yet linked from `rt-ai-tool` or `rt-tests-ai`, so nothing here is reachable from `ruletrace-ai` yet.
I built and tested in a separate worktree at 5c7f555. The suite is strong: 15 of 16 mutants of my own were killed (one only by a source scan), and the survivor is equivalent, the stub suite passed 5 of 5 runs, `cargo deny check`, `check-tree`, `check-graph`, fmt and clippy are clean, and the core-only build contains no `ring`, `ureq`, `rustls` or AI artifact. Transport security held up under every probe I could construct.
Watch for: `tools/dependencies.v1` now makes false statements about what ships in `ruletrace-ai` (confirmed). The completion-order defect the author listed is real: with this adapter, a refusal or truncation reports RT-AI-0201 instead of RT-AI-0205 (confirmed by running `parse_response`). Invalid-header credentials fail with no diagnosable cause (confirmed). TLS verification has no automated test, only a source scan (confirmed; I checked it by hand against a self-signed server).

**Verdict**: NEEDS_CHANGES

## High-level view

The request body matches Meta's documented Responses shape (`text.format` flat `json_schema` with `name`, `schema`, `strict`; `store`, `max_output_tokens`, `reasoning.effort` only when configured, no `tools`, no `instructions`). The bytes are pinned by a hand-written expectation. The envelope mapper fails closed on every shape it does not recognise, and maps every status other than `completed` to Incomplete, as Req 35.13 says.

Error handling decides from the status line only. Error bodies are never read, so no provider text can reach a diagnostic from this crate. The status table, the 3xx/4xx/5xx boundaries and Retry-After parsing match Req 35.14 and 29.3. Only 2xx metadata (`model`, `id`) carries provider text, and the tool's Req 35.15 filter must handle it when the crates are linked.

The transport keeps redirects, proxy and environment out, cannot be given a way to skip verification, and bounds the whole attempt with one global timer. A slow-drip body, a slow-drip header and a stalled server each ended at the timeout (1.0 s for a 1.0 s budget). The endpoint parser is conservative and builds the request URL from the same authority text it validated, so the credential cannot go to a different host from the one configured.

The open points are about integration, not about this crate's transport: the tool's parse order, credential validation before use, a missing TLS behaviour test, a duplicated credential type, and prompt adequacy for the live run.

## Request body against the Meta documentation

I fetched `https://dev.meta.ai/docs/protocols/responses` and `https://dev.meta.ai/docs/structured-output` on 2026-11-16. They document `POST /v1/responses` with `model` and `input` (a string or an item array), `store`, `include`, `instructions`, `previous_response_id`, a `max_output_tokens` minimum of 16 that includes reasoning tokens, and `text.format` as the Responses parameter for structured output (`response_format` is the Chat Completions one). The structured-output page states that `strict` defaults to false, that output is schema-constrained either way, and that strict mode requires closed objects. The pages show the Chat Completions example (`response_format.json_schema`); the flat `text.format = {type, name, schema, strict}` shape is the OpenAI Responses form that Meta says it follows. The body in `body.rs` uses that form, so the shape is consistent with both documents. I could not confirm the flat form against a Meta Responses example, since the fetched pages carry none; the live run (10.8) is the first real check. `reasoning.effort` is documented on the Responses API as the control, matching `{"reasoning":{"effort":...}}`.

The member order (`model`, `input`, `text`, `store`, `max_output_tokens`, `reasoning`) is the author's choice and is pinned by two tests. JSON member order is not significant to the provider, so the pin is a determinism choice, not a protocol requirement.

## Envelope mapping and fail-closed behaviour

I ran 23 envelopes through the real adapter. `failed`, `in_progress`, `cancelled` and `queued` all map to Incomplete even when a usable message sits in `output`, which is what Req 35.13 requires ("any status other than completed"). A numeric `status`, a missing `status`, an array root, a BOM, a duplicate `status` key and a nesting depth of 40 are Malformed. `function_call` and `web_search_call` items are Malformed even when a valid message follows, so a tool call cannot be skipped over. Annotations on an `output_text` are ignored and do not change the text. Two refusals, or a refusal beside text, are Malformed. Usage counts that are negative, fractional or above `u64` are dropped, never derived.

One consequence of the Req 35.13 wording: a `failed` response carrying a provider `server_error` becomes "incomplete" (exit 6, not retried) and never "unavailable" (retried). That follows the specification, but it means a transient provider failure that arrives as a 200 with `status: "failed"` is not retried. I record it as a specification observation, not a defect.

Issue 6 comes from the same probe. A message whose own `status` is `incomplete` inside a `completed` response is returned as Complete with cut-off text (`{"a":`), which the tool then rejects as RT-AI-0201 rather than RT-AI-0205. The documentation says output items carry a status that moves from `in_progress` to `completed`, so the field exists. Whether Meta sets it to `incomplete` on truncation is unverified.

## Completion order and the empty payload (author's open item)

`parse_response` in `crates/rt-ai-tool/src/response.rs` tests size, then UTF-8, then JSON parse, and only then `completion != Complete`. The adapter returns an empty payload for Refused, Incomplete and Malformed, so I called `parse_response(Refused | Incomplete | Complete, b"")`: all three return RT-AI-0201. The `refusal_and_incomplete_are_0205` tests use a parseable payload, so they pass and hide the problem. The first live failure most likely to happen is a reasoning model that spends all 8192 tokens, which would be reported as "malformed" and send the operator looking for a protocol bug. Moving the completion check before the parse fixes it and keeps the documented order for the size check. The alternative of a typed `Malformed` failure in the adapter contract is larger and not needed.

The malformed-envelope route (empty payload plus `detail`) is workable for the same reason: an empty payload is not JSON, so the tool reports RT-AI-0201. Its weakness is that the reason string lives only in `AttemptReport.detail`; confirm the tool prints it when it links the crates.

## Error mapping, Retry-After and the "no provider text" claim

The status table in `status.rs` agrees with Req 35.14: 401 and 403 are AuthFailed, 429 is RateLimited, every 5xx including 504 is Unavailable, and 3xx, 400, 402 and any other status are Other. Real responses confirm the boundaries: 300, 304, 399, 418, 451, 499, 600 and 999 are Other with the status; 500, 501 and 599 are Unavailable; 100 and 199 are Other without a status; 204 is a 2xx with an empty body and ends as RT-AI-0201 through the empty payload.

Retry-After through the wire: `0` gives `Some(0)`, which the retry decision treats as the scheduled wait (Req 29.3). `007` gives 7. Nine digits are accepted, ten are absent. `+5`, `-5`, `5.0`, an empty value, `5, 6`, `1e3` and an Arabic-Indic digit are absent. Two separate headers are absent, which Req 29.3 does not state, and the code comment records the choice. Surrounding spaces and tabs are trimmed by the HTTP parser before the value reaches the crate, so ` 5` is 5; that is OWS, not a different syntax, and the unit table row for ` 5` (absent) tests a path the wire never produces. A 503 with `Retry-After: 60` leaves the wait at 2 s, checked through `next_step`.

`post` never reads the body of a non-2xx response, and `classify` drops the `ureq::Error`, so no provider text and no URL can reach a diagnostic. `detail` strings are static. The 2xx fields `model` and `id` are provider text, forwarded unfiltered and unbounded up to the response limit; Req 35.15's 256-scalar and control-character filter lives in the tool and must be applied when the crates are linked.

## Transport security

Every setting I could find is set safely: `max_redirects(0)`, `proxy(None)`, `http_status_as_error(false)`, a fresh agent per attempt, `https_only(!clear_text)`, no gzip or cookie feature, and the default `rustls` configuration with `webpki-roots`. The source has no verifier override, and `ureq` with `default-features = false` offers none through its `Config`. I ran the real transport against `openssl s_server` with a self-signed certificate for `127.0.0.1` and got `TlsFailed`, so verification is on. I did not make a TLS connection to a public host, because that would send a request to a third party.

Redirects: 301, 302, 307 and 308 to a second stub produce `Other { http_status: Some(code) }`, one connection to the original and none to the target. With `max_redirects(5)` the redirect test fails, so the behaviour is covered and not only the text scan. Setting `max_redirects_will_error(true)` does not fail anything, because with zero redirects allowed the flag has no effect (equivalent mutant).

Endpoint: the scheme is lower-cased, `@`, `?`, `#`, control characters, spaces and backslashes are refused, a port must be 1 to 5 digits, and the URL is built from the validated authority text, so no parser disagreement can redirect the credential. `localhost.evil.example`, `127.0.0.1.evil.example`, `127.1`, `0x7f.0.0.1`, `::ffff:127.0.0.1` and `0.0.0.0` are all refused for `http`. For `meta` and `openai` the host check is the tool's (Req 35.6), not this crate's, so this crate would send to any `https` host it is handed. That is the intended layering, and the reason issue 7 matters at link time.

Header injection: a credential containing `\r\nX-Evil: 1` never reached the stub (zero requests), and nothing in the head was injected. The failure surfaces as `Other { http_status: None }` with no detail (issue 3). A trailing `\n`, a DEL, a tab-free non-ASCII value and similar all take that path; a leading space and an inner tab are sent as written. `Credential` prints `Credential([REDACTED])`, has no `Display`, and the adapter's `Debug` and the report's `Debug` contain no canary. The authorization string is a plain `String` that is not wiped; acceptable here.

Environment: `std::env::var_os` appears in `rt-ai-responses/src/credential.rs` and, from before, in `rt-ai-tool/src/credential.rs`. Nothing in the adapter, mock or core reads the environment. The new crate never calls its own reader (issue 5).

## Response limit and slow servers

The adapter reads `limit + 1` bytes through `take`, so an exact-limit body is parsed and a body one byte over returns `limit + 1` bytes, which `response_limit_boundary_is_exact` and `oversize_body_is_read_only_up_to_limit_plus_one` pin (the `limit` mutant fails both).

`timeout_global` covers the whole call, body included. A server sending one body byte every 100 ms against a 1.0 s budget returned Timeout at 1.007 s. A server sending the header one byte every 100 ms did the same, and a server that accepted and went silent ended at 1.03 s. Per-read timeouts therefore cannot be stretched into a longer attempt. The caller must still pass `min(attempt, remaining deadline)` as the timeout; that is the tool's loop, not this crate's.

## Tests: independence, flakiness and mutants

The body tests compare against a hand-written byte string, the status and Retry-After tables are written from the requirement text, and the stub suite asserts the exact request line, headers and body members. One assertion is circular: `request_bytes_are_exactly_as_specified` builds the expected `input` from `canonical_bytes()` and `INPUT_PREAMBLE`; the byte-exact unit test covers the same text independently, so no behaviour goes unchecked.

Five consecutive runs of `stub_http` each passed 16 of 16 in 3.1 to 3.2 s. The tests rely on time bounds of 2 s against a 0.4 s timeout and on a 0.3 s lower bound, which is generous on Linux. The plaintext-server TLS test (`https_to_a_plain_text_server_is_a_tls_failure`) has the stub write and then close with the ClientHello unread, which sends a reset on close. On Windows an arriving reset can discard unread data, which would turn `TlsFailed` into `Unavailable` (possible; unverifiable locally).

## Dependencies, licences, CI

`cargo deny check` passes (advisories, bans, licences, sources); advisory data freshness was not checked, and it warns that `Unicode-3.0` is no longer encountered. `CDLA-Permissive-2.0` is the Community Data License Agreement Permissive 2.0, an SPDX-listed licence written for data sets. `webpki-roots` 1.0.12 carries the Mozilla CA bundle as data under it, so the allowance is the right one and is listed narrowly with a comment. Its terms ask for the licence text to travel with the data when the data is shared; the binary is not distributed today (`publish = false`).

`ring` 0.17.14 is `Apache-2.0 AND ISC`, both allowed. Its build script ships pregenerated objects for MSVC, so windows-2022 needs only the C toolchain that runners have; macos-15 has Xcode's compiler. I could not run a Windows build here.

The `rt-cli` tree has no `ureq`, `rustls`, `ring` or `rt-ai-` entry, `check-tree` and `check-graph` report ok for 26 crates, and the core-only build (all five AI crates excluded) produced `ruletrace` with no `ring`, `ureq`, `rustls`, `webpki` or `rt_ai_` artifact. `rt-xtask` (66 tests) and `rt-ai-tool` (634 tests) pass. `allowed-edges.v1` lists `rt-hash` as an allowed dependency of `rt-ai-responses` although `Cargo.toml` does not use it; harmless over-permission.

On honesty (issue 1): of the 29 new `dep` lines, the `ring`, `rustls`, `webpki-roots`, `ureq` entries and their purposes are accurate and name real alternatives. The edited `getrandom` line changed only `used-by`. Its purpose text and the `libc`, `itoa` and `cfg-if` lines keep "dev-dependency closure only" or "dev-only oracle closure", which the dependency closure of `rt-ai-responses` contradicts. ## Windows reading

`.gitattributes` is `* -text`, so no line-ending conversion changes the pinned preamble, the HTTP stub bytes or the `include_str!` scans. The preamble's string continuation tolerates CRLF in any case. The stub clears the non-blocking flag on accepted sockets, which avoids the platform differences in inherited flags. Timeouts surface as `TimedOut` on Windows and `WouldBlock` on Unix, and both map to Timeout. `ConnectionReset` and `ConnectionAborted` fall through to Unavailable, which Req 29.2 wants for a reset before the body is complete. A refused connection on Windows can take about two seconds; the 5 s test budget covers it. The proxy test sets both cases of each variable, which matches Windows' case-insensitive environment. Tests use `127.0.0.1` only, so an IPv6-first resolution of `localhost` is untested. The one real risk is the reset race in the plaintext-TLS test above.

## Prompt text and the preamble

`INPUT_PREAMBLE` is a compile-time constant and nothing else is added to `input` except the canonical request bytes that already passed the credential scan. It holds no user, host, path or environment data, so it is neither a privacy nor an injection channel. It asks the model to treat request text as data; that sentence is advice to the model and does not replace the local strict parser. The canonical request does carry the configured model name, the limit values and the reasoning effort, all non-secret configuration.

Whether the text is enough for the model to fill the flat schema is not established. The schema has no `description` members (`grep -c description proposal_schema.rs` is 0), the preamble never says what a proposal is, and the quote, span and node-index rules the local parser enforces (child index greater than parent, every node referenced once, quotes verbatim) are not stated to the model. Constrained decoding guarantees structure, not those semantic rules, so a first live run may produce batches that the local parser rejects as RT-AI-0202. The design does not mention instructions at all, and Req 35.12 ("no other field") rules out the `instructions` member, so any task text must go into `input` and change the pin test. Because the Request_Identifier covers only the canonical request, a later change to the preamble, schema or `max_output_tokens` leaves the identifier unchanged and a stored batch still short-circuits the call (Req 29.10).
