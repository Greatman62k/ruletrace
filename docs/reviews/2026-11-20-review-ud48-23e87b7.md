## 3. Blocking findings

**B1. Residuals 2 and 3 (UD-48.md:56-62) understate the exposure, and the
section 4 control (UD-48.md:121-124) inherits the understatement.**

- Residual 3 says the cookie leaks through "the user's visit to a hostile
  server at `/s/<token>/`". The user does not need to navigate to that path.
  `SameSite=Strict` does not separate ports (same site means same host and
  scheme). Any page the user loads from any port of `127.0.0.1`, including the
  hostile server's own `/`, can issue a request to
  `http://127.0.0.1:<hostile>/s/<token>/x` (image, fetch, form), and the
  browser sends the path-matching cookie. One page load is enough. "All three
  parts needed" stays true (token, that page load, secret), but the middle part
  needs no user decision. Only secrecy of the token, and of the secret,
  protects. Say so, and describe the section 4 item 2 control the same way
  (the recorder's own page requests `/s/<token>/`).
- Residual 2 gives the precondition but not the result. An attacker who obtains
  the secret before the user's first login can send `GET /` itself, receive the
  303 and the cookie, and hold the whole session, including the CSRF token and
  approval pages. The user then sees 403 and may take it for a glitch. The 403
  text (UD-48.md:90-93, draft 37.7) does not say that a session started
  elsewhere may be someone else's. State the consequence (full Laboratory
  authority, including approval) and add to the fixed 403 message: if you did
  not start this session, stop the Laboratory and restart it. Residual 1 has the
  same consequence and should point to it.
- Section 1 (UD-48.md:23-24) says the token is kept "from everyone but the
  user's browser". The token is also in browser history and sync, the screen
  and the window title. Residuals 3 and 5 cover part of this. Reword to "kept
  from every server".

## 4. Non-blocking findings

Conditions for the prototype (C) and for the wording (W).

**C1. The `Sec-Fetch-Site` rule is silent on an absent or unknown value**
(UD-48.md:68-70, 53-55). Specify: absent or `none` or `same-origin` is not
refused on that ground; only `same-site` and `cross-site` are. In a browser
without the header (old Safari, Firefox before 90) the row 4 sentence "refused"
is false; the unguessable path is the only control there. Row 4 should say so.
Fetch-metadata headers are sent to `127.0.0.1` because it is a potentially
trustworthy origin; I did not verify this in a browser.

**C2. Behaviour with valid credentials, no session, and a request other than
`GET /`** (for example `/favicon.ico` before the start) is unspecified in
section 3 item 4 ("With a Laboratory_Session"). Draft 37.7 covers it (403, as
"neither authenticated nor starting"). Make section 3 say the same, and say that
only a `GET` of exactly `/` (no query, not `HEAD`) starts a session.

**C3. Session starts on a speculative request.** A prerender or prefetch
`GET /` (header `Sec-Purpose` or `Purpose`) with cached credentials could win
the start, and its cookie handling differs by browser. Add: a request with such
a header never starts the session (403), with a test. The race rule itself is
right: only a top-level `GET /` can lose it. Favicon, preload and other
subresources are not `GET /`; they get 403 for being outside the path, which
does not affect the page. A real loss needs two top-level `GET /` requests.

**C4. Lost start response.** If the 303 never reaches the browser (connection
reset after the compare-and-set), the browser may retry `GET /` and get 403, and
the session is unusable. The same happens when the browser rejects the cookie
(cookies disabled, privacy settings). Both need a Laboratory restart. Add to
residual 6 and to the 403 text. Tab address wording: "use the address in the
tab where you logged in".

**C5. Path matching and charset.** Define "under the Session_Path" as a
byte-exact raw-prefix test of `/s/<token>/` before any percent-decoding or
dot-segment handling; refuse `..`, `%2e`, `%2f` and `//` tricks (400) with tests;
fix the token and identifier alphabet (for example lowercase hex or base64url
without padding, no `;`, `,`, space, `%`). RFC 6265 path-match sends a cookie
with `Path=/s/<token>/` only to a request path that begins with that string
including the final slash, so `/s/<token>` (no slash) gets no cookie and, being
outside the path, gets 403. This holds on any port because cookies are not
port-scoped (RFC 6265 section 8.5). It is the intended behaviour; test it.

**C6. Constant-time compare** is required for the cookie (item 4) but not for the
token in the path. Require it for the token, and require that every cookie
value is compared (no early exit on the first match). The path check runs only
after credentials, so a timing oracle needs the secret, but the cost is small.

**C7. Logs.** Item 7 redacts the logged path. Also name error and diagnostic
text, 400 and 404 bodies, and terminal output: none may echo a request target
containing the token. Test with the canary token across all outputs.

**W1. Draft 37.19** (UD-48.md:177-178) changes the first condition to "is not
an authenticated request" but leaves the sentence "a test that omits each of
these elements in turn". The test must omit credentials, Session_Path and
binding cookie separately (ledger byte-identical each time). This was part of
B3 of the UD-47 review; it is only half applied. Rename the elements in the
draft.

**W2. Requirement 36 criterion 23** (requirements.md:1299, run instructions
"the loopback address and port that the user opens") is not in "Places to
update" (UD-48.md:196-199). The instructions must name `http://127.0.0.1:<port>/`
for the first open, the session-address rule for new tabs, and the restart rule.
Draft 37.5 adds the address to the terminal output but not to the instructions.

**W3. Draft 37.6** (UD-48.md:151-159) replaces the whole criterion and drops the
sentence "The Launch_Secret is valid for that Laboratory_Session only". The
definition and 37.8 keep the substance; restore it or state that it moved.
Draft 37.6 also needs "exactly `GET /`" (C2) and "no `Sec-Purpose`" (C3).

**W4. Section 5 4.** Draft 37.4 refuses `same-site` and `cross-site` for any
method, so a cross-site preflight gets 403 where 37.10 says 405. At HEAD the
Origin check already refuses a preflight first, so this is not new. State the
order in 37.10's test.

**W5. Row 1 wording** "never sent to it" (UD-48.md:35): evidence covers Firefox
153.5.1esr and Google Chrome 158.0.8127.36 on Linux only. Write "not sent
(evidence on two browsers)".

**W6. Front matter.** UD-47 stays `status: Confirmed` after the superseded note.
`check-decisions` accepts it, and `UD-33.md` shows no other status is in use,
so I do not require a change; consider recording the supersession in the
`title` or `amends`.

## 5. What held up

Each item says how it was checked (reading, not running a browser).

1. **Row 1 (other-port server, T7).** True for credentials by the browser
   evidence file (no Authorization header in either browser). True for the
   cookie: it is sent to a request path that path-matches, on any port, so a
   server learns it only by being requested at `/s/<token>/...`.
2. **Row 2 (terminal reader).** True: valid secret, no cookie, no token. 403 with
   no token in the body (item 4; draft 37.7).
3. **Row 3 (phisher after login).** True for the same reason. It does not
   cover phishing before the first login (B1, residual 2).
4. **Token leak channels (question 1a).** None found. `Referer`: the Laboratory
   sends `Referrer-Policy: no-referrer` (Req 37.10) and has no outbound link
   (37.11, 37.12). The 303 `Location` is visible only to the browser; a
   cross-origin window handle or `fetch(redirect: manual)` cannot read it. The
   attacker-triggered redirect to `/` gets 403 (cross-site, where the header is
   sent) or no cached credentials. `window.name` is never set by the Laboratory
   and is cleared on cross-site navigation in current browsers. History and
   `document.referrer` give nothing across origins. A 403 or 401 page holds no
   token, so "open in new tab" of it leaks nothing. Timing: see C6. Prefetch:
   see C3. Browser history, sync and the screen: residuals 3 and 5, and B1.
5. **Cookie path match (1b).** As C5: not sent for `/s/<token>`, sent for
   everything beneath `/s/<token>/`, on any port and scheme (no `Secure`).
6. **Legitimate navigations and `Sec-Fetch-Site` (1c).** A typed URL, a bookmark
   and a terminal link give `none`; in-page requests give `same-origin`. Both are
   allowed. A redirect inside the Laboratory stays one origin, so it cannot become
   `same-site`. A link from a page on another local port is refused as
   `same-site`; add this to residual 6. I did not confirm browser behaviour for
   the 303 hop.
7. **Residual 3 correct as to "all three needed" (1e).** Token only gives no
   cookie (403). Token and cookie without the secret gives 401. Secret and token
   without the cookie gives 403. Only the three together authenticate. The
   wording defect is in B1.
8. **UD-47 review findings (question 2).**
   - B1: addressed by the design (path-scoped cookie). Residual wording: B1 above.
   - B2: addressed (item 3: start on valid credentials whatever the cookies).
   - B3: partly addressed. Authenticated-request definition, 37.9, 37.22, 37.23
     (separate mutants), the glossary entries and 37.18 are drafted. 37.19 is
     half done (W1).
   - N1: addressed (atomic compare-and-set; loser 403; test in 37.25).
   - N2: addressed (per-port name, unmatched values ignored, test with a
     `Path=/` cookie; cookie bombing stated as residual 4).
   - N3: addressed (`Sec-Fetch-Site`), with C1.
   - N4: addressed (constant time, any number of Cookie lines), with C6.
   - N5: addressed as residual 6; not added to the run instructions (W2).
   - N6: addressed (evidence file cited, UD-48.md:19-20).
9. **401 versus 403 (question 3).** Consistent with RFC 9110: 401 always carries
   `WWW-Authenticate`; 403 for valid credentials without authorization carries
   none. After session end every request is 401, which matches 37.8. A refused
   request does not reset the clock (item 6 and 37.8).
10. **Front matter and gates (question 5).** UD-48 has the same keys as UD-46 and
    UD-47 in the same order. `amends: none yet` is honest: no requirement,
    design or threat-model file changed (`git status`: only the two paths).
    UD-47's note is an insertion only; `git diff` shows 4 added lines and none
    removed, and the earlier paused note is intact. LT-6 reads OPEN in
    `laboratory-threat-model.md:351` and UD-48 section 6 keeps it OPEN.
11. **Draft consistency (question 4).** Compared with criteria 3-10, 17-19,
    22-25 and the definitions at HEAD. The grep for cookie, session identifier,
    Launch_Secret, start page and Laboratory_Session found these places outside
    Requirement 37: lines 187-188 (covered), 1285 (no change needed), 1299
    (gap W2). Within 37, criteria 5-9, 18, 19, 22-25 are covered; 37.17 needs no
    change. The remaining "start page" mentions are in the design (3356) and the
    threat model T12d, both in "Places to update" or already noted by UD-46.
12. **Implementable and testable (question 3).** Items 1-7 can each be tested
    over HTTP with a mutant (credential, path, cookie, `Sec-Fetch-Site`, CSRF,
    token in a refusal). Randomness and constant-time compare are checkable by a
    source scan plus a mutant, as for existing criteria.
