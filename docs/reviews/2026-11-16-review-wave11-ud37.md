<summary>Issues (5)</summary>

1. **Live runner runs `argv[0]` as a path (non-blocking, likely)** — `run_live_step` passes the step to `spawn`, which joins `argv[0]` onto `bin_dir`. An absolute `argv[0]` (or `C:\...` on Windows) replaces `bin_dir`, so any file named `ruletrace-ai` would start with the credential variable. Only a hand-built `Step` reaches this; `parse_runbook` rejects such spellings. Make `spawn` use the logical name only.
2. **Base-prefix case folding untested (non-blocking, confirmed gap)** — replacing `eq_ignore_ascii_case` with `eq` in `strip_prefix_folded` survives every test on Linux, because the base and the target come from the same canonicalised strings. The name comparison for `golden` and `provider` is killed. Add a unit test of `strip_prefix_folded` with differing-case bases, or record it as a macOS/Windows-only expectation.
3. **15 s bound is blunt (non-blocking, confirmed)** — the 429 test now detects a sleep of 15 s or more out of 30. A mutant that slept 10 s would pass; the old 2 s bound against a 3 s wait caught shorter sleeps. The added `rig.waits.now == 30 s` assertion covers the simulated clock. No action needed unless a partial-sleep mutant matters.
4. **Misleading test name (nit, confirmed)** — `other_file_names_are_not_ruletrace_ai` expects `Class::Live` for `"ruletrace-ai/"`. Move that case into the positive test.
5. **8.3 short names on Windows (non-blocking, possible)** — a hand-built `argv[0]` such as `RULETR~1` would not match the stem check and would be offline. I did not run Windows. Same fix as issue 1.

### Guard fixes (a) to (j)

`names_ruletrace_ai` splits on `/` and `\`, trims trailing separators, removes a case-insensitive `.exe` and compares the stem case-insensitively. It is used by both `classify` and `authorize_live`, so the offline runner and the live runner agree. `resolve` now returns an error when a component exists (`symlink_metadata` succeeds) but `canonicalize` fails, so dangling and looping links are refused with `UnresolvablePath`. A component that does not exist is still allowed. `may_transmit` requires the id to be listed and every entry to be permitted. The placeholder check compares the literal after reading `provider.model`, then `model`, and runs before the store check and before spawn. The by-default paths are unchanged: any unreadable, unknown or unparsed input is live.

My 8 cases ran against both runners with a fake `ruletrace-ai` that writes a marker and connects to a loopback listener, using the committed test fixture. All passed, and the marker never appeared for a refused step.

1. `C:\x\RuleTrace-AI.EXE`, the same with a trailing backslash, and `x\..\ruletrace-ai`: live, refused by `run_step` with `LiveStepInOfflineRunner`.

3. `models`, `Propose` and `propose ` as the command, and `models --config ai/live.toml`: live, refused by `run_step`.
4. Seven configurations that add a `provider` endpoint or protocol by inline table, dotted key, quoted key, quoted table key, nested table, and a spaced header: all live.
5. Duplicate manifest ids in three orders, with an unrelated entry between them and across two consents: every one refused with the permission error.

The live runner does not check the command word. A permitted document with command `models` or `Propose` reaches the fake. The tool's own parser rejects those, so the guard stays an authorisation check, not a command validator. This matches the earlier design and is not a finding.

### Hand-built `argv[0]` reaches `spawn`

`binary_path(bin_dir, logical)` is `bin_dir.join(format!("{logical}{EXE_SUFFIX}"))`, and `Path::join` with an absolute second argument discards the first. `authorize_live` accepts `/other/dir/ruletrace-ai` as the tool by name and `spawn` then runs that path with the credential variable. The committed `a_path_spelling_of_ruletrace_ai_is_refused_before_the_process_starts` covers the offline runner only. The condition is a caller building a `Step` by hand, which the runbook parser forbids, and the live runner is the explicit opt-in. I read the code and did not run an absolute path through `run_live_step`; my Windows-style string on Linux was a relative join and ended in "cannot run".

### Rewritten tests (h) and (f)

429 test. Old assertions: exit 0, first warning `RT-AI-0103`, 2 connections, waits equal `[Retry-After]`, elapsed below 2 s, 2 log lines, batch exists. New: the same, with `Retry-After` 3 changed to 30 and the wait expectation changed to `[30 s]`, the bound raised to 15 s, and a new assertion that the simulated clock reads 30 s. The wait is the longer of the header and the 2 s schedule in both versions (30 and 3 both exceed 2). Req 29.3 treatment of `Retry-After` in seconds is therefore preserved and exercised on a larger value. A mutant whose test clock really sleeps the wait failed with "the test slept" after 30.7 s. Neither version distinguishes "longer of" from "header only", because both header values exceed the schedule; this predates the change.

Inline-secret test. `!refused.is_empty()` became `codes == ["RT-AI-0003"]`, which equals `AI_CONFIG_INLINE_SECRET` in the catalogue. Stricter than before.

Stalled-body test. 401 and 403 became eight statuses (400, 401, 402, 403, 429, 500, 503, 504), each asserting the exact failure variant, one connection and `elapsed < 500 ms`, with the stall at 1.5 s and the cases in parallel threads. Five runs of the test passed in 1.51 s each, and three more under 8 busy loops on 4 cores passed. The margin is 1 s between the bound and a mutant's observed 1.505 s. Mutants that drain the body for 504 and for 400 both failed with "took 1.5s, the stalled body was awaited". Under a runner that delays the stub thread by more than 500 ms the test could fail, which would be a false alarm and not a hidden defect.
