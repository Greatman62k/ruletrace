## 4. Non-blocking findings

1. **Window after the command finished is undocumented.** `crates/rt-cli/src/main.rs:15-24` and `crates/rt-ai-tool/src/main.rs:15-24`. The watcher thread calls `process::exit(70)` whenever the pipe is closed, at any time before `main` returns. If the pipe closes after `run` has produced its outcome but before `main` returns, the exit code becomes 70 and the stdout write can be cut off. A command that finishes before the watcher runs can lose the same way: with stdin at EOF from the start, `ruletrace --lifeline-stdin validate --no-such-option </dev/null` exited 70 in 6 of 6 runs, while without the option it exits 2. This is consistent with UD-44 (the parent is gone, the output has no reader, exit 70 is the specified result) and cannot happen while the parent holds the pipe until the child ends. But neither `lifeline.rs`, UD-44 nor design §11.18.6 states it, and no test pins it. I recommend one sentence in the module docs or UD-44. An open idle pipe cannot change a normal run: `normal_run_is_unchanged_by_the_option` compares code, stdout, stderr and files byte for byte with an open idle pipe, and M6 shows the comparison is sensitive.
2. **A zombie counts as gone.** `crates/rt-cli/tests/lifeline_rig/mod.rs:259-280` (`state`), `:480-506` (`kill_and_time`). The test passes once the child is not `Running` (it is Absent or Zombie). That proves the child stopped executing. It does not prove it was reaped, and design Req 37.17 as quoted in §11.18.6 says "terminates and is reaped". A killed parent's children are normally reparented to init and reaped at once (the observed times were about 1 ms and 5 ms). In a container whose PID 1 does not reap, a defunct child would still pass. Judged against UD-44 "absence of every child", this is a weaker check than the wording. Either require Absent within the bound or document that "gone" means "no longer running" in UD-44 or the rig header. The rig header does disclose it for the probe.
3. **Custom-harness checks are not in the summed count.** The 2490 passed, 0 failed, 0 ignored figure sums only libtest `test result: ok. N passed` lines. The two `harness = false` binaries (`crates/rt-cli/tests/lifeline.rs`, `crates/rt-ai-tool/tests/lifeline.rs`) print `test result: ok (0 failed)` and contribute 12 checks that the sum omits. They did pass (exit 0, 6 `... ok` lines each). Reports should say "2490 libtest tests plus 12 harness-less checks".
4. **Windows start-up concurrency.** `lifeline_rig/mod.rs` `run_checks` runs all checks of a binary concurrently on threads, so several `CreateProcess` calls with piped stdin run at the same moment. Design §11.18.6 names handle inheritance between simultaneously started children as the Windows risk and says tests start one child at a time. A leaked write end would make closure and crash tests fail (a loud failure, not a false pass). I could not run Windows, so this is unverified. Serialising the process-spawning checks on Windows would remove the question.
5. **`catalogue_ud44.rs` does not pin the `executable` column or the meaning text.** It pins id, mnemonic, severity and exit code independently. `check-catalogue` (155 codes) and the generated enum cover the rest, and I regenerated with `gen-catalogue` to a byte-identical `code_generated.rs`. Low value, noted only.

## 5. What held up

- **Position rule.** `strip` (`lifeline.rs:21-26`) accepts the exact string as the first argument only. Unit tests: exact name, near misses (`=1`, trailing space, `--lifeline`, `-lifeline-stdin`), empty list, option alone gives RT-CLI-0002 path via `CliMissingArgument`. Process tests: a misplaced option gives exit 2 with RT-CLI-0004. A repeated option gives exit 2 with RT-CLI-0001 and no RT-CLI-0007. The remainder reaching `run`/`parse` is byte-identical (`a_command_line_without_the_option_parses_and_runs_as_before`).
- **Watcher only in `main`.** The thread is spawned only in the two `main.rs` files. `grep stdin` over `rt-cli/src`, `rt-ai-tool/src` and `rt-ai-responses/src` finds no other reader of standard input, so the watcher cannot compete with a command for stdin.
- **Watcher behaviour.** `wait_for_close` discards data, retries `Interrupted`, and returns on EOF or any other error. `watch` writes the rendered Diagnostic and ignores write and flush errors. The exit code is `ExitCode::Internal` = 70. Unit tests assert each of these with scripted readers and a failing writer. The expected text is hand-written and matches the Req 19.5 shape.
- **Catalogue.** The RT-CLI-0007 row text, code, mnemonic, Error, exit 70 and `rt, ai` are identical in the catalogue, design.md:1722 and UD-44. `gen-catalogue` reproduces `code_generated.rs` byte-identically, so it is not hand-edited. `check-catalogue` prints `ok (155 codes)`. The `catalogue_ud37.rs` change (`147 + RESERVED.len() + 2` to `... + 1`, with the reason in the comment) raises an expected count for a code that UD-44 adds. It is a justified expectation update, not a weakening: the assertion is still an exact count. `catalogue_ud44.rs` pins the new row from the decision text.
- **Long-running children are real and need no hook.** `evaluate --render` writes more than 1 MiB (`MIN_RENDER_BYTES` asserted on the plain run) to an unread stdout pipe, so the child cannot finish. `ruletrace-ai propose` connects to a loopback listener that never answers, the test waits for the accepted connection (`wait_for_connection`), and the attempt timeout is 90 s. No production test hook exists; `git diff` of production files shows only the option, the module and the thread.
- **`__parent` re-exec and `harness = false`.** `run_checks` joins each check, prints one line per check, and exits 1 on any failed check. Cargo reported the failing target with exit status 1 in every mutant run below (including `H1`, an edited expected code in the rig).
- **Control is meaningful.** Without the option, killing the parent leaves the child running at the 5 s bound. Mutants M6 (watcher always on) failed the control in `rt-ai-tool`, and the `rt-cli` control sits next to the same code path.
- **Bound enforced.** `BOUND` = 5 s is the only limit in `wait_within` and `kill_and_time`. M1 failed with "still ran 5s after the close/kill". Measured: about 5 ms after close, about 1 ms after kill for `ruletrace-ai` (loopback, one run).
- **PID reuse.** The Unix probe requires the scratch tag in the `ps` command line before reporting Running, so a reused PID of an unrelated process counts as Absent.
- **Rules.** `Cargo.lock` unchanged, no new dependency (only two `[[test]] harness = false` stanzas), no `unsafe` (both mains keep `forbid(unsafe_code)`, `scan-sources` ok), no change under `tools/`, `demo/`, `tests/fixtures`, `crates/*/tests/fixtures`, no scan allow-list or edge change, no golden change. The Req 17.10 exit-code tests pass. I found no claim of Req 17.8, V-1, V-2 or V-4 in the changed files.
- **Portability reading.** The Windows `state` parses `tasklist /FO CSV /NH`, matches PID column and image name case-insensitively, and `Stdio::inherit` of the held pipe goes to the child only in `__parent` mode. The macOS path uses `ps -o stat=,args= -p`, which is the POSIX form. Neither was run (see section 8).
