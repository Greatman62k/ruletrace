# Proof_Report ranking label for all-submitted standings

Five commits (`b912772`..`af8ffcf`, after `58ad25b`) add one line, `ranking`, under every decided-Standings `DECISION` line of the human Proof_Report. The text is the user-decided label. The change covers one rt-explain presentation function, four goldens, three test files and one design.md paragraph. No core logic changed. All checks requested pass, and the mutants are detected.

Watch for: the design.md claim that the Proof_Report format is "pre-release and has no consumer outside the demonstration goldens" is not established anywhere in the repository (confirmed, non-blocking). The eligible-only half of the regression test can only check the report text, because the IR has no such construct (confirmed, inherent).

**Verdict**: APPROVED

## High-level view

The label is rendered by `render_section` in `rt-explain/src/report/proof.rs` whenever the outcome is a decided Standings value. It is a fixed constant, so it is attached to the outcome shape and does not depend on the ranking rule's content. The JSON report and the version-1 format header are untouched, and the only golden changes are one added line in each of four `proof*.txt` files.

The regression test builds a report with a value decision and a standings decision. It requires the label exactly once, in the standings section only, and absent from the JSON. The two demo acceptance tests also require one label per standings decision and require ineligible p3 to appear in the ranked places. This establishes the all-submitted behaviour for the demo data, and it is the only evidence available because the IR has no eligible-only ranking.

The unit test fails when the label is removed, so it is independent of the goldens. The golden tests would also catch a change, though golden failures alone would be a weaker signal because goldens are regenerated by a bless step.

## Accuracy of the label

The golden shows `4: p3, p5` in the standings, and p3 has `eligible = false` (age 15) in DECISION 3. The ranking is therefore not eligibility-gated, and the label is accurate for the demo. The engine has no ranking filter step in the IR: a `Ranking` rule has a key, direction, tie breakers and a tie policy only (`rt-ir/src/rule.rs:183`). The design.md sentence "the first-version IR has no eligible-only ranking" matches this.

## Eligible-only distinction and test honesty

The IR cannot express an eligible-only ranking, so no executable contrast case exists. The test comment says so openly, and the test checks the report text and the presence of an ineligible participant in the standings. In the unit test, the name "p3" is only a string in a hand-built trace. It carries no eligibility fact, so it is the acceptance tests that establish the claim on real data. That is acceptable and honestly described.

## Format version

`PROOF_REPORT_VERSION` stays 1. The version appears in the human header (`format ruletrace-proof-report v1`) and in `proof.json` as a header field. Neither changed, and no golden header changed. No test pins the version number against the label change. The human text did change, so a consumer that parses `proof.txt` line by line would see a new line. I found no such consumer in the repository, and the format is not declared stable in any spec text I could find. Keeping v1 is acceptable for that reason, but the "pre-release" wording in design.md is an assertion, not something the repository establishes (see Issues).
