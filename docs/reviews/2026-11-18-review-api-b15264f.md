## 4. Non-blocking findings

- **F1 (medium): leading-`::` path is not detected.** `::rt_engine::evaluate(1)` in an expression is not reported (`app_api.rs`, `external_paths`, `after_path_or_field` treats the preceding `::` as a path continuation). `use ::rt_engine::...` is handled. Reproduced in a scratch test: result `[]`. It is a valid fully qualified path that the module doc says is read. No current source uses it. Not blocking now. It matters for 13.4, where the rule is the enforcement of Req 24.13. Fix: treat `::` as a path start when the token before it is not an identifier or `>`, `)`, `]`. Add a negative test.
- **F2 (low): module entries are not refused.** `parse_allow` accepts `allow x rt_explain::report -- r`. That would permit `use rt_explain::report` and then every short path `report::f` unseen. No such entry exists. The real bypass needs a visible, reasoned list entry, so the implementer's claim holds: after `use rt_explain::report` the short path `report::assemble_report` is unseen, but the `use` itself fails because only leaf items are listed (tested, see section 7). Not a realistic bypass. Suggest a reviewer note or a lint for module-like entries (lowercase last segment that is not a function is not decidable from tokens).
- **F3 (low): prefix extension is broad for a listed type.** A listed type allows any associated item (`rt_data::Question::anything`). Documented and tested. Acceptable.
- **F4 (info): `rt_engine::evaluate` is listed for both layers.** Required by Req 31.11. The note in the list header correctly says the Req 24.13 ban for rt-lab is "not listing".
- **F5 (info): the superseded design table still contains an "APP-API" row.** It sits under the "Superseded text" heading and the blockquote, so it is visible and marked. No change needed.
