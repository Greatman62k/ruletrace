## 4. Non-blocking findings

F1 (for the user to judge). An unrequested row of a reportable kind with an invalid value is RT-APP-0004 and exit 2 (probe: `p1,eligible,xx`, requested `[]`, gives `AppInputValueInvalid` at (2,13), field `value`; same for `score`, and for an empty value `p1,eligible,`). The design text (amended §8.3) says this explicitly: "its value is still checked", and the unused-row reason `NotRequested` applies only to a row that passed. Decision B says a "structurally valid" row whose target is declared but not requested "is not rejected solely because its target was not requested". The code and design agree with each other. It is consistent with B if "structurally valid" includes a valid value, and it is a stricter reading than B if it means CSV structure only. Consequence of the two readings: an unrequested `Other` row with value `xx` is listed (value not checked), an unrequested `score` row with `xx` is an error. The asymmetry follows from "no value type is known for Other". It also follows from decision A: `p1,score,` is now a well-formed row and is rejected for its empty value (RT-APP-0004), not for structure. An empty published value is invalid for every kind and was so before the commit (design: "an invalid value (an empty value included)"); decision A's "Missing like any empty cell" holds for participants and collections but a published empty value is still an error. The user should confirm that this is intended.

F2. `UnusedReason` has no `#[non_exhaustive]`; it is a new public enum with two variants. Only rt-data uses it today (grep over `crates/` outside `tabular` found no other user). Not a defect.

F3. Mutant M5 (removing `lexer.peek().is_none() ||` at csv.rs:319) is killed by one test only (`a_header_ending_in_a_separator_is_an_error_at_the_separator`) and no data-row test. This suggests the clause is partly redundant with `at_line_end()` for data rows. I did not classify it as equivalent or not (see section 8).
