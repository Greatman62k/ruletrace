### Canary fragment logic (item 4)

`leak::first_leak` uses an 8-byte window, or the whole secret when it is shorter. I traced the rolling `u64` and found no defect. After the shift the register holds exactly the last 8 bytes. The 4096-slot table is a pure pre-filter, since a window that is present always has its slot set. The final check is an exact lookup in the window set. Haystacks shorter than 8 bytes and empty secrets are handled. A 512-case proptest compares it with a naive reference over a small alphabet, and the saved regression seed replays. A 7-byte run is correctly not a leak, and the 8-byte one is. The strictness is about right: a window of 8 bytes of a 43-byte random-looking canary will not occur by chance. It will not detect encoded forms (base64, case-folded, split across lines). That is outside what the user asked for.

### `review approve` replacing `review list` (item 5)

The old failing command was `review list` on a missing ledger. Req 26.6 was amended, so `list` is read-only and exits 0, and the matrix now expects exit 0, `status Proposed` and no created file. The failure case is kept as `review approve` with a missing ledger and no `--create-ledger`, expecting exit 2 and `RT-CLI-0003`. That is a negative that still has an exact code and exit. The change is justified and the negative is not lost.

### CI guard (item 7)

The step runs in the `core-only` job, which is `ubuntu-24.04` only, so shell portability is not a concern. It uses POSIX `test`, a `for` loop, `ls | grep -Eq` and `[ -e ]`. GitHub's default `bash -e` is enough. The guard works because `--target-dir target/core-only` is fresh in a checkout and the real executable would land in `debug/`. It also checks that `ruletrace` exists, so a build that produced nothing cannot pass. The `.exe` name is harmless on Linux. See issue 3 for the narrow pattern.
