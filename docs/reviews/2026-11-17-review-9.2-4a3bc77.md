## 4. Non-blocking findings

1. Mutant M4 survived: removing `known_position(found).is_none()` from the guard in
   `classify` (`compare.rs`, first `if` of `classify`) changes no test. The code is right.
   The test `an_indeterminate_ranking_is_never_equal_and_never_a_tie_kind` makes every
   participant Indeterminate, so it cannot show that an Indeterminate entry sitting in a
   published tie with a Known entry at another position stays `value_differs`. Needs a
   tie-breaker-missing case where only a tied subset is Indeterminate. Genuine coverage gap
   against the user constraint "Indeterminate never classifies".
2. Mutant M10 survived: counting an Indeterminate or non-ranking other member as
   "separating" (`is_some_and` to `map_or(true, ..)`). Same missing case as 1.
3. Mutant M6 survived: mapping a published Boolean to the text `"1"` in `published_number`.
   The Boolean test has one entry, so a Boolean cannot collide with a number. Add a case
   with a Boolean and the number 1 on one Target.
4. The determinism property compares two runs with the same entry order. Permutation of
   published entries is true by construction (`PublishedResult` holds a `BTreeMap`,
   `rt-data/src/published.rs:47`), and one fixed test reverses participants and entries.
   The property does not permute. Acceptable, but the claim "deterministic under
   permutations" rests on the container, not on a test.
5. The reference `model` in `tests_published_ranks.rs` has the same structure as
   `classify` (split, then separated, then plain). Its positions come from scores only, so
   the values are independent, but the classification order is the same code shape. The
   hand-computed tests carry the independent evidence for the order.
6. `group` of a `tie_not_in_computed_result` difference lists every participant with that
   published value, including ones not compared (unlisted in the questions). Consistent
   with "published tie members" in the design. No change needed.
7. Amendment text (`docs/requirements-amendments.md`) is consistent with design §3.6.3 and
   with Req 13.12, 31.7, 32.6. It adds two things the design leaves open: the name
   `value_differs` and the rule that a split needs at least two distinct published
   positions among listed members. Both are stated as open points. The second is the
   reading of "gives different positions". The user should confirm both.
8. Claim check: "RT-EXE-0011's base message is unchanged". True for `value_differs`. For the
   two new kinds a sentence is appended (`compare.rs`, the `match kind` block), so the
   message text of those differences is new. The status note says this, the commit-message
   claim is the shorter form.

## 5. What held up

- Classification order against design §3.6.3: read the text and the code. Split of a
  computed Tie_Group (needs more than one distinct published position among listed members)
  is tested before the published-tie test, so each entry has one kind. Design is silent on
  precedence; the amendment records it. Hand-computed tests
  `a_published_split_of_a_computed_tie_group...`, `every_member_of_a_split_group...`,
  `a_published_tie_that_the_computed_result_separates...`,
  `a_published_tie_at_the_position_of_one_member_reports_the_other`,
  `a_published_tie_of_a_computed_group_at_another_position_is_a_plain_difference` have
  expected positions that I re-derived from the scores in the test (10,10,2 gives 1,1,3;
  9,5,1 gives 1,2,3). They match.
- Participants absent: unlisted participants are not compared; published entries with no
  computed pair go to `unused` (`only_listed_entries_are_compared...`,
  `an_unlisted_member_of_a_computed_group...`). Passed.
- Indeterminate and Missing: a computed Indeterminate position never equals a published
  value (`equal` returns false) and `classify` returns plain for it. Tested for the
  all-Indeterminate case only (see finding 1).
- Boolean published value for a ranking target: plain difference, never a tie kind.
  `a_published_boolean_for_a_ranking_target_is_a_plain_difference`.
- Every difference keeps `question` and `entry`, the Decision_Trace index of the `Place`
  entry. Two tests check that the entry at `entry - 1` is the expected `Place` with the
  expected members.
- No tolerance or rounding: comparison uses `rt_numeric::cmp` and canonical text only. No
  float in the diff. No `rank_reference`, no external ranking data, no IR or catalogue
  change. 9.3 stays deferred.
- Both property tests use `with_cases(256)`, so the 256 minimum holds. The first checks the
  differences, kinds and groups against a model computed from scores, plus `compared`
  count. The second builds the equal published result from scores and asserts no
  difference.
- Existing published-result tests in `tests_rank.rs` are unchanged apart from visibility.
- Workspace tests, rt-demo tests, clippy, rustfmt and five xtask checks pass (section 6).
- Claim: "no golden changed, no data type or file format changed". Verified by the empty
  diff on those paths and the untouched `rt-data`. Note `Difference` gained two public
  fields and `DifferenceKind` is new public API in `rt-engine`; that is a Rust API change,
  not a data or file format change. `scan-api` passes.
- Claim: "`check-catalogue` fails only because of a release-tag/baseline issue". Partly
  reproduced. Without tags it passes (exit 0, "baseline skipped: no release tag exists").
  With `--release-tags v0.1.0` it fails with "catalogue/baseline.v1.json is missing but
  release tags exist (v0.1.0); Req 7.12 requires it" (exit 1). The diff touches no
  `catalogue/` file, and `catalogue/baseline.v1.json` is absent at both ends of the range.
  So the failure, where it occurs (a checkout with a release tag), is independent of this
  change. I could not list tags with `git tag` (blocked by the profile), and
  `.git/packed-refs` has no tag line; I did not see CI output.
