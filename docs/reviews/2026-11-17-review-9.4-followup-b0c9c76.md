## 3. Blocking findings

### B1. `TraceRef::new` ownership check: length, rule and revision comparisons are unpinned (mutants N15, N16, N17 survive)

`Verification::is_for` (`crates/rt-explain/src/verify.rs:130-139`) compares four things: span count, rule, revision and recorded span. Only the span comparison has a test (`a_verification_of_another_trace_is_refused`, N1 killed).

- N15: delete `refs.len() == self.spans.len() &&`. Result: SURVIVED. Without it `zip` truncates, so a verification of fewer spans would be accepted for a trace with more spans. A one-span verified verification could then mark a two-span trace `verified`. That is the B1 forgery in a new form.
- N16: delete `**rule == v.rule &&`. SURVIVED.
- N17: delete `*revision == v.revision &&`. SURVIVED.

The production code is correct. Scratch test (kept only in my scratch directory):

```
len:      one-span verification for two-span trace => Some(VerificationNotForTrace { trace: 0 })
rule:     => Some(VerificationNotForTrace { trace: 0 })
revision: => Some(VerificationNotForTrace { trace: 0 })
```

Needed: three tests in `tests/trust_boundary.rs`, one per comparison, each asserting `ReportError::VerificationNotForTrace { trace }`. The span case is the model.

### B2. `ReportDoc::new` refusal of differing evidence sources is unpinned (mutant N3 survives)

`crates/rt-explain/src/report/model.rs`, `ReportDoc::new`, the check `e.sources == v.spans()`.

N3 removes it, and every test still passes. The three refusal tests (`trust_boundary.rs:238,254,270`) are all decided by the `verified` flag or by a missing index, never by differing sources between two verifications with the same flag. The index and order mismatch you asked about is therefore unpinned. Scratch attempts R3 (verified entry whose sources are 0..20, verification at the index covers 0..10) and R7 (verifications swapped, both verified) are refused by the real code:

```

```

Needed: two tests of that shape (R3 and R7) in `tests/trust_boundary.rs`.
