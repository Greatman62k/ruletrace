## 4. Non-blocking findings
1. Surviving mutant: the once-only guard is untested. Replacing the `static`
   OnceLock with a per-call local made origin_independence build 3 times (3
   "NESTED_BUILD" markers vs 1) and all 3 tests still passed. Nothing detects a
   regression of the guard. Acceptable for a CI-flake mitigation, but the guard
   rests on code review only.
2. coverage_unreferenced.rs:40-50 (`build_binary`) ignores RT_BIN_DIR and always
   runs a nested cargo build. Pre-existing (the diff only adds lines) and
   inconsistent with the other five files. It still builds once per process.
3. The guard is per test process. Each file in tests/ is a separate process.
   Cargo runs test binaries one after another, so builds from different files do
   not overlap under `cargo test`. They would overlap if run in parallel (for
   example nextest). The commit message claims only per-process scope, which is
   accurate.
4. Errors from a failed build come from `assert!` (panic) inside get_or_init.
   A panic leaves the OnceLock uninitialised, so later tests retry the build and
   panic again. Each failing test reports the failure. This is safe, only noisy.
   Launch errors (`?`) are cached as `Err(String)` and every test sees them.
   The Err loses the original error type (stringified). Cosmetic.

## 5. What held up
1. Behaviour. `bin_dir()` wraps the old body, renamed `build_bin_dir()`, in
   `static OnceLock<Result<PathBuf,String>>`. `git diff 75dfe7d 5644e52` has no
   removed lines (66 insertions only). The `RT_BIN_DIR` check is still the first
   statement of the build function, so it keeps precedence. Result is cloned and
   converted with `Into` into Box<dyn Error>. No unsafe, no unwrap/expect.
2. No test weakened. No assertion, test, #[ignore] or cfg changed. Tests still
   spawn the real built binaries. Mutant 1 (wrong path) shows a test cannot pass
   without a usable binary.
3. Consistency with bf25ce2: same OnceLock pattern, same string-error caching.
4. Remaining nested builds in rt-demo: only the six edited files call
   `cargo build` (grep for "build" in crates/*.rs). Outside rt-demo:
   rt-tests-core golden/ingest.rs (already guarded by bf25ce2) and
   rt-xtask/src/metadata.rs (not a test of the executables, not examined for
   concurrency). coverage.rs, coverage_partition.rs, coverage_store.rs and
   live_guard.rs do not build or run binaries. Within one file, parallel tests
   now share one build, so intra-process concurrent builds are gone.
5. Plausibility of the mitigation (item 3 of the task). Mechanism: concurrent
   `cargo build` calls on the same target dir serialise on cargo's build lock,
   but a build that rewrites the output executable can replace or relink it while
   another test is exec-ing it. Building once removes the intra-process
   concurrent builds. NOT confirmed: the root cause was not reproduced locally
   (the author says the nested build does not relink on Linux, and I ran no
   macOS). The fix might also leave the race open if the relink came from another
   process (the outer `cargo test` or another test binary). The evidence is one
   macOS pass.
6. CI (read-only gh): run 43896108442, headSha 5644e529, attempt 5 conclusion
   success. Attempts 1-4 failed only because macos-15 jobs were "cancelled"
   (toolchain, and in the earlier attempts demo-offline, clippy, fmt and test
   on macos-15) with ci-gate failing as a result. Attempt 5 ran toolchain
   (macos-15) and ci-gate; the other 21 jobs are carried over from 2026-11-16.
   test (macos-15) (job 136164328723, started 15:56:12Z, ended 16:07:17Z) and
   demo-offline (macos-15) (136164388433, 16:13:16Z to 16:13:47Z) are "success".
   Caveat: the macOS jobs passed once; a single pass does not prove a flaky race
   is gone. Their original attempt numbers were not shown by the gh output I used.
