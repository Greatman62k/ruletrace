### 1a. LT-6 acceptance (design section 11.18.5, evidence item 3)

Basis, each point checked by reading the named file:

- Requirement text. Req 37.5 to 37.9, 37.24 and 37.25 as amended give option A:
  no cookie, Basic credentials with user name `lab`, constant-time compare,
  check order Host, Origin, credentials, CSRF token, Cookie headers ignored,
  CSRF token issued only to authenticated requests.
  (`requirements.md:1313-1316, 1332, 1333`.)
- Browser evidence. `docs/security/lt6-browser-2026-11-20/` hashes match the
  record (`sha256sum`: `e0597b9c`, `cd3ba3fe`, `d55aa7d9`, `0f54d1441`), and
  `grep -ci authorization recorder-*.log` gives 0 and 0. The recorder logs show
  requests for `/`, `/favicon.ico`, `/other` at 127.0.0.1:18081 after the lab at
  :18080 had logged `authorization=present`. The lab logs show the cross-origin
  POST at 16:28:45 and 16:37:49 with `authorization=present` and 403 BadOrigin.
  This supports "Firefox 153.5.1esr and Google Chrome 158.0.8127.36 on Linux do
  not send the credentials to another port" and "the browser does attach them
  to a cross-origin POST to the lab, so Origin and CSRF checks are load-bearing".
- Prototype. `spikes/lt6-basic-auth/src/lab.rs:93-122` applies the decided
  order; `tests/server.rs` has tests for no credentials, cookie only, wrong
  credentials, malformed header, wrong Host, wrong or missing Origin, wrong or
  missing CSRF, and credentials without Origin/CSRF.

Residuals, judged:

| Residual | Judgement |
| --- | --- |
| Secret valid for the whole session (T12d, R-L7) | This is a real weakening. Before, a scrollback reader after first use could not open a session. Now a reader of the terminal, tmux log or shared screen during the session can authenticate, fetch a page, take the CSRF token and approve. The attacker needs access to the user's terminal output, which is a narrower population than "any local server the browser can be lured to" (T7), but it is not a subset. Acceptable only if stated plainly as a residual (condition C3). The user did not accept T7 as a residual (UD-39), so the swap should be shown to the user as a trade, not only as wording. |
| Safari, Windows, other browsers not run | Protection rests on browser conformance to RFC 9110 section 11.5 (credentials per scheme, host and port). Two browsers on one OS were observed. No claim can be made for others (C2). |
| Prototype Origin check narrower than Req 37.4 | `lab.rs:98` checks Origin only on POST and requires an exact match. Req 37.4 also refuses a foreign Origin on GET and accepts a state-changing request with no Origin when `Sec-Fetch-Site: same-origin`. The browser run therefore does not exercise the full check. Acceptable because it is owed in 13.4/13.6 (C1). |
| Prompt phishing (a hostile local server answers 401 Basic and the user types the secret) | Recorded in the evidence record section 4 but not in the threat model. Needs an entry (C3). |
| Stand-in, not `ruletrace-lab` | The evidence shows the browser behaviour, which does not depend on the server. Server-side behaviour must be re-shown on the real executable (C1). |

Conditions:

- **C1 (tests owed in 13.4/13.6, each asserting exact status and no side
  effect):** two Authorization headers, one valid, give 401; full Req 37.4
  Origin check (foreign Origin on GET gives 403; state-changing request with no
  Origin and no or other `Sec-Fetch-Site` gives 403); check-order table (Host
  before Origin before credentials before CSRF); cookie only gives 401 and no
  `Set-Cookie` is ever sent; credentials of an earlier Launch_Secret give 401;
  a refused request does not reset the 30-minute limit (simulated timer, at
  29:59 and 30:00); no CSRF token in any 401 or pre-authentication body; canary
  Launch_Secret and Authorization value absent from logs and responses
  (37.22); mutants removing the Origin check and the credential check (37.23).
- **C2 (browser):** repeat the protocol of
  `spikes/lt6-basic-auth/BROWSER-PROTOCOL.md` against `ruletrace-lab` on
  Firefox and Chrome on Linux when it exists. The threat model states that only
  those two browsers on Linux were verified. Safari (and any Windows browser)
  must be run before the protection is claimed for macOS or Windows, which are
  Req 21 platforms.
- **C3 (threat model edits at resolution):** rewrite T7 (it still says
  "Candidate"), update R-L2 (`laboratory-threat-model.md:335`), state T12d as a
  residual in plain words including that the secret authenticates until the
  session ends, add the prompt-phishing residual, record that browsers attach
  the credentials to cross-origin requests (so Origin and CSRF are load-bearing),
  and record the user's explicit acceptance of the T12d residual.
