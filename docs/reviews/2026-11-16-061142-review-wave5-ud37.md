# Wave 4 fixes: `models` escaping and one loopback definition (commits 74a78b4..ed6c3e2)

The seven commits fix the two blocking defects of the wave 4 review. `models` now escapes every control character and U+2028/U+2029 before it appends the line feed. The tool's endpoint validation and the adapter share `rt_ai_responses::is_loopback_host` and `has_unusable_character`. The same commits widen the RT-AI-0007 meaning, extend the network-guard scan to IP literals and add a runtime loopback assertion to the `rt-ai-responses` unit tests. They also change the RT-AI-0203 message, strip every trailing slash from an endpoint, refuse Cf format characters, and record deferrals and an approval note.
I built and tested in separate worktrees (HEAD and 74a78b4) in a loopback-only network namespace, offline. At HEAD: 1,747 tests passed, 0 failed, 0 ignored; clippy `-D warnings`, `rustfmt --check` (changed files and `--all`), the seven xtask checks and `cargo deny --offline check` are clean. Five mutants of my own were killed.
Watch for: the claim "every endpoint that validation accepts builds an adapter" is still false for a loopback endpoint with a fragment (`http://127.0.0.1:9#f`), which passes validation and ends as `RT-CLI-0006`, exit 70 (*confirmed*). The credential never reached a non-loopback host over http in any of 3,000,040 inputs.

**Verdict**: NEEDS_CHANGES

## High-level view

The `models` defect is fixed. An identifier that ends in LF, CR, U+2028, U+2029 or U+0085 prints as one escaped line, and the old code reproduces the defect (`good\n` printed `good` plus a blank line).

The spelled-out IPv6 loopback defect is fixed: validation and the adapter now call one function, and the previous failures (`[0:0:0:0:0:0:0:1]`, `[0::1]`) build an adapter. The two parsers still differ in what else they accept, and the agreement test does not cover that: a fragment and a zero-padded six-digit port pass the tool and fail the adapter. All divergences I found fail closed. No input sent a credential over clear text to a host that is not loopback.

The behaviour change (`127.0.0.01` no longer accepted by the adapter) removes a disagreement. The tool already refused it, because `std` rejects leading zeros. The catalogue change is meaning text only. The tests were extended, not weakened.

## `models` line escaping (Req 35.18)

`escape_line` escapes `char::is_control` characters plus U+2028 and U+2029 as `\u{hex}`, and the caller appends one LF. On 74a78b4 the new tests fail with `left: "good\n\n"` against `"good\\u{a}\n"` and `"good\ngood\n\n"` for the pair test. At HEAD all seven cases pass, including CR, CRLF, U+0085, U+2028 and U+2029 and the ordering of `good` and `good\n`. Expected strings are written by hand. Removing the U+2028/U+2029 clause (mutant M2) fails `every_line_break_in_an_identifier_is_escaped_before_the_terminator`.

## Endpoint agreement and the credential

Reproduction on 74a78b4: `http://[0:0:0:0:0:0:0:1]:9` ends in `RT-CLI-0006` (expected `RT-AI-0109`), and the adapter accepts `http://127.0.0.01` where the table expects refusal. At HEAD `tests_endpoint_agreement` passes.

I ran 40 spellings through `run_models` against a closed loopback port and printed the tool verdict next to the adapter verdict. Refused with `RT-AI-0004`, exit 2, and nothing sent: `http://127.0.0.1.:9`, `0x7f.0.0.1`, `2130706433`, `[::ffff:7f00:1]`, `0177.0.0.1`, `[::127.0.0.1]`, `[::1%25eth0]`, `LOCALHOST.`, `ftp://`, fullwidth digits, ideographic full stops, a fullwidth `l` in `localhost`, and `127.0.0.1.evil.example`. Refused earlier with `RT-AI-0003` (userinfo): `localhost:9@evil.example`, `127.0.0.1@evil.example:9`, `[::1]:9@evil.example`, a query. Refused with `RT-AI-0002` (invalid URL): leading and trailing space, CRLF injection, U+2028, U+200B, `[::1]:0`, port 99999, `localhost:+9`, `127.0.0.1:9:9`. Accepted and failing only at the wire (`RT-AI-0109`, exit 5): `HTTP://127.0.0.1:9`, `Http://LOCALHOST:9`, `[::1]:9/`, `127.0.0.1:09`, `/v1//`, `/%2e%2e`.

For a wider check I generated 3,000,000 strings from a 35-token alphabet with a fixed seed (133,649 accepted by the tool). For every accepted text I asserted that the adapter either accepts it or fails, and that a clear-text adapter host is loopback. The second assertion never failed. The first failed for two classes: a fragment (25,686 texts) and `https` with a zero-padded port of six characters (4 texts). Both fail closed with exit 70 and a wrong code, so this is a correctness defect and not a leak. The probe is not committed; it was a temporary test in the worktree.

## `127.0.0.01`

Req 28.6 names 127.0.0.0/8, `::1` and `localhost` and says nothing about leading zeros. The tool used `std::net::Ipv4Addr`, which rejects `127.0.0.01`, before and after this range, so the tool's behaviour did not change. The adapter's old hand-written octet check accepted it, which is the disagreement the table row now pins. No documented form regresses: `127.0.0.1`, `127.255.255.254`, `localhost` in any case and every `::1` spelling accepted by `std` work in both.

## Catalogue, assertions, traceability note

The generated doc comment in `code_generated.rs`, `requirements.md` and `design.md` carry the same text, and `check-catalogue` passes (152 codes; it skips the release-tag baseline because no tag exists).
