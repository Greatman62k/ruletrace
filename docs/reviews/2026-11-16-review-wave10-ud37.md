# Review wave 10: transmission-permission guard in the demo runner (task 10.7)

Commits 57e03ca, 27652f7, 5f6b754 (the 10.15 commits 49c4cd3, 07f53a5, d84ce26 are excluded). Reviewed in a separate worktree at 5f6b754, every cargo command inside `unshare -rn` with loopback only, no credentials, no network, no live provider call, no real Kiroween or ICC document.

The change adds `rt-demo/src/guard.rs` and calls it from the real runner. `run_step` now refuses any `ruletrace-ai` step whose configuration is not provably `mock-replay`. A new `run_live_step` is the only path that starts a live step. It starts one only when the manifest has `transmission_permitted == true` for every `--consent` document and the store, `--out` and `transmission_log` are outside `golden/` and `provider/`. Two example configurations, a RUNBOOK live section and tests come with it. The guard held against every bypass I could build from the runbook and the CLI. It has one CI-breaking defect (Windows clippy) and several hardening gaps that only matter for hand-built `Step` values, hostile symlinks or malformed manifests.

Watch for: the `live_guard.rs` test file fails `clippy -D warnings` on Windows, and CI runs clippy on `windows-2022` (confirmed). A hand-built `Step` with `argv[0] = "./ruletrace-ai"` passes `run_step` unguarded (confirmed, not reachable from `parse_runbook`). A dangling symlink into `golden/` is not detected (confirmed). Duplicate manifest ids with `[false, true]` authorise a transmission (confirmed). The unmodified OpenAI example sends the consented document before the provider can reject the placeholder model (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The guard classifies each step at the moment it runs, not once per runbook, so a configuration changed by an earlier step is judged fresh. Offline is the exception: a step is offline only if argv is exactly `ruletrace-ai propose` with one readable `--config` that a deliberately small TOML reader proves to be `mock-replay`. Everything the reader or the argument parser does not understand counts as live. Against the real loader this held on 6,960 generated configurations (845 judged offline, 0 where the loader would use a network provider).

The permission check is exact: every consented document must be in the manifest and be the boolean `true`. It runs before the output-location checks and before any process starts. The tests prove "before spawn" with a fake executable that writes a marker and opens a loopback connection, with a positive control. Fifteen mutants of my own: fourteen killed, one equivalent.

The weak points are at the edges. The offline default is "anything that is not exactly the string `ruletrace-ai`", which is only safe because `parse_runbook` restricts argv[0]. Symlink resolution ignores dangling links. The manifest lookup uses `any`. The examples and runbook are accurate against the real CLI, but the by-hand flow does not go through the harness and the OpenAI placeholder is not refused by anything.

### Where the guard runs and what it can be made to run

`spawn` is the only process start in `rt-demo` (grep for `Command::new`, `spawn` and `process::` finds one site). It is private and reached from `run_step` (which classifies first) and `run_live_step` (which calls `authorize_live` first). `run_runbook_recorded` calls `steps_for`, which drops steps declared `"live": true`, and then `run_step`. A live-configured step without the live mark is still refused by `run_step`; a step in another profile is never reached. The live mark is therefore documentation plus a filter, not the safety mechanism. The claim that only `run_live_step` starts a live step holds for steps from `parse_runbook`. It does not hold for a hand-built `Step` (issue 2).

`parse_runbook` rejects `./ruletrace-ai`, `/abs/ruletrace-ai`, `ruletrace-ai.exe`, `Ruletrace-AI` and `RULETRACE-AI` as "not a logical executable". It also rejects arguments that start with `/`, `\` or `X:` and any `..` segment.

`parse_ai_args` mirrors the tool's own `scan` in `rt-ai-tool/src/cli.rs`: exact option tokens, value is the next token and must not start with `--`, `--config=x` and `--` are unsupported, only `--source-model` and `--consent` repeat. The guard rejects what the tool rejects and more (`--dry-run` twice is an error for the tool but accepted by the guard). It never accepts what the tool would read differently. `--consent=x`, `--config=x`, abbreviations, a repeated `--config` and a stray positional all end as live. `models` is not `propose` and so is live and refused offline. In the live runner it needs `--consent` and `--store`, which the tool's `models` parser rejects.

The environment is cleared for every step. Offline steps get no variables, live steps get only the variable named by the configuration's `credential_env_var`. Config discovery from the environment does not exist in the tool, and the relative `--config` resolves against `work_dir/cwd`, the same directory `Command::current_dir` uses.

### Configuration reader

The reader accepts comment lines, `[bare]` headers and `bare = "string"` or other single-line values. Dotted, quoted and unicode-escaped keys, inline tables, triple-quoted strings, multi-line arrays, duplicate keys and tables, `[[x]]`, trailing comments after a header or a string, and a leading BOM all make the file unreadable, which makes the step live. Any `endpoint` or `credential_env_var` key anywhere also disqualifies offline.

I tested the invariant "guard says offline implies the real `load_config` either refuses or yields `mock-replay` with no endpoint" with three base files, 30 hostile snippets inserted at every line position, and 6,000 random character edits (6,960 inputs). 845 were judged offline, none violated the invariant. The `!has_network_field` clause is not exercised by this oracle, because the loader itself drops or refuses an endpoint on `mock-replay`; only the unit test `mock_replay_v2_is_offline_and_a_provider_with_an_endpoint_is_not` pins it. That is acceptable defence in depth.

### Output locations

Verified by running `authorize_live` in a scratch test (removed afterwards). `..` into `golden/` (via `transmission_log`), a live symlink to `golden/`, `golden/x`, `GOLDEN/x` and `./Golden/x` were refused. Absolute and `../../escape.log` log paths were authorised, because the rules protect only `golden/` and `provider/`, not the work directory. A dangling symlink into `golden/` was authorised (issue 3). `Provider/` and `PROVIDER/` were authorised on Linux, correctly, since they are different directories there (issue 5 covers the other systems). Store paths that do not exist yet are handled by resolving existing ancestors and appending the rest. Windows `\\?\` and short-name forms rely on `canonicalize` of both the base and the target returning the same verbatim form; I did not run it.

### Tests

Most refusal tests use an empty `bin`, so a leaking guard would produce `DemoError::Step "cannot run"` instead of the exact refusal. Those work on Windows too.

### Example configurations and RUNBOOK

Both examples load through the real `load_config`. They name the credential by variable only, the endpoints are the exact official hosts `https://api.meta.ai` and `https://api.openai.com` (the adapter appends `/v1/responses`), and an inline `api_key` is refused. The OpenAI file is the issue 6 case.

I ran the RUNBOOK by-hand blocks in a temporary HOME inside the sandbox: `ruletrace ingest` exited 0, and `propose --dry-run` printed the request id and sent nothing, with no credential set.
