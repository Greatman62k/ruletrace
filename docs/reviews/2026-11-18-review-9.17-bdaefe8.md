## 4. Non-blocking findings

Numbered; severity in brackets.

**F1 [medium] The solo baseline is produced in the same process as the runs
under test, so state that persists across runs is masked.**
`solo_runs` in `workflow_module_isolation.rs` calls `Job::run` in the test
process, and the six tests run on parallel threads of that one binary. A
sticky state set by an earlier or parallel test is already present in the
"solo" run. Only Outcomes are pinned to hand-derived values
(`solo_runs_have_the_hand_derived_outcomes_and_classes`). Traces, the human
report and the JSON report are never compared with an independent value, and
the run "alone" is not a fresh process. Evidence: mutants I2 and I3 below.
I3 survived the isolation binary (6 passed) and was caught only incidentally
by the environment binary (`the_baseline_child_prints_what_this_process_computes`
compared a fresh child with this process). I2 survived both binaries. Req 20.6
requires equality with "executing that Rulebook alone".
Recommended fix: take the solo baseline from a fresh child process (the spawn
helper of the environment test already exists), or pin the human and JSON
bytes of the jobs to committed goldens (`tests/fixtures/app-reports/` holds
reviewed `report.txt` and `report.json` for the Bracket data), and keep the
interleaved runs in one process.

**F2 [medium] The probe does not show that "each variant reached the child".**
`the_probe_shows_that_each_variant_reaches_the_child` probes one combined
variant. It asserts `TZ`, `LC_ALL`, `LANG`, cwd files and `OPENAI_API_KEY`.
It does not assert `MODEL_API_KEY`, `RULETRACE_OPENAI_API_KEY` (only
`MODEL_API_KEY=(unset)` is asserted in a variant that never sets it), `PATH`
(printed, never asserted), the empty-`PATH` case, or the `C` and `UTC`
values. Evidence: mutants A and C2 below survived; B (cwd ignored) was killed
by the probe alone. The status note's sentence "a probe mode shows that each
variant reached the child" overstates this. The spawn code is one generic
loop, so the real risk is low, but the claim is not backed.
Recommended fix: probe every `Variant` the tests use inside `assert_all_equal`
(spawn in `probe` mode and compare the printed values with `v.env` and `v.cwd`).

**F3 [low] The 9.5 checklist note still carries stale text.**
The edit adds the 2026-11-18 update correctly, but it leaves the sentence "9.5
therefore cannot close while 9.17 stays deferred unless the user moves that
one test" in the same bullet. It also still says 31.4 and 15.6 "wait for
9.11", and 9.11 is `[x]` (line 1132). The 9.5 status note (line 1082) still
lists "the Req 31.15 isolation test (9.17)" as pending, and the 9.6 status
note (line 1093) still says "9.17, deferred". None of these were touched by
the commit. The 9.5 note is otherwise accurate: 9.16 goldens are committed
(`42e9e01`) and 9.16 is `[ ]`; 9.8 is `[ ]` with the source scan open; 9.5
stays `[ ]`.

**F4 [low] Original 9.17 text and Req 31.11 versus what was delivered.**
- Original text: "run each executable ... assert byte-identical stdout, stderr,
  report files and exit code". The commit tests the library output (class,
  results, human, JSON), plus the canary absent from stdout and stderr. This
  follows the UD-38 amendment (libraries have no stdout, stderr, files or exit
  code; the executable part belongs to 13.6) and the status note says so.
- Req 31.11 says "at least two values of the clock". The test cannot set the
  clock. It uses two starts 1.1 s apart and requires the wall-clock second to
  advance. This catches a library that embeds the time of day. It does not
  catch a library that depends on a specific clock value, for example a
  parity of seconds (which would survive about 1 run in 10, since the gap is
  1 or 2 seconds). The status note states the limit honestly. I judge this
  acceptable for a library that the scan of 9.8 also forbids from reading the
  clock, but the closure of Req 31.11 should name the source scan as the
  other half of the evidence.
- "With and without `ruletrace`, `ruletrace-ai`" is tested with shell-script
  stand-ins on `PATH` (a control test shows the marker works). The libraries
  are not given a path to any executable, so the test shows only that the
  process environment does not reach the reports. The note says this. I judge
  it acceptable for Req 31.11 as worded for library crates, where "present"
  can only mean present in the environment. The locale variants set `LC_ALL`
  and `LANG`; the review machine may not have `de_DE` or `tr_TR` installed
  and Rust does not read the C locale, so those values show little. The note
  does not say this.
- "Observable: three platforms": not delivered, and the note says pending.
  Stand-ins are inert on Windows, so the PATH marker control is Unix only.

**F5 [info] "Interleaved per input record" is implemented as one run per
participant record, alternating modules.** The engine has no API to
interleave two evaluations inside one run, so this is the only available
reading. Reasonable.

## 5. What held up

- **Anchors recomputed by hand.** Scores p1 0.6*8+0.4*7 = 7.6, p2 4.2+3.6 =
  7.8, p3 3.6+2.4 = 6, p4 5.4+2.4 = 7.8. Ranking p4, p2, p1, p3 (judges 9 vs
  7 break the 7.8 tie); CSV_TIE gives a Tie_Group {p2,p4} at 1, next 3.
  Eligibility true, true, false, false. Qualified (>= 7.7) false, true, false,
  true. They match the pinned values and the rule text in
  `tests/fixtures/app-reports/*/app-rules.md` and `slice-basic/PROVENANCE.md`.
  The expected values are written as literals, not computed by the code under
  test.
- **Two different rulebooks.** Prize runs `slice-basic/compiled.json`
  (document `rules.md`), Bracket runs the compiled `app-rules.md` book (adds
  `qualified`). `the_two_modules_run_over_different_rulebooks` checks that the
  reports cite different documents.
- **Orders.** A->B, B->A, repeat A->B, per-record interleaving in both start
  orders and reversed, whole sets between records, and two threads with a
  barrier and ten rounds. Each run is compared on results bytes (outcomes and
  traces through `serialize_results`), human bytes, JSON bytes and class.
- **Environment child.** `spawn` uses `env_clear`, then only `RT_WORKFLOW_MODULE_CHILD`
  and the variant's variables (plus `SystemRoot` on Windows). Output is
  compared byte for byte with the baseline child and with the parent for all
  jobs of both modules. Canaries are checked in stdout and stderr together.
  Baseline equality is not vacuous (job lines with both classes asserted).
- **Gates**, run in the worktree inside the loopback-only wrapper: see section 6.
- No existing test, golden or assertion was weakened; no `#[ignore]`, no skip.
  Req 27.15 is explicitly marked unsatisfied in the status note and is not
  claimed. The deferral note and the original text are intact; the lift is a
  new line.
