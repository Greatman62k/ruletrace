## 4. Non-blocking findings

**F1 (Low).** `assert_cases_ran` is tested only as a plain function, in `proptest_floor_unit.rs`. No test checks that the macro's counter increments only for passing cases or that the macro calls the assertion.
- M1 (call to `assert_cases_ran` removed from the macro) survived.
- M5 (counter incremented before the body, so cases rejected by `prop_assume!` would count) survived.
- Today the check is redundant in practice. proptest runs until `cases` passes, so `ran >= wanted` holds on any `Ok` result.
- It is the only guard if proptest's run loop changes.
- Suggested test: a `property_tests!` block whose body rejects some inputs with `prop_assume!`, with a counter that is asserted to equal the case count.

**F2 (Low).** The commit message says "13 blocks / 22 tests". The list has 21 `below` lines over 13 files. There are 13 `below_floor_config` blocks. A per-file count of `fn` items inside those blocks gives 21. The scan test requires an exact match between the list and the sources.
- The 128/64/24 counts are right: 15 entries at 128, 5 at 64, 1 at 24.
- The commit message and the brief should say 21. No file needs to change.

**F3 (Info).**
- The scan checks that the crate `lib.rs` contains the `mod proptest_floor;` line and the `#[path]` attribute. It does not check the `#[cfg(test)]` line.
- All 12 `lib.rs` includes are `#[cfg(test)]`. Checked with a script: 12 of 12.
- A non-test include would fail to compile, because `proptest` is only a dev-dependency.
- The scan reads only literal `with_cases(N)` counts. rt-data's `cases(512)` helper and the struct-form configs are caught only at run time by `effective_config`, which asserts a count of at least 256.

**F4 (Info).**
- The body is expanded as `{ $body; ran.set(..); }`. A body that returns early with `return Ok(())` would pass in proptest but not be counted here, so the run would fail.
- Search of the converted files: only `?` and `return Err` appear, and `prop_assume!` in three tests. No early `Ok` return.

## 5. What held up

**Check 1: the diff changes no assertion, generator, strategy or count.**
- I normalised whitespace, then counted every distinct added or removed line in the non-tool, non-new-test files. Result: 68 `proptest!`→`property_tests!` renames (67 at one indent, 1 at another).
- The other added lines are 38 `#[path]` lines, 38 `mod proptest_floor;`, 58 `use ...property_tests;` lines (32 `crate::`, 26 plain), and 12 `#[cfg(test)]` lines with blank lines.
- Config lines: 8 of `with_cases(128)`, 4 of `with_cases(64)` and 1 of `with_cases(24)` were renamed `proptest_config`→`below_floor_config`, with the count unchanged.
- Nothing else changed.
- `git grep 'with_cases('` before and after gives identical counts per value: 1024 ×2, 512 ×7, 256 ×24, 128 ×8, 64 ×4, 24 ×1.
- No `Cargo.toml`, `Cargo.lock` or CI file changed.
- Proptest regression files were not touched.

**Check 2: macro semantics.** I compared `property_tests!` with proptest 1.12.0 `proptest!` (`src/sugar.rs` lines 151-199 and `@_BODY`/`@_BODY2`).
- The body expansion goes through `proptest_helper!(@_BODY / @_BODY2)`, both arms present.
- `test_name` is `module_path::name`, the same as `proptest!`.
- `source_file` is set by the helper from `file!()`. The call site is the test file, so the failure-persistence path is unchanged.
- `contextualize_config` is applied, so every `PROPTEST_*` variable except the count behaves as before. Shrinking and the failure panic format come from the same helper.
- `config.cases = config.cases.max(configured.cases)`: the environment can raise the count but not lower it.
- `effective_config` fails a configured count below 256 unless the macro set `below_floor`. Only the `below_floor_config` arm sets it, and the scan ties that arm to the list.
- The counter increments after `$body`. A `prop_assume!` rejection returns from the closure before the increment, so rejected cases are not counted.
- Persisted-seed replays can push `ran` above `wanted`, so the check is `ran >= wanted`. Observed: `ran` 257, 1035 and similar.
- `prop_assume` and filters: three converted tests use `prop_assume!` (`tests_log.rs:495`, `tests_redaction_property.rs:361`, `coverage_partition.rs:203`). `prop_filter` and `prop_filter_map` are used in several files, and they filter at generation time. All of these tests passed with `ran == wanted`: 7 redaction tests and the log test at 256/256, `coverage_partition` at 128/128. A legitimate run is not failed by the counter.
- `PROPTEST_FORK` was not tested. The feature is not used in the repository (`git grep PROPTEST_` finds only the floor tests and docs).

**Check 3: default-config blocks keep their cases.** The 10 default blocks now use `Config::with_cases(256)`. This keeps `Config::default()`'s failure persistence, since `with_cases` is `Config { cases, ..Config::default() }`. Previously the default was 256 unless the environment overrode it. No count dropped, and the environment can no longer lower it. The run with `PROPTEST_CASES=3` showed 61 tests at exactly 256.

**Check 4: includes and architecture.**
- `xtask check-graph` reports ok (28 workspace crates), and so do `check-tree`, `scan-sources`, `scan-api`, `check-decisions`, `check-catalogue`, `check-justification`, `check-app-layers` and `check-executables`.
- No `Cargo.toml` changed, so no edge was added.
- The include appears in 12 `lib.rs` files under `#[cfg(test)]` and in 26 `tests/*.rs` files (38 includes in all). No file under `src/` other than `lib.rs` includes it.
- Production builds do not see it.

**Check 5: below-floor list.** `tools/proptest-below-floor.v1` has 21 entries over 13 blocks, each with its count (see F2). The counts equal the parent commit's `with_cases` values for the same files. The header calls each entry a "Req 20.2 gap awaiting a user decision". Nothing in the list or macro says the tests comply. The scan test fails on a stale entry, a wrong count, or a `below_floor_config` block at 256 or more. A listed test is still protected against `PROPTEST_CASES` (counts 128, 64 and 24 observed unchanged under `PROPTEST_CASES=3`).

**Check 6: the scan test.** I read all of `proptest_floor_scan.rs`. It covers the four stated rules, and each rule has a negative fixture with exact expected messages. The workspace test also requires more than 40 files to be seen, so an empty scan cannot pass. Gaps are F3.

**Check 7: `PROPTEST_CASES=3` over the workspace.** I temporarily added an `eprintln!` to `assert_cases_ran` in the scratch worktree and removed it afterwards. Under `PROPTEST_CASES=3`, 2389 tests passed and every property test ran at least its configured count: 1024, 512, 256 (61 tests), 128, 64 and 24. The environment test raised to 300 and ran 300. Several tests ran slightly more than configured because of persisted regression seeds.
