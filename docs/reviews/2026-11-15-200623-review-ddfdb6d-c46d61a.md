# Stand-in `ai` demonstration profile, store-aware coverage and CI action upgrade

Commits ddfdb6d..c46d61a add task 8.17. `demo/stand-in-ai` is a five-clause synthetic demonstration whose proposals come from an authored provider script replayed by the mock provider. The coverage generator (`rt-demo::coverage`) learns to read Proposal_Store batches. A new acceptance test, `crates/rt-demo/tests/acceptance.rs`, runs the `ai` profile step by step against new goldens. CI moves `checkout` to v5 and `upload-artifact` to v6 (Node 20 deprecation), runs the `ai` profile in `demo-offline`, and skips it in `core-only`. No existing golden, fixture or assertion was changed.

Watch for: no blocking defect found. The Windows `.windows` goldens have never run on Windows (confirmed, disclosed by the author). The owner-only chmod is only caught by the test when the checked-out source file is group- or other-readable (confirmed by mutant). The `core-only` skip is a broad substring filter with no guard (confirmed).

**Verdict**: APPROVED

## High-level view

The script is two authored entries keyed by the Request_Identifiers that `--dry-run` prints, and the document is the `hand` text plus two clauses. Clause 4 (prize money) is an `unrecognized` draft that stays pending with RT-VAL-0003. Clause 5 is a deliberate off-by-one misreading ("at most 18" for "under 18") that the reviewer rejects with a reason. The two clauses classify as claimed, and mutants on the capability source and the unsupported finding are killed.

Everything under `demo/stand-in-ai/` is added. The only modified files outside the new directory are `ci.yml`, `Cargo.lock`, `rt-demo` sources (additive) and the spec notes. The only removed line in `crates` is a doc line in `golden.rs` that was reworded.

The Windows goldens differ from the Unix ones by exactly the skipped-directory-sync wording that the pre-existing `rt-ai-tool` Windows constants (`tests_gate_rig.rs`) fix independently. The Windows target compiles with `--all-targets`. Beyond that, nothing is verified on Windows.

In CI the `ai` profile needs `ruletrace-ai`, which `core-only` deliberately does not build, so the skip is justified. The rest of `core-only` (hand profile, tree check, byte-identity) is unchanged. The skip mechanism is the weak part.

Both deviations are acceptable against the requirements. The first needs the design and task text amended. The second needs a decision before task 8.18.

## Authored script keyed by dry-run ids, and the two classified clauses

Both entries in `provider/authored-script.json` have `origin: "authored"`, and the file's `captured` text says "not provider output". The manifest counts authored 2, recorded 0. The ids `ab5e5c4a…` and `be41f0e4…` are the ones printed in the s02 golden stderr, which is produced by the real tool, and the acceptance test compares them with the script keys. The `response_sha256` values are checked against the payload by the test, and a negative test shows a changed payload is reported with its Request_Identifier. A stand-in script with an `authored` label does not satisfy "real provider output" in Req 33.8, but 33.8 itself allows authored entries if they are labelled and never described as provider output. The RUNBOOK says exactly that.

Clause 4 is a draft of kind `unrecognized` named `prize_allocation`. It is not approved or rejected, stays pending, and `validate` is unaffected (RT-ING-0006 Warning only, s04 stderr). The Coverage_Statement row reads `unsupported | RT-VAL-0003, prize_allocation`. Clause 5 tests `age <= 18` against text "under 18", so the rejection reason in the ledger is accurate: an entrant aged exactly 18 would be a junior. The ledger holds three approvals and one rejection with the reason. I re-ran the acceptance test and the coverage unit tests on Linux: 7 `ai_profile_` tests and the rest of `rt-demo` pass, clippy with `-D warnings` is clean, and `cargo fmt --check` is clean.

## Windows goldens and platform risks

`s02.stdout.windows` and `s02.stderr.windows` follow the wording of the pre-existing, independently written Windows constants in `rt-ai-tool/src/tests_gate_rig.rs` (header `complete, directory durability not confirmed`, `stored:` `(none)`, the `stored, directory durability not confirmed (skipped by platform)` heading) and the warning text in `run.rs`. RT-AI-0309 is appended last, after the two RT-AI-0305 warnings, matching `run_requests`, which pushes it after the loop. The check `ai_profile_windows_goldens_differ_from_…` compares both files with literals written in the test, so it detects drift between the two sets of goldens, but its literals come from the same author and commit. The independent anchor is the `rt-ai-tool` constants, which I compared by reading.

`cargo check --target x86_64-pc-windows-gnu -p rt-demo --all-targets` finished with no errors, and `make_private` has a `cfg(not(unix))` no-op. Compile success says nothing about runtime. The acceptance test also expects RT-AI-0309 per platform through `with_platform_skip`, so the step diagnostics on a real-disk Windows run are covered by that expectation. `perm.rs` returns no mode on non-Unix, so RT-AI-0009 cannot appear there and no Windows chmod is needed. `.gitattributes` has `* -text`, so no line-ending conversion alters goldens. Goldens and runbook use forward slashes only, and no host path is printed.

Mutants run by me, each restored afterwards (`git status` clean): reading the capability from the validator message was killed (2 tests fail), forcing the Windows golden on Linux was killed (2 fail), disabling the unsupported finding was killed (2 fail). Removing `make_private` survived with my checkout (source file mode 0600, `fs::copy` carries the mode) and was killed (3 tests fail) once the source was 0644, which is the mode git records. I changed the local mode of `mock-replay.toml` from 0600 to 0644 for that run and left it (git status is clean either way). CI checkouts are normally 0644 under umask 022, so CI would catch it, but the test depends on the checkout (issue 1).

## CI changes

`checkout@v5` and `upload-artifact@v6` both exist as tags upstream (`git ls-remote`). Each of the 19 replaced lines is a pure version bump with unchanged inputs. Artifact names are unique per matrix entry, so v4+ semantics cause no conflict. Node 24 actions need a recent runner, which hosted runners provide. No other deprecated syntax was found. This answers the steering request to handle CI deprecations as far as can be known without logs.

`demo-offline` adds `--test acceptance` to the command run under `unshare --net` on Linux and without isolation on macOS and Windows. The ai tests need `ruletrace-ai`, and `cargo build --workspace --bins` in that job builds it, so the binary exists. The acceptance test's `cargo metadata` uses `--offline`.

`core-only` excludes the AI crates from the build and test. If the ai tests ran there they would fall back to `cargo build -p rt-ai-tool` and build the auxiliary crates inside the job, which defeats what the job proves. Skipping them is correct. The job still builds and tests the hand profile and the rest, then runs the tree checks and byte comparisons. What it cannot show is that the ai tests ran: they run in `test` (three OSes) and `demo-offline` (three OSes), so the tests are not unrun overall, only filtered in this job, and the filter appears in the job log as "filtered out", not as a pass. The filter is a substring match over the whole workspace (issue 2).

## Deviations

Review list order: Req 33.7 step 3 says "list and review the Proposals with review list, approve, and reject" and fixes no order inside the step. `review list` requires an existing ledger (RT-CLI-0003 otherwise) and only approve or reject with `--create-ledger` may create one (Req 33.11 forbids creating a ledger any other way). The implementation follows the requirement and contradicts only the design table (§8.11.4, "review list …, then one approve") and the task text. This is not a requirement violation, but the design and task text should be amended by a recorded decision. The cost is that s03a approves without a listing in the runbook, and the content hashes of every approve step were read from the tool, so they are not independent of the tool (the author discloses this).

Hand and ai compiled bytes: Req 16.18 and design 668 define equal output for equal Rule_Content, and Rule_Content includes spans and the document hash. The `ai` document has two more clauses and a different hash, so the Rule_Content is not equal and no requirement is violated. The test asserts equal Outcomes, which is the correct claim here. Task 8.18 asks for byte-identical artifacts "when their Rule_Content is equal", which this pair cannot give. A decision is needed before 8.18 (issue 5). It does not block 8.17.

## Spec notes

Task 8.17 stays `[-]`, with the two open points stated, and the traceability entry claims neither the three-platform run nor the Proof_Report replay check for `ai`. Both statements match what I found. The entry says "four controlled mutants killed"; I reproduced four mutant runs with the outcome described above, and one is checkout-dependent.
