## 4. Non-blocking findings

Report-content issues the user should know before approving (point 2):

**F1. Provenance "verified" next to a clause that does not state the rule (point 2a). Caveat, recommend a README note.**
`rank.standing` in `slice-basic` cites bytes 92..170, the score clause. The source has no ranking clause and no tie-breaker clause, yet the three Tie_Group goldens print `source rank.standing@1 rules.md 92..170 line 4:1 "2. The score is 0.6 times …"` under `trace … verified`, and the bracket goldens print "criterion 1 (desc, rule rank.standing): 7 vs 7" with no source for the judges tie-breaker. The test-local `elig.qual` (threshold 7.7) cites the same span (`QUALIFIED_RULE` in the test, `"start":92,"end":170`), and the qualification golden prints that clause as its source. 7.7 appears nowhere in the source. Under Req 34.4 "verified" means the span resolves against a hash-matching Source_Model, which is true here, so this is not a false claim by the letter. It is misleading to a reader, because the report header carries no statement that defines "verified" (F3). It also reflects a fixture limit: no span is fabricated, but the fixture's rules are loosely bound to the source. A golden would freeze this presentation. Mitigation that needs no code change: add one sentence to the READMEs of the five ranking cases and the qualification case saying the cited clause is the score clause because the source has no ranking or threshold clause. Re-staging the README changes only README.md.

**F2. DIAGNOSTICS "none" in published cases (point 2b). Caveat.**
`ruletrace evaluate` writes the published differences as Warnings RT-EXE-0011/0012 (`rt-cli/src/evaluate.rs:393-412`, `published_warnings`). The application reports show `DIAGNOSTICS none` in all four published cases and carry the difference, with its code, only under PUBLISHED CONSISTENCY. Req 31.7 (published value, computed value, trace entry reference, no own comparison) is met. Req 31.14 does not cover diagnostics. The report is consistent with the CLI about the difference but not about the Diagnostic list: a reader who compares with stderr sees two Warnings against "none". The test checks the difference count against stderr (`identical`, `DIFFERENCE_CODES`) but not the DIAGNOSTICS section against stderr text. No decision exists on whether application reports should list these Warnings. User decision needed only if the user wants them listed.

**F3. Empty `statements` (point 2c). Caveat, known N4 and task 11.9.**
Header prints `statements: ` with a trailing space (every `report.txt`, line 5) and `"statements":[]` in every `report.json`. The reports therefore carry none of the required header statements: the Workflow_Module boundary statement (design §8.6, ST-BOUNDARY, Req 34.1), the definition of verified (Req 34.4), and the synthetic-data statement of Req 34.6 beyond the `data: synthetic` label. Req 34.7 requires the documentation scan to fail on an application report header lacking a required statement, so these goldens would fail that scan when it exists. Approving now freezes a header that task 11.9 must change, so all 11 `report.txt` and `report.json` files will be re-blessed. The headers make no claim outside the support boundary, so nothing prohibited is frozen.

**F4. `data: synthetic` (point 2d). Correct, with a note.**
The label is correct: the participants are hand-made, and `synthetic_data: Some(true)` is passed by the test (design §8.5: "from the caller; label only"). It is a caller assertion, not derived.

**F5. Machine report closed and deterministic (point 2e). Correct.**
Field-set check above (0 extra paths in 11 files), no timestamp, path, or environment value, inputs named by role and SHA-256 only. Two independent runs of bless mode produced identical bytes (see section 5). The existing `bracket_check_field_set` and no-IO tests passed in the workspace run.

F6. **Whole-standings Indeterminate.** For missing `judges`, the report shows one Indeterminate entry for the whole ranking Target and no per-participant positions. This follows Req 12.4 as implemented by the engine (every participant's position depends on the unknown comparison). Req 32.1 words it "each Indeterminate position". The user should read the golden as "all positions Indeterminate", which the README says.

**F7. Qualification report carries a ranking line.** `bracket-qualification-weighted-score/report.txt` and `.json` print `ranking: Standings are calculated solely from the declared ranking rules; this report does not apply eligibility filtering.` although no ranking was requested. Harmless but irrelevant to that case.

**F8. Design divergence on fixture layout.** Design §7.3 names `tests/fixtures/app-*` directories and says each holds the emitted data, questions, published and results files. The staged layout is `tests/fixtures/app-reports/<case>/` with request.txt and the CSV inputs only. The task text as amended by UD-38 asks for reports, so this is not a task failure. Task 9.18 (s08) is the stated place for the byte-identity of emitted files.

Test-design findings (point 3):

**T1. Tautological assertion.** `check_expectations` begins with `assert_eq!(produced.observed.class_code, case.code, …)`. `Observed.class_code` is set to `case.code` in `produce`, so this assertion cannot fail. The exit code is genuinely checked inside `identical()` (CLI exit code against `class_code`), so coverage is not lost, but the line is a tautology under testing-integrity §2.3 and should be removed or replaced.

**T2. Weaker pin for the Indeterminate ranking Outcome.** `bracket-standings-indeterminate` pins the Outcome by `starts_with` the first reason and `contains("RT-EXE-0006")` instead of the full text. The golden bytes cover the rest once approved. The comment states why.

**T3. Present-from-typed-values limit.** Honestly stated in the file header ("Limit: no results-file parser exists before task 13.3"). The test does assert that the results bytes of the library run equal the bytes `ruletrace evaluate` wrote (`identical`, bytes compared), that the exit codes agree, and that the published difference counts equal the Warnings on stderr. Present still receives typed values from the library evaluation, not parsed from the CLI results file. `diagnostics`, `verifications` and `comparison` handed to Present are checked only indirectly (results bytes include diagnostics and verification, and difference counts are compared).

**T4. Bless mode is unguarded.** `RT_APP_GOLDEN_BLESS=<dir>` makes each case write and return success without comparing. If the variable leaks into CI, 11 tests pass with no comparison. If `<dir>` is `tests/fixtures/app-reports`, it overwrites goldens with no diff review, which testing-integrity §9 treats as automatic snapshot updating. The hand-derived Outcome checks still run before writing, which is good. The doc comment says "another directory" but nothing enforces it. Suggest a refusal when `<dir>` resolves under `CASES_DIR`. A relative `<dir>` resolves against the crate directory, so the user should pass an absolute path.

**T5. Stray files not detected.** Compare mode checks every expected file but not extra files in a case directory. Minor.

**T6. Inputs are generated, then compared.** The test builds inputs from constants and compares the committed input files to them; it does not read the committed `participants.csv` as input. The effect is the same byte check. The `request.txt` format is invented by this test; task 13.3 may define a different one.

APP_TARGET_* at the CLI-argument Cli_Location is covered in both crates. Since the mapping is one implementation in `rt-data`, this is a gap in Req 31.15's "for each Application_Layer", not in behavior.
