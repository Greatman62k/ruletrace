## 4. Non-blocking findings

**Q1. Is the byte comparison circular? Not in a way that hides a defect the
property is meant to catch.**
Both sides call `rt_explain::results::serialize_results`. Design 8.10 and D-12
make this the means of byte identity. What the test does not check is the
serializer itself: a defect in `serialize_results` or in the engine changes both
sides equally. Those are covered by other tests (golden files and engine tests).
The two sides differ in everything between the engine and the serializer:

- The CLI side never sees the library's typed values. It receives only the bytes
  `Prepared::{data,questions,published}_bytes` produced, plus `compiled.json` and
  one `model{i}.json` per Source_Model (printed with `m.print()`). It parses them,
  runs `rt_engine::evaluate` itself, verifies traces and serialises.
- The expected exit code is not derived by the CLI. It is the library's
  `ResultClass` mapped to 0, 4, 2, 70 by the macro `exit_code!` at lines 118 to 127.
  The map is written in the test. The pinned test (lines 478 to 502) writes 0, 0,
  0, 4, 2 for five inputs. `rt_explain::class_of_run` is shared between the two
  sides, so only the pinned expectations are independent of it.

The test catches (each shown by a mutant in section 7):

- Canonical-bytes defects: `data_bytes`, `questions_bytes`, `published_bytes`
  (M12, M13) and any round-trip loss.
- Evaluate-group engine-call arguments: Questions passed, published passed (M6, M7).
- Source_Models handed to `verify_trace` (M5).
- Exit-class mapping (M14, M15).
- Published comparison count seen by the CLI (M6, and M12 together with the results file).

It cannot catch (Prepare mutants survive, M1 to M4):

- A Prepare defect that keeps the typed values and their canonical bytes consistent
  with each other: dropped published rows, reordered or dropped Questions, changed
  id mapping, Missing becoming a default. The library and the CLI both consume
  Prepare's output. Those defects are owned by the `prize-check` and `bracket-check`
  unit tests, which killed M1 to M4 when I ran them (section 7).
- A defect in `serialize_results`, the engine, or `rt_explain::class_of_run`.

This matches Req 31.5. It states the Competition_Data as "serialized from the
Competition_Data that the Application_Layer mapped".

**Q2. Generator.** I instrumented a scratch copy to log each case, then reverted.
Over 256 cases per application (512 logged runs, matching `with_cases(256)` at line 458):

| | Prize | Bracket |
| --- | --- | --- |
| exit 0 / 4 / 2 | 125 / 114 / 17 | 147 / 94 / 15 |
| published file present | 117 | 123 |
| cases with any published difference | 113 | 111 |
| cases with tie split (kind 1) / tie not computed (kind 2) | 9 / 15 | 10 / 15 |
| sources Real / Absent / OtherDocument | 142 / 69 / 27 | 158 / 59 / 20 |
| row counts | 1 to 11 seen (12 in 3 runs overall) | same generator |

- Target subsets: every non-empty mask is reached (Prize masks 1 to 7 at 29 to 53
  cases each, Bracket masks 1 to 3 at 75 to 96 each).
- Boundary values: threshold 16 spelled `16`, `16.0`, `15.99`, `16.01`; threshold
  7.7 and `7.70`; ties via `7`, `7.0`, `8.00`; a 28-fractional-digit literal;
  Missing cells in half of the cases.
- The cases are meaningful and non-trivial. Exit 2 arises only from the
  OtherDocument source kind (not from invalid data).
- The 256 count is fixed in source and not guarded by a tool. Other properties
  in the repository do the same. I did not run with `PROPTEST_CASES` set.
  `with_cases` overrides the environment variable by proptest's documented behaviour.

**Q3. Fixtures and CSV helper.** The test reports 64 runs, and the arithmetic is
right: four slice fixtures with one data file and no published file give 4 runs
each, and the two demos with two data files and three published variants give 24
each. 16 plus 48 is 64. `data_to_csv` and `published_to_csv` panic only for
collections, unknown fields or an unparsable canonical file. I added a temporary
assertion in the scratch copy that `parse_data` of the prepared bytes equals
`parse_data` of the committed file. It held for all six fixtures and every data
file. Byte equality to the committed files fails everywhere, because the committed
files are pretty-printed. That is expected, and the test does not claim byte equality.
Gap: lossless conversion is not asserted in the test (F4).

**Q4. Stderr check of RT-EXE-0011/0012/0013.** It is correct. The three codes are
written in the test from the catalogue (`DIFFERENCE_CODES`), and `check-catalogue`
passes. Req 31.5 lists the Published_Result as one of the equal inputs, but the
results file holds no comparison. Without this check a dropped or altered published
file whose rows do not touch outcome bytes would pass. M6 is killed by it together
with the pinned test. It belongs in Property 42. The check compares counts only
(F5). A string count of the code could include a code mentioned in a message body,
but 512 generated runs agree, and `published_warnings` emits one diagnostic per difference.

**Q6. MemFs duplication.** `support/app_eval.rs` copies the in-memory `Fs` already
present in nine other test files (`prize_check_exit_codes.rs`,
`bracket_check_exit_codes.rs`, `exit_code_*`, `contradictory_flags_*`,
`review_refusals_*`, `approval_*`). `read` truncates at `max_bytes` exactly as
`StdFs::read` does with `take`. Risk: a future change to the `Fs` trait needs
eleven edits, and a fake that diverges from `StdFs` can make one test pass or
fail alone. No present defect.

Also: `evaluate_bracket_with_eligible` (lines 695 to 755) repeats about 50 lines of
the `go!` macro. It exists because the committed rulebooks hold no `qualified`
rule, so Bracket qualification is requested on `eligible`. The note in lines 660
to 663 explains this.

Comments and formatting: `rustfmt --edition 2021 --check` on both files exits 0.
The comments are short and give reasons.
