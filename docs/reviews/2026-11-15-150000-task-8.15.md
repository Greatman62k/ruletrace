# Gate-level failure tests for `ruletrace-ai propose` (task 8.15) and three fixes found on the way

Six commits (2d333c1, a27432f, 2bc7339, e71697a, ac69cf2, 67d51ca) add one `run_with` gate test per failure class, pin RT-IR-0001 for a malformed Rulebook, add an over-redaction test, extend Property 30, and fix three defects: RT-AI-0006 raised too late, RT-AI-0302 never raised, and provider failures located at the request instead of the `provider` field. The fixes match the spec on placement and location, and the mutants I ran are killed. One in-scope requirement is still unmet: Req 23.17 asks for the number of attempts in the message of every provider failure, and the non-transient errors (RT-AI-0104, 0105, 0108) omit it.

Watch for: (1) RT-AI-0104/0105/0108 messages carry no attempt count, which Req 23.17 requires and which is in the task's requirement list (confirmed, `run.rs` NonTransient arm). (2) A batch file whose name differs from its internal `request_id` passes `check_store`, but the idempotency check looks up by file name, so such a batch is invisible and the same request is sent and stored again (likely, not run). (3) `Providers::is_linked` defaults to `true`.

**Verdict**: NEEDS_CHANGES

## High-level view

The gate tests drive the real entry point over a scratch directory and assert exit code, Run_Summary text, store file list and Transmission_Log lines. Expected values are written out in the tests from the requirements and catalogue.

The step-2 placement of RT-AI-0006 matches the Req 28.17 order (provider kind after disabled state, before consent and credential). The new store check sits at step 4, after plan build and before the first request, which fits the Req 23.33 table. Parser diagnostics pass through unchanged, which Req 22 (lifecycle flags) requires.

Provider-failure location now follows Req 23.17. The same criterion also requires the attempt count in the message, and only the retry-related errors have it.

Property 30 runs 256 cases against a hand-written ladder. Both mutants I applied are killed by it and by dedicated tests.

## RT-AI-0006 moved to configuration time

Req 28.17 orders the load checks as TOML syntax, inline secret, field checks, limits, endpoint, disabled state, provider kind, consent, credential. `propose` now runs `load_config` (which covers everything up to the disabled state) and then asks `is_linked`, before `load()` handles consent and credential. That is the 28.17 order, and the step table of Req 16.17 lists AI_PROVIDER_UNKNOWN in step 2 and the credential and consent in step 3. Req 28.12 asks for the Input_Location of the provider kind field, and the diagnostic now uses `config.provider_at`.

The config is parsed twice (`load_config` here, then again inside `load`). The cost is trivial, but both parses must keep agreeing, and nothing asserts they do.

`--dry-run` returns before the link check. No spec text says it must refuse an unknown or unlinked provider. Req 28.12 says "no network call" for an unknown provider, and dry-run opens none. The design's `--dry-run` paragraph (CLI section, near line 1208 of design.md) says it reads no credential, writes nothing and needs no consent, and a person may want to preview what an unlinked hosted provider would receive. I would leave it, and I would record the decision (issue 6).

`is_linked` defaults to `true`. With the default, an implementation that forgets the override still ends in `unavailable_provider` from `adapter()`, so it is not a fail-open on transmission. It does silently put RT-AI-0006 back at step 4 for that implementation, which is the bug this commit fixed, and the compiler cannot flag it. `BuiltInProviders` overrides it correctly. Task 10.5 will link `rt-ai-openai` and must update `is_linked` for `openai-responses`; the existing test `an_unlinked_provider_*` will then need a different unlinked kind. Make the method required (issue 3).

The two step-3 tests were moved to the linked `Steps` provider and kept their assertions; that is a legitimate input change, since a hosted provider that this build does not link now correctly wins.

## RT-AI-0302 and the store check

`check_store` is called after `build_plan` and before `providers.adapter` and the first request. Req 16.17 step 4 is "Input load and idempotency check" and the 23.33 table lists, in order: AI_REQUEST_INVALID, AI_STORE_INVALID, Req 22 codes, then the idempotency Warning. Plan build failures are request-invalid cases, so plan before store matches the table. The idempotency check lives in the call loop (`batch_exists` per request) and so runs after the store check, which is required: a malformed store must not be trusted for the "already stored" answer.

Parser diagnostics are returned as-is. Req 22 criterion 17 (lifecycle flags) says a flagged input yields exactly one LIFECYCLE_FLAG_CONTRADICTION naming the fields, and `parse_batch` returns RT-DGN-0001 to 0003 for that case and RT-AI-0302 for the rest. Mapping everything to RT-AI-0302 would break that. Read errors and a listing error become RT-AI-0302 at the path.

The read is bounded at `MAX_PROPOSAL_BATCH_BYTES + 1` (16 MiB + 1), so a huge file cannot exhaust memory, and `parse_batch` rejects anything above the limit. Files are read one at a time. No test builds an oversize file, so the "limit+1 gives RT-AI-0302" path rests on reading (issue 4).

The spec is silent on a batch whose file name differs from its `request_id`. `batch_exists` looks only for `batches/<request_id>.json`, so a batch stored under another name does not count as stored. The run would send the request again and write a second batch with the same `request_id`. `rt review` has the same blind spot. I recommend `check_store` returns RT-AI-0302 located at the file when the stem is not the 64-hex `request_id` of the parsed batch, with a test (issue 2). This is a spec decision for the user, because both Req 23.33 and the design are silent.

Dry-run does not validate the store. The design text for `--dry-run` lists what it reads and writes and names no store, and the Req 23.33 "no provider call" effect does not apply since nothing is sent. Leave it.

The mixed-failure order between a Req 22 flag in an input file and a malformed store is not pinned (issue 5).

## Provider failure location and attempt count

`provider_failure` uses `config.provider_at` for per-attempt Warnings and final Errors. The test expects `ai.toml`, line 3, column 1, field `provider`, which is what Req 23.17 states.

The implementer's note is right. Req 23.17 reads: "THE AI_Tool SHALL return the Diagnostic defined in the following table with a primary Location that is the Input_Location of the provider field ..., and the number of attempts made (1 to 3) in the message". The sentence is unconditional on the failure kind. Req 29 criteria 5 and 6 repeat it for RETRY_EXHAUSTED and DEADLINE_EXCEEDED, which do have counts ("3 attempts failed; ..." and "... after 2; ..."). In `run.rs` the `NonTransient` arm builds `"<MNEMONIC> (<detail>)"` with no count, so RT-AI-0104, 0105 and 0108 omit it (confirmed). Those tests check code and severity only, so the omission is not pinned by an assertion and the fix does not need an assertion change. 8.15 lists 23.17, so this is a defect in scope. It is also a place where the tests need exact messages (issue 1).

## Property 30 and test quality

`ProptestConfig::with_cases(256)`, and the generator varies hosting (mock, linked, unlinked), missing credential, invalid store, TooLarge and Incomplete responses on top of earlier causes. The expected ladder is written in `expected()` from the Req 16.17/28.17 order, not computed by the production code. I ran two mutants (below), each failing the property. The commit says the property failed before the fixes (RT-AI-0008 for an unlinked provider without consent); I did not re-run the pre-fix state.

The gate tests assert Run_Summary strings (`COMPLETE_ONE`, `NONE_PROCESSED`), exact `findings`, store file lists, log lines and batch bytes against a clean baseline run. `unwrap` appears only in test rigs; `store_check.rs` has none on input paths. Comments follow the placement rules.
