## 3. Blocking findings
B1. `tools/decisions/UD-44.md:27-28` says "No Diagnostic is printed for this exit, as the design states". Design §11.18.6 (lines 3636-3652) does not say this. `grep -n -i "no diagnostic\|prints no"` in design.md finds only unrelated lines (735, 1998). The same claim is stated as fact in the amendment note, design.md:3651 ("prints no Diagnostic"). Req 5.12 (requirements.md:663) says a failure that is an internal error exits 70 "and SHALL write a Diagnostic of Severity Error ... to standard error". A silent exit 70 is therefore a new decision that departs from Req 5.12 wording, and the decision should say so. Fix: either remove "as the design states" and record the silent exit as a new, user-confirmed point (with the Req 5.12 and Req 27 exit-code-table exception named), or have the exit write a Diagnostic. Because UD-44 has `amends: none`, the Req 5.12 tension is currently hidden.

## 4. Non-blocking findings
N1. `UD-44.md:27` adds "or a read error" to the exit-70 trigger. Design L says only "on end of file". This is a new design decision, and it is a reasonable one (fail closed), but it is not flagged. Flag it in the decision as an author addition for the user to confirm, or drop it.
N2. `UD-44.md:28-29` says "Code 70 is in the exit-code set of both executables (Req 27)". Verified for the sets (steering: ruletrace 0, 2, 3, 4, 70; ruletrace-ai 0, 2, 3, 5, 6, 70; requirements.md:666 lists 70 for ruletrace). The citation to Req 27 is loose; the code sets come from Req 5 and the Req 27 table, and mean "internal error", not "parent gone". Cite exactly.
N3. The design's own text (line 3646) says the bound is "set from that measurement" by 13.9. UD-44 sets it ahead of 13.9 on prototype evidence. The note states the evidence and says it is measured again, so this is acceptable. 13.9 (tasks.md:1696) is still `[ ]`.
