# `review list` on a missing ledger

Range a5dc07b..2834071 (d50a8ce, 2834071). `ruletrace review list` now treats a missing ledger as the empty ledger: it exits 0, shows prospective revision numbers and creates nothing. The production change is one argument in `crates/rt-cli/src/review.rs` (`load(args, true, &pair)`). Malformed, zero-byte, tampered and unreadable ledgers are still refused. Req 26.6, design 3.8.3 and traceability were amended. The production change is sufficient and safe on every case probed on real disk. The commit leaves one test that now fails and one unfixed instruction in the demo runbook.

Watch for: `crates/rt-demo/tests/ai_independence.rs` still expects `review list` on a missing ledger to exit 2 with `RT-CLI-0003`, so `ruletrace_output_is_identical_in_all_eight_combinations` fails (confirmed, blocking); a mutant that treats every read error as a missing ledger survives (confirmed, non-blocking coverage gap); `tasks.md` line 926 and `demo/stand-in-ai/RUNBOOK.md` line 25 still describe the old behaviour (confirmed, non-blocking).

**Verdict**: NEEDS_CHANGES

## High-level view

The change works through the existing reader path. `list` still calls `read_pair`, which takes the shared lock by opening `<ledger>.lock` read-only, so it never creates the lock file. A missing ledger is recorded there as a failed read of kind `NotFound`, and `load_ledger` turns exactly that kind into the empty ledger when its `create` flag is set. `approve` and `reject` still pass `--create-ledger` as that flag, so only they can start a ledger. Every other read failure goes through the same diagnostics as before.

Prospective numbers come from the Rulebook alone (`prospective_adoption` takes the highest revision of the rule in the Rulebook and adds 1), so they are right for rules that already have revisions, with or without a ledger. No new test covers that case.

The amended text matches the behaviour. The test suite catches reverting the change and catches letting `approve` ignore `--create-ledger`. It does not catch widening "missing" to "any read error". The `rt-demo` acceptance test was not updated, and that test fails.

## Why the one-line change is enough, and what was probed on disk

The check is on the error kind, not on the text or the path. I ran the built binary on a copy of the fixture with these ledger paths: a missing file, a missing parent directory, a directory in place of the file, a zero-byte file, a path below a regular file, a dangling symlink, a file with mode 000, and a path under a read-only directory. A missing file, a missing parent, a dangling symlink and a missing file below a read-only directory exit 0 and leave the tree unchanged. A directory exits 2 with `RT-CLI-0003` ("is a directory"). A zero-byte file exits 2 with `RT-APR-0101` (header missing). A path below a regular file exits 2 with `RT-APR-0214`, because the shared-lock open fails first. A mode-000 file exits 2 with `RT-CLI-0003` ("permission denied"). None of the exit-2 cases is turned into an empty ledger.

The dangling symlink is read as missing, which is correct for `list` because nothing is written. `approve --create-ledger` on that path would replace the link by renaming over it. That behaviour belongs to the existing commit path and the diff does not touch it.

Concurrent creation between the check and a later approve is handled by the existing reader. `read_pair` reads both files twice and refuses with `RT-APR-0214` if the bytes differ, or if the lock file appears while it was absent at the start. A ledger that appears between the two reads therefore refuses instead of showing a stale empty listing. `approve` takes the exclusive lock before it reads, so a ledger created by a racing approve is read, not overwritten.

## Does `list` write, and the lock file

`list` creates nothing. The real-disk test compares the full tree before and after for both an existing-parent and a missing-parent ledger path. I also listed the directory after each run: no `.lock` file appears. The shared lock is opened with `File::open`, never with create. The in-process test also asserts that the fault log has no `create_new`, `rename`, `remove`, `hard_link` or `try_lock` operation.

A refused `approve` without `--create-ledger` does create an empty `<ledger>.lock`: I reproduced it (`l.jsonl.lock`, 0 bytes). I do not count this as a defect. Req 26.37 requires the writer to take the exclusive lock "before it reads or changes any file", and the lock file is the thing that is locked, so it must exist. The only requirement that demands no file creation on a lock failure is the unsupported-locking case, and that path is unchanged. The review module doc already says the lock file is a control file that is not review state. The consequence is that the task 6.2 sentence "refusals ... leave every file byte-identical" is not literally true for a refusal on a missing ledger, and the real-disk test says so in a comment instead of asserting it. That matches the user decision and is acceptable. A later `list` still creates nothing when the lock exists, and I checked that it exits 0 and leaves the tree as it was.

## The failing demo test

`failing_commands()` runs after every runbook step in each of the eight cells and asserts an exact exit code and a diagnostic code. Its second entry runs `review list` with `--ledger work/no-ledger.jsonl` and expects `2` and `RT-CLI-0003`. The Rulebook exists, so the command now succeeds and the matrix fails with `left: 0, right: 2` at "failing command 2". `cargo test -p rt-cli` (164 library tests) and `cargo test -p rt-tests-ai` pass, so the break is visible only in `rt-demo`. The author's commit message lists in-process and binary tests but not `rt-demo`. This is a real behavioural consequence of the user decision, so the test must change. Changing the expected result is justified by the amended Req 26.6, and the replacement entry must keep an exact code and exit code so the coverage of "missing input is refused" is not reduced.

## Test strength

I ran three mutants against `crates/rt-cli/src/review.rs`.

1. `list` passes `false` (the old behaviour): killed by four tests in `tests_review_list_missing.rs` (the list, equals-empty, no-store and approve-after-list tests).
2. `decide` passes `true` instead of `d.create_ledger`: killed by `approve_and_reject_without_create_ledger_still_fail_on_a_missing_ledger` and the older `a_missing_ledger_needs_create_ledger`.
3. `load_ledger` accepts any read error as empty when `create` is set: survived the `rt-cli` library, binary and integration tests. This is a genuine coverage gap. The positive tests only use a really missing file, and the malformed tests only use bytes that were read successfully.

The tests have an independent basis: expected text comes from the requirement and from a fixture with pinned hashes, and the `list` output is compared with the output for an explicitly empty ledger, which is a good oracle for "missing equals empty". The tampered-ledger test breaks the chain by editing a reviewer name and checks `RT-APR-0102`. The zero-byte case is covered. No assertion was weakened, no golden changed, and nothing was skipped.

## Spec text

Req 26.6(b) says what the code does: exit 0, prospective numbers, no ledger, lock or temporary file, and malformed or chain-failing ledgers rejected with the same diagnostic. Design 3.8.3 step 3 matches, apart from one imprecise phrase: "the pair read of `read_pair` already reports a missing ledger" should say that `read_pair` records the ledger as not found and `load_ledger` maps that to empty. Req 26.6 and the catalogue name `LEDGER_NOT_FOUND` (RT-APR-0106) for the refusal, while the binary emits `RT-CLI-0003`. That mismatch existed before this change and the tests assert `RT-CLI-0003`. It is out of scope here and worth a separate decision.
