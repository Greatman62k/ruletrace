## 4. Non-blocking findings

**F1 (medium). Duplicated Workflow_Module code between `prize-check` and `bracket-check`.**

- Evidence (`diff` of the two crates at cf9c12b):
  - `mapping.rs` (199 lines) and `classify.rs` (63 lines) are byte-identical.
  - `prepare.rs` (183 lines) and `evaluate.rs` (122 lines) differ only in the type names `PrizeRequest`/`PrizeInputs` vs `BracketRequest`/`BracketInputs`.
  - In `report.rs`, `PresentError`, its `Display`, `published_text`, `computed_text`, `published_section` and `run_diagnostics` (about lines 54 to 180) are identical.
  - About 600 duplicated library lines in total. The 5 test files are largely parallel.
- No drift exists today. Nothing guards against it. Any fix to the mapping, the published section or the class logic must be made twice by hand.
- Is the design violated?
  - Design §8.2 says "Shared code is not duplicated between the two applications". That sentence is violated in letter.
  - The §8.2 table does not assign the compiled-to-`InputSchema`/`TargetKinds` derivation, `Prepared`/`Rejection`, `PresentError`, the published section or `ResultClass`. For these the design is silent, so this is a gap in the design.
  - Req 15.6 and 31.2 are not violated. They forbid a second implementation of eligibility, scoring, ranking or tie-breaking. The duplicated code is mapping glue and presentation, and no computation is duplicated.
  - The status note discloses the duplication ("Duplication to resolve later") and gives the cause: `forbid-name` between the packages, and no shared crate on the allowed-edges list.
- The fix is only partly mechanical.
  - `classify.rs` can move into `rt-explain` with no edge change. `rt-explain` already owns `classify_evaluation` and `has_question_fault`, and the file needs only `Outcome`, `DiagnosticState` and `Verification`.
  - `mapping.rs`, `prepare.rs` and the published part of `report.rs` need `CompiledRulebook` (`rt-compiled`) together with `rt-data::tabular`, or `rt-engine::Comparison`. No crate that both applications may use has these dependencies today.
  - So the fix needs a decision. The options are a new edge (`rt-data` to `rt-compiled`, or `rt-explain` to `rt-engine`/`rt-compiled`), or a shared crate with an amendment of the Req 24.12 whitelist. A new edge or a new crate is not a decision to take in a refactor.
  - Until then, a cheap guard would be a test or xtask rule that fails when `mapping.rs` and `classify.rs` differ between the crates.
- Recommend: record the decision (a design RN with the edge or crate) and a follow-up task before 9.8 or 9.16. Do not fold it into 9.6.

**F5 (low). The engine-call scan exempts files by name (`tests_*`).**

- The scan in `bracket_check_no_io.rs` (`the_engine_is_called_in_exactly_one_place`) skips every file whose name starts with `tests_`. `tests_report.rs:502` calls `rt_engine::evaluate` directly to build a trace the library never produces.
  - The exemption is acceptable. `lib.rs` declares every `tests_*` module under `#[cfg(test)]`. The forbidden-identifier scan still covers those files.
  - It rests on a naming convention. A production file named `tests_x.rs` would escape the call scan.
- The scan sees only the token pair `rt_engine evaluate`. `use rt_engine as e; e::evaluate(..)` or `use rt_engine::{evaluate}` is not seen.
- Recommend: also assert that each `tests_*.rs` is declared after `#[cfg(test)]` in `lib.rs`. This is a heuristic scan, and 9.8 owns the full scan.
