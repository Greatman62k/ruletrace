# Windows real-disk test expectations and golden binary build

Commit 1b042e5 gives the real-disk `rt-ai-tool` tests per-platform expectations for the Windows directory-sync skip (`RT-AI-0309`, header note, separate `stored, directory durability not confirmed (skipped by platform)` heading). It adds `cfg(windows)` constants and the helpers `skip_shapes` and `skip_findings`, which the changed tests use. Commit bf25ce2 builds the `ruletrace` binary once per process in the golden tests, using a `OnceLock`, to address a macOS `Os NotFound` flake. It adds a launch-failure message and a thread test.

Watch for: one real-disk test still asserts Unix-only stderr and will fail on Windows (confirmed by simulation, not on a real Windows host). The new golden test passes on the old code, so it cannot detect the flake, yet its doc comment calls it a regression test (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The Windows constants match design 3.7.5 and Req 23.36 / 29.19 line for line. Linux and macOS constants are the old literals moved into `cfg(not(windows))`, and the old Linux assertions are unchanged. The coverage is almost complete. The one miss is a second, baseline run inside `transport_failure_then_success_stores_one_batch_and_exits_0`, which asserts that every stderr line starts with `request ` and will see the `RT-AI-0309` warning line on Windows.

The `OnceLock` is sound for the in-process race it targets and harmless otherwise. It does not help if tests ever run one process per test, and CI uses plain `cargo test`, so it does not apply today. The commit message says honestly that the flake was not reproduced. The new test was never red, and neither the commit message nor the test comment says so.

Reword it as a launchability smoke check and record in the commit or a doc that the fix is an unverified mitigation.
3. **`skip_findings` comment claims a basis it lacks** (confirmed, minor) — the comment says the message is "written by hand from the design (3.7.5)". Design 3.7.5 does not give that text. 4. **Nested build can still race across processes** (possible) — the `OnceLock` serializes threads of one test binary only. Other integration binaries in `rt-tests-core` that launch `ruletrace` through a different path are not covered, and nextest-style per-test processes would bring the race back. Check what the other test binaries do before closing the flake.

## Coverage of real-disk tests that store a batch

I enumerated every `run_std`, `run_with(..., &StdFs)` and `run_providers(..., &StdFs)` user in `rt-ai-tool` and read each one that ends in a successful store. The updated ones are `tests_cli_run` (the stdout/shape test, the blocking-findings test, the `a_warning_never_changes_the_exit_code` non-Unix arm), `tests_gate_failures` (retry success, unsupported clause, three-request clean and failing runs), `tests_revise` (the observable revision run) and `tests_store_invalid` (two shape checks). Tests that store but assert only the exit code, file lists or batch bytes are platform-neutral (`a_run_opens_no_ledger_file...`, `tests_revise_target`, `tests_store_invalid` rename cases). The second-run tests find an existing batch and store nothing, so they correctly expect only `RT-AI-0301`. `tests_run` and `tests_store` already branch on `cfg!(unix)` from 8fdfe97, and `tests_exit_order_property` filters on errors only. The one exception is the baseline run at `tests_gate_failures.rs:100` (issue 1).

I could not run Windows. To find misses I simulated it on Linux: `StdFs::sync_directory` forced to return `SkippedByPlatform`, and the `cfg(windows)` choices in `tests_gate_rig.rs` forced on (temporary edits, restored with `git checkout`, tree clean afterwards). Of 514 lib tests, 509 passed. Four failures were artefacts of the simulation, because their branches key on `cfg!(unix)` or `cfg(unix)` which I did not flip. Those are `a_warning_never_changes_the_exit_code`, `two_runs_on_one_real_disk_store_each_batch_once`, `the_real_file_system_reports_the_platform_directory_outcome` and `concurrent_runs_on_a_real_disk_store_one_batch_and_report_the_rest`, and each already carries a correct non-Unix branch. ## Windows constants against the requirements

The header `run summary: complete, directory durability not confirmed`, the empty `stored:\n  (none)`, and the heading `stored, directory durability not confirmed (skipped by platform):` match Req 23.36 and the worked example in design 3.7.7. The incomplete case keeps plain `incomplete` with the skip heading, as Req 23.36 states. A skip warning ordered after `RT-AI-0305` matches the Diagnostic ordering text. Nothing on Linux or macOS is weakened: the `cfg(not(windows))` literals equal the strings the tests had before (verified in the diff for `COMPLETE_ONE`, the three-request text and the incomplete text), `skip_shapes()` and `skip_findings()` return empty off Windows, and the `assert_eq!` forms are stricter than the earlier `is_empty()` checks, not looser.

`cargo check --target x86_64-pc-windows-gnu -p rt-ai-tool --tests` finished with exit 0, after touching `lib.rs` to force a recheck. The `cfg(windows)` constants therefore compile. Compilation is not execution, and no Windows or macOS test run was available to me.

The `skip_findings` comment names design 3.7.5 as the source of the message text (issue 3). The code string and the test string are identical, so the test pins the implementation, not an independent text.

## Golden binary build once per process

The likely cause is a nested `cargo build` from a parallel test relinking the binary while another thread launches it. The `OnceLock` removes that within one test binary: the first caller builds, the others block in `get_or_init`, and nobody launches before the build finishes. The launch panic now names the binary and work dir and records whether each exists, which helps diagnose a recurrence.

The commit message says "not reproduced on Linux" and the cause is stated as a theory ("Parallel golden tests each ran a nested cargo build"). That is honest about the evidence. The test doc comment is not: "Regression for the macOS NotFound flake". I put the old `ruletrace_binary` back with the new test appended and ran it three times: 1 passed each time. The thread test never fails on the old code on Linux, so it shows only that 24 threads can launch the binary. It ignores the exit status of `--help`, so it checks launchability and nothing more. As a smoke test it is fine. As a red/green regression test it is not, and `docs` or the commit should say the fix is an unverified mitigation until one macOS CI run is green. I do not treat this as blocking, because there is no reproducible defect to pin and the change cannot make anything worse.

Whether other `rt-tests-core` test binaries launch `ruletrace` is not established by this diff. Only `tests/golden/slice.rs` and `ingest.rs` use `ruletrace_binary` (grep), and `cargo test` runs test binaries one after another, so the race is limited to threads inside `golden`.
