## 4. Non-blocking findings

- N1. The module doc of `workflow_module_isolation.rs` (lines 8 to 10) still
  says each run "must equal the same run made alone". The code compares with the
  fresh-child baseline. The `tasks.md` correction states this, the file header
  does not. Comment only.
- N2. The 9.17 status note counts "6 tests" and "11 tests, one of them the child
  entry". The isolation file now has 8 tests (7 plus `child_entry`). The
  correction line does not restate the count. The original note stays as
  written by rule, so this is only a stale number in a preserved note.
- N3. The baseline child runs the jobs of one module one after another in one
  process, so state that leaks between jobs of the same module appears in the
  baseline too. It is still detected, because the parent runs the jobs in other
  orders, and in the same process as other tests (I tried mutant C1, section
  7). A leak that depends only on the job order of the first pass would not be
  caught by the baseline. I did not find one. Low risk.
- N4. The isolation tests do not detect process-wide state in the environment
  tests' sense (a mutant that leaks identically into child and parent passes the
  environment tests, as with I2). The isolation tests cover that. This is
  correct division of labour, noted for completeness.
- N5. The clock variant stays probabilistic, as F4 and the note state. My
  parity-of-second mutant (E4) was killed in one run, partly by chance across
  separate processes. It is not a deterministic kill.

## 5. What held up

F1, fresh-process baseline.
- `baseline_child(app)` (`app_runs.rs`, end of file) uses `spawn_child`, which
  calls `Command::new(current_exe())` with `.env_clear()`, sets only
  `RT_WORKFLOW_MODULE_CHILD` and `RT_WORKFLOW_MODULE_APP`, and `current_dir`
  of the temp directory. Each baseline is one child per module that runs only
  that module's jobs (`jobs_of`). Verified by reading, and by mutants S7 (no
  `env_clear`) and S6 (wrong cwd), both failing seven environment tests.
- Comparison covers class, results, human and JSON: `render_job` prints all
  four, length-prefixed, and `assert_sequence_equals_solo` compares the whole
  byte string for every job. The orders covered: prize then bracket, bracket
  then prize, a third pass, interleaved per record in both start orders and in
  reverse, whole sets between records, and two threads with ten rounds. The
  child result is keyed by job name and `solo[&job.name]` panics on a missing
  key, so no job is skipped. All jobs of both modules are in the baseline.
- My earlier I2 (`render_human` caches the first report per module) now fails
  `prize_then_bracket_and_bracket_then_prize_equal_the_solo_runs`,
  `runs_interleaved_per_participant_record_equal_the_solo_runs` and
  `two_threads_running_the_modules_at_once_equal_the_solo_runs`.
- My earlier I3 (append `!` once both modules ran) fails the same three
  isolation tests, plus two environment tests (the in-process comparison).
- The expected outcomes pinned by hand (`solo_runs_have_the_hand_derived_...`,
  `single_record_runs_...`) are unchanged and independent of the baseline.

F2, per-variant probe.
- `assert_all_equal` calls `assert_probe_matches(v)` for every `Variant` before
  the run. The probe prints cwd, presence of `ai.toml` and `ruletrace.toml`,
  and every variable it holds. `assert_eq!(got, intended(v))` compares the
  maps exactly, so an extra or missing variable, a wrong value or a wrong cwd
  fails. The only skipped names are the marker and, on Windows, `SystemRoot`.
- Every variant of the cwd, locale, time zone, PATH (including empty) and
  credential tests goes through `assert_all_equal`. The combined variant too.
  The clock test runs two starts of the empty-environment variant and does not
  go through the probe. Its environment is empty by construction (`framed`
  with `variant("clock", &w.empty, &[])`). See N5 for its limit.
- Canaries: the probe shows a canary only as `<canary one>` or `<canary two>`.
  `assert_probe_matches` and `assert_all_equal` both search stdout and stderr of
  the probe and the run for both canary strings. The control test asserts the
  literal probe lines and that `RT-CANARY` appears nowhere.
- Earlier spawn-drop survivors re-run: S1 (drop `MODEL*` and `RULETRACE_*`)
  and S2 (drop `PATH`) now fail three environment tests each. Further: S3 (drop
  `OPENAI_API_KEY`), S4 (drop `TZ`, `LC_ALL`, `LANG`), S5 (drop empty values,

- Library-side environment mutants (E1 to E4) fail as expected.
